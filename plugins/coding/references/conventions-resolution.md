# コーディング規約の優先順位解決

Analyze フェーズで実施する、適用すべきコーディング規約の解決手順。`orchestrator-coding` / `orchestrator-design` と各言語スキル（単独起動時）が共用する。
「プロジェクト独自規約が常にデファクト規約より優先される」ことを保証する単一情報源。

## 1. 優先順位（上位が勝つ）

| 優先度 | 規約ソース | 例 |
|-------|----------|-----|
| 1（最優先） | **ユーザの明示指示**（当該セッションでの指定） | 「インデントはタブで」「この命名規則で」 |
| 2 | **プロジェクトの機械設定ファイル** | `.editorconfig`、リンター/フォーマッタ設定（`eslint.config.js` / `.prettierrc` / `pyproject.toml [tool.ruff]` / `.php-cs-fixer.php` / `phpcs.xml` / `stylelint` / `dotnet .editorconfig` 等） |
| 3 | **プロジェクトの文書規約** | リポジトリの `CLAUDE.md`（ルート + 対象ディレクトリの階層）、`.claude/rules/**/*.md`、`docs/` 配下のコーディング規約文書、`CONTRIBUTING.md` |
| 4 | **既存コードの一貫した慣習** | 同一モジュール内の既存コードが一貫して従うスタイル（新規コードは周辺コードに揃える） |
| 5（デフォルト） | **言語プロファイルのデファクト規約** | 各言語スキル `coding-{lang}` の `references/conventions.md` の準拠規約 |

判断原則:

- 上位ソースが規定していない項目は、次順位のソースで補完する（全面置換ではなく **項目単位のオーバーライド**）
- 優先度 2（機械設定）と 3（文書規約）が矛盾する場合は機械設定を優先し、矛盾があった旨を成果物に記録する
- 優先度 4 の「既存慣習」がデファクト規約と異なる場合（例: 既存 JS が 4 スペース）、**既存慣習に揃える**。ただし既存コードに一貫性がない場合は言語スキルのデファクト規約を採用し、その判断を記録する

## 2. 検出手順

### 2.1 機械設定ファイルの走査（優先度 2）

対象リポジトリのルートから以下を Glob で検出し、存在するものを Read する:

| 分類 | 検出対象 |
|------|---------|
| 共通 | `.editorconfig` |
| JS/TS | `eslint.config.{js,mjs,cjs,ts}`、`.eslintrc*`、`.prettierrc*`、`prettier.config.*`、`biome.json` |
| Python | `pyproject.toml`（`[tool.ruff]` / `[tool.black]` / `[tool.mypy]`）、`setup.cfg`、`ruff.toml` |
| C# | `.editorconfig`（dotnet 診断規則）、`Directory.Build.props`、`stylecop.json` |
| PHP | `.php-cs-fixer{,.dist}.php`、`phpcs.xml{,.dist}`、`phpstan.neon` |
| CSS | `.stylelintrc*`、`stylelint.config.*` |
| SQL | `.sqlfluff`、ORM 設定（`prisma/schema.prisma` 等） |

各言語の設定ファイル詳細は対応する言語スキルの `conventions.md` にある「プロジェクト規約ファイル」セクションを参照。

### 2.2 文書規約の走査（優先度 3）

| 検出対象 | 読み方 |
|---------|-------|
| `CLAUDE.md`（リポジトリルート） | 全体を確認し、コーディング規約に関する記述を抽出 |
| `CLAUDE.md`（変更対象ディレクトリの祖先階層） | 対象ファイルに近い階層を優先 |
| `.claude/rules/**/*.md` | コーディング関連ルールを抽出 |
| `docs/**/*.md` のうち規約系文書 | ファイル名に `convention` / `style` / `coding` / `規約` を含むものを優先確認 |
| `CONTRIBUTING.md` | コーディングスタイルのセクションのみ |

### 2.3 既存慣習のサンプリング（優先度 4）

変更対象と同じディレクトリ・同じ言語の既存ファイルを 2〜3 件 Read し、以下を確認する:

- インデント（幅・スペース/タブ）
- 命名規則（言語スキルのデファクト規約と一致するか）
- import / using の整理順
- コメントの密度・言語（日本語 / 英語）

## 3. 規約サマリの生成（成果物への記録）

解決結果は `impact-analysis.md` の「適用規約サマリ」セクションに **必ず** 記録する。形式・記入欄はテンプレート [`template/impact-analysis.md`](template/impact-analysis.md) の同名セクションが正典（構成: 「検出された規約ソース」= 優先度 1〜5 の検出結果表 / 「適用規約（解決後）」= 項目・適用値・根拠ソース表 / 「矛盾・特記事項」）。下流フェーズ（Design / Implement / Self-Review）はこのサマリのみを規約の根拠として参照する。

## 4. 禁止事項

- プロジェクト独自規約の走査（節 2.1〜2.3）を省略して言語スキルのデファクト規約だけで実装すること
- 規約サマリを生成せずに Phase 3 以降へ進むこと
- 上位ソースの規定を言語スキルのデファクト規約で上書きすること
- 既存コードの一貫した慣習を「デファクトと違う」という理由で書き換えること（規約統一のリファクタリングはユーザの明示依頼があった場合のみ）
