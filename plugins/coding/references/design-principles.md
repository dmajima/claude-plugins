# 設計原則（SSOT）

設計観点・リスクヘッジ・データフローの言語横断ルール。
`orchestrator-coding` の Phase 3（Design）と `orchestrator-design` の設計フェーズが共通で参照する。
言語ごとのコード構造（レイヤ配置・モジュール構成・FW 固有パターン）は各言語スキル `coding-{lang}` が保有し、本ファイルには置かない。

## 1. 設計観点（言語非依存）

設計書（implementation-design.md）を作成する際、以下の観点を必ず検討する:

| 観点 | 確認内容 |
|------|---------|
| 責務分離 | 変更・追加するコードの責務が単一か。既存の責務分割（層・モジュール）と整合するか |
| 依存方向 | 依存が安定した方向（下位層・抽象）へ向くか。循環依存を生まないか |
| 境界 | モジュール境界・API 境界を跨ぐ変更は境界の契約（型・スキーマ・エラー仕様）を明示したか |
| 拡張性 | 将来の変更に対して閉じすぎ / 開きすぎでないか（推測に基づく過剰な抽象化はしない） |
| 一貫性 | 既存コードベースのパターン（命名・構造・エラー処理）と揃うか。新パターン導入は理由を明記 |
| テスト容易性 | 変更部分を独立に検証できるか（依存の注入・副作用の分離） |
| 可観測性 | 障害時に原因を追えるか（ログ・エラーメッセージの設計） |

## 2. リスクヘッジ

### 2.1 リスク分類と対応戦略

設計書のリスク欄は以下の分類で評価する:

| 分類 | 典型リスク | 標準対応 |
|------|----------|---------|
| 互換性 | 既存 API / データ形式 / 挙動の破壊 | 後方互換の維持（変更でなく追加）。破壊的変更はユーザ確認 + 移行手順の明記 |
| データ | スキーマ変更・データ移行の失敗 | expand-contract（追加 → 移行 → 削除の段階分割）。破壊的マイグレーションの単独実施禁止 |
| 性能 | N+1・大量データ・ブロッキング | データ量の見積り。ホットパスの変更は計測手段を先に確認 |
| セキュリティ | インジェクション・認可漏れ・秘密情報露出 | 入力検証と出力エスケープの境界を設計段階で明示。秘密情報は設定・環境変数へ |
| 運用 | ロールバック不能・デプロイ順序依存 | ロールバック手順を設計に含める。デプロイ順序に依存する変更は手順を明記 |

### 2.2 ロールバック方針

- 変更は「戻せる単位」で計画する（1 目的 = 1 まとまり）
- 戻せない操作（データ削除・不可逆マイグレーション）は実行前にユーザ確認を必須とする
- 実装中の遡行でコードを破棄する場合の既定動作は「変更を残したまま遡行」（破棄はユーザ確認後）

### 2.3 大規模・高リスク判定（architect レビューの起動条件）

以下のいずれかに該当する設計は `architect` エージェントのレビューを必須とする:

- 5 ファイル以上かつ複数モジュール横断
- 技術選定（新規依存・ライブラリ・FW の導入）を伴う
- 認証・認可・決済・個人情報などの高リスク領域に触れる
- スキーマ変更・データ移行を伴う

## 3. データフロー設計

### 3.1 基本原則

| 段階 | 原則 |
|------|------|
| 入力 | 信頼境界（ユーザ入力・外部 API・ファイル）を跨ぐデータは境界の直後で検証する |
| 変換 | 変換ロジックは純粋（副作用なし）に保ち、検証済みデータのみを受け取る |
| 永続化 | パラメータ化クエリ / ORM 経由を必須とする（文字列結合による SQL 組み立て禁止） |
| 出力 | 出力先の文脈（HTML / SQL / シェル / URL）に応じたエスケープを出口で行う |

### 3.2 エラーハンドリング方針

- エラーは「握りつぶさない・二重処理しない」: 処理できる層で 1 回だけ処理し、できない層は伝播させる
- ユーザ向けメッセージと内部ログを分離する（内部詳細・スタックトレースをユーザに露出しない）
- 失敗時のデータ整合性を設計する（トランザクション境界・部分失敗時の状態）

### 3.3 設計書への記録

データの流れが変わる変更では、設計書に「入力元 → 検証 → 変換 → 保存/出力先」の流れを 1 段落または簡潔な図（mermaid）で記録する。

| 知識 | 置き場所 |
