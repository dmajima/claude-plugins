# Case 02: スキーマ全体設計への波及による orchestrator への切替提案

## 入力

| 項目 | 値 |
|-----|---|
| 起動フレーズ | 「注文テーブルにステータス履歴を持たせて」 |
| 引数 | なし |
| フラグ | なし |
| 既存状態 | `provider = "postgresql"` が判定できるリポジトリ。単独依頼として起動したが、方言判定・規約解決の過程で `orders` テーブル変更に加え履歴テーブル新設・外部キー・インデックス・ORM モデル／リポジトリ層の修正へ波及し、変更見込みが 4 ファイル以上かつスキーマ全体設計に及ぶと判明 |

## 期待動作

### ステップ1〜3: 方言判定・規約解決・ORM 確認
- 通常どおり PostgreSQL を確定し、独自規約（`.sqlfluff` / ORM スキーマ規約等）と `prisma/schema.prisma` を走査
- この過程で影響が単一クエリ／単一テーブルに収まらず、複数テーブルのスキーマ変更とアプリコード（ORM モデル・リポジトリ層）修正に広がることを把握

### ステップ4 手前での規模判定
- 変更見込みが 4 ファイル以上に膨らむ、かつスキーマ全体設計（テーブル間関連・マイグレーション順序・後方互換）に及ぶため、言語スキル単独の想定規模を超えると判断
- 実行フローのステップ6 に定義された「変更見込みが 4 ファイル以上に膨らむ、またはスキーマ全体設計に及ぶ場合は `orchestrator-coding` への切替を提案する」に従う

### 切替提案
- 対話モード: 影響範囲・想定変更ファイル数・スキーマ設計論点（履歴の持ち方・expand-contract の段階）を提示し、`orchestrator-coding`（6 フェーズ統括）への切替を提案。ユーザ承認後に切替
- 非対話モード（`--non-interactive`）: 最も保守的な解釈として、破壊的変更を確定せず、後方互換を保てる最小の expand 段階のみ提示し、残りの波及範囲と `orchestrator-coding` 推奨を報告に記録

## 期待出力

| 項目 | 期待値 |
|-----|-------|
| 切替提案 | `orchestrator-coding` への切替を提案（対話）／推奨を報告に記録（非対話） |
| 生成ファイル | 提案時点ではスキーマ変更・マイグレーションを確定しない。フェーズ成果物は生成しない |
| 終了状態 | 成功（切替提案）／ユーザ判断待ち |

## 分岐の根拠

このケースが分岐するトリガーは 変更見込み = 4 ファイル以上 または スキーマ全体設計に波及 である。
複数テーブルにまたがるスキーマ変更とアプリコードへの波及はフェーズ統括を要するため、単独実行モードで押し切らず `orchestrator-coding` へエスカレーションする。
