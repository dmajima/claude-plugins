# SQL 言語プロファイル（方言横断・共通）

SQL には C# の `.editorconfig` 慣習や Python の PEP 8 に相当する **単一のデファクトスタンダード規約が存在しない**。
本プロファイルは、複数の DBMS・スタイルガイド・ORM で **広く受け入れられている慣習** を「プロジェクト独自規約が存在しない場合のデフォルト」として整理したものである。
断定的な「標準」ではなく「慣習」として扱い、プロジェクト内に既存の書式・命名がある場合は必ずそちらを優先する（優先順位の解決は
[`conventions-resolution.md`](../../../references/conventions-resolution.md) に従う）。

方言固有の仕様（識別子クォート・データ型・ページング構文・UPSERT・実行計画コマンド・エラーコード）は
各方言プロファイル（[mysql.md](mysql.md) / [sqlserver.md](sqlserver.md) / [postgresql.md](postgresql.md)）に分離している。

## 1. 識別（プロジェクト検出）

| 項目 | 値 |
|------|-----|
| 対象拡張子 | `.sql` |
| マーカー | `migrations/` ディレクトリ、`db/` / `database/` 配下の SQL、ORM スキーマファイル（`schema.prisma` / EF Core の `Migrations/`（`*.cs`） / Alembic の `alembic/versions/` / Laravel の `database/migrations/`） |
| 方言判定 | 接続設定・ポート・コンテナイメージから判定する。詳細な検出マーカーは [mysql.md](mysql.md) / [sqlserver.md](sqlserver.md) / [postgresql.md](postgresql.md) の「識別」を参照 |

方言が特定できない場合は本プロファイル（共通）のみを適用し、方言固有構文が必要になった時点でユーザに使用 DBMS を確認する。

## 2. 広く受け入れられた慣習（方言横断）

**位置づけ**: 以下は各 DBMS 公式のコーディング例・主要スタイルガイド・ORM 既定で共通して見られる慣習である。強制ではなく、**プロジェクト内での統一** を最優先とする。

### 2.1 命名規則

| 対象 | 慣習 | 例 |
|------|------|-----|
| テーブル名 | `snake_case` を推奨。単数形／複数形は **プロジェクト内で統一**（ORM の既定に従う。例: Eloquent は複数形 `users`、EF Core は `DbSet` 名に従う） | `order_items` |
| カラム名 | `snake_case` を推奨 | `created_at`, `unit_price` |
| 主キー | `id`、または `<table>_id`（プロジェクト内で統一） | `id` / `order_id` |
| 外部キー | 参照先を示す `<参照テーブル単数>_id` | `customer_id` |
| インデックス | 接頭辞＋対象を示す規則的な名前（プロジェクト内で統一） | `ix_orders_customer_id` |
| 制約 | 種別が分かる接頭辞（`pk_` / `fk_` / `uq_` / `ck_` 等） | `fk_orders_customer_id` |

- 大文字混在名（`OrderItems` 等）は方言によってクォートが必須になり事故の元になるため避ける（PostgreSQL は引用符なし識別子を小文字化、MySQL はテーブル名の大文字小文字感度が環境依存）。各方言プロファイルの「大文字小文字の扱い」を参照。
- 予約語（`order` / `user` / `group` 等）を識別子に使わない。使わざるを得ない場合はクォートするが、原則回避する。

### 2.2 インデント・フォーマット

| 項目 | 慣習 |
|------|------|
| キーワードの大小 | `SELECT` / `FROM` / `WHERE` 等の予約語を **大文字**、識別子を小文字にする書式が広く用いられる。プロジェクトで小文字統一している場合はそれに従う（重要なのは統一） |
| 主要句の改行 | `SELECT` / `FROM` / `WHERE` / `GROUP BY` / `HAVING` / `ORDER BY` / 各 `JOIN` は行頭で改行する |
| インデント | サブクエリ・`CASE` 式・`JOIN ... ON` の条件をスペース 2〜4 個でインデントする（プロジェクトで統一） |
| カンマ | 列挙時のカンマ位置（行末／行頭）はプロジェクト内で統一する |
| 文字列引用符 | 文字列リテラルは **シングルクォート** `'...'`（ダブルクォートは方言により識別子引用符の意味を持つため文字列には使わない） |
| 文末 | ステートメント区切りにセミコロン `;` を付ける |

書式例:

```sql
SELECT
    o.id,
    o.ordered_at,
    c.name AS customer_name
FROM orders AS o
INNER JOIN customers AS c
    ON c.id = o.customer_id
WHERE o.status = 'shipped'
  AND o.ordered_at >= '2026-01-01'
ORDER BY o.ordered_at DESC;
```

### 2.3 主要スタイル規則

- **明示的 JOIN 構文を使う**。`FROM a, b WHERE a.id = b.a_id` のカンマ結合（暗黙の内部結合）は使わず、`INNER JOIN ... ON` / `LEFT JOIN ... ON` を用いる。結合条件と絞り込み条件が分離され可読性・保守性が上がる。
- **本番コードで `SELECT *` を避ける**。必要な列を明示する。列追加時の予期せぬ挙動・不要なデータ転送・インデックスカバリングの阻害を防ぐ（アドホックな調査用途は可）。
- **意味のあるエイリアス** を付ける。`a` / `b` のような無意味な 1 文字ではなく、`orders AS o` / `customers AS c` のようにテーブルを示す短縮名を使う。相関サブクエリや自己結合で特に重要。
- 明示的な列指定を伴わない `INSERT`（`INSERT INTO t VALUES (...)`）は避け、`INSERT INTO t (col1, col2) VALUES (...)` と列を明示する。
- `NULL` 比較は `= NULL` ではなく `IS NULL` / `IS NOT NULL` を使う。
- 集計と非集計列の混在では `GROUP BY` に非集計列をすべて含める（方言により緩い場合もあるが、移植性のため明示する）。

## 3. ツールチェーン

SQL 用のフォーマッタ・リンタは複数存在し、いずれも「デファクト」ではないが実務で広く使われる。プロジェクトに設定ファイルがあればそれを優先する。

| 用途 | ツール（例） | 備考 |
|------|-------------|------|
| Lint / フォーマット | [SQLFluff](https://sqlfluff.com/) | 方言指定可能（`--dialect` / `.sqlfluff` の `dialect`）。`sqlfluff lint` / `sqlfluff fix` |
| フォーマット | pgFormatter、Prettier の SQL プラグイン等 | プロジェクトで採用しているものに従う |
| 実行計画 | 方言別（`EXPLAIN` 等） | コマンドは各方言プロファイルを参照 |

### プロジェクト規約ファイル（存在時は本プロファイルより優先）

| ファイル | 内容 |
|---------|------|
| `.editorconfig` | インデント・改行・文字コード |
| `.sqlfluff` / `pyproject.toml` の `[tool.sqlfluff]` | SQLFluff の方言・ルール設定 |
| ORM のスキーマ／マイグレーション規約 | [orm.md](../../../references/frameworks/orm.md) を参照。ORM が SQL を生成する場合、命名・DDL はそちらが一次情報源 |

## 4. イディオム・ベストプラクティス

### 4.1 安全性

- **パラメータ化クエリを必須とする（SQL インジェクション防止）**。ユーザ入力を文字列連結で SQL に埋め込まない。プレースホルダ（`?` / `$1` / `:name` / `@name`、方言・ドライバによる）とバインド値を使う。ORM 経由でも生 SQL を書く場合はパラメータ化する（[orm.md](../../../references/frameworks/orm.md) 参照）。
- **マイグレーションは後方互換を意識する（expand-contract パターン）**。破壊的変更（カラム削除・リネーム・NOT NULL 化）を 1 ステップで行わず、以下の 3 段階に分ける。
  1. **expand**: 新カラム／新テーブルを追加（既存を壊さない。旧新を並存させる）
  2. **migrate**: アプリを新スキーマ対応にデプロイし、データを移行
  3. **contract**: 全参照が新スキーマに移った後で旧カラム／旧テーブルを削除
  これによりデプロイ中の新旧アプリ混在（ローリングデプロイ）でも整合を保てる。
- **トランザクション境界を明示する**。関連する複数の変更は 1 トランザクションにまとめ、途中失敗時はロールバックする。DDL のトランザクション挙動は方言依存（PostgreSQL は多くの DDL がトランザクション可能、MySQL は多くの DDL が暗黙コミットを伴う）なので各方言プロファイルを参照。
- **大量更新・削除はバッチ分割する**。1 回の巨大な `UPDATE` / `DELETE` はロック保持時間・ログ肥大・レプリケーション遅延を招く。主キー範囲や `LIMIT`／`TOP` で数千〜数万件単位に分割し、各バッチをコミットする。

### 4.2 パフォーマンス基本

- **インデックス設計**: `WHERE` の絞り込み列、`JOIN` の結合列、`ORDER BY` のソート列にインデックスを検討する。複合インデックスは選択性の高い列・等値比較する列を先頭に置く（左端プレフィクスの原則）。ただしインデックスは書き込みコスト・容量とのトレードオフであり、過剰作成は避ける。
- **実行計画を確認する**: 遅いクエリは推測で直さず実行計画で確認する。フルスキャン／不要なソート／想定外の結合順序を検出する。方言別コマンド（`EXPLAIN` 系）は各方言プロファイルを参照。
- **N+1 問題を回避する**: 「一覧を 1 回取得し、その各行について関連を都度追加取得する」パターンは往復回数が行数に比例して増える。`JOIN` あるいは `IN` によるまとめ取得、ORM のイーガーロード（`include` / `Include` / `selectinload` / `with`）で解消する。詳細は [orm.md](../../../references/frameworks/orm.md)。
- 関数を索引列に適用しない（`WHERE DATE(created_at) = ...` はインデックスを使えないことが多い）。範囲条件（`created_at >= ... AND created_at < ...`）に書き換えるか、式インデックス／生成列を検討する。
- `LIKE '%foo%'`（前方一致でない部分一致）は通常インデックスが効かない。全文検索機能や専用インデックスの利用を検討する。

## 5. 典型エラーパターンと対処（方言横断）

方言固有のエラーコード（MySQL の `1062`、SQL Server の `2627`、PostgreSQL の `23505` 等）は各方言プロファイルの「典型エラーパターン」を参照。ここでは方言によらない一般的な誤りを挙げる。

| エラー傾向 | 原因 | 対処 |
|-----------|------|------|
| 一意制約違反 | 重複値の挿入 | 事前に存在確認、または UPSERT（方言別構文）を使う |
| 外部キー制約違反 | 親行不在の子行挿入／被参照の親行削除 | 挿入順序を見直す、`ON DELETE` 方針を設計、削除は子→親の順 |
| 意図しない全行更新／削除 | `WHERE` 句の付け忘れ | `UPDATE`／`DELETE` は必ず `WHERE` を確認。トランザクション内で `SELECT` により影響範囲を先に確認 |
| 暗黙の型変換による索引無効化 | 列と比較値の型不一致（文字列列に数値を比較等） | 比較値の型を列に合わせる |
| 照合順序（collation）の不一致 | 異なる collation の列同士の結合・比較 | 結合キーの collation を揃える |
