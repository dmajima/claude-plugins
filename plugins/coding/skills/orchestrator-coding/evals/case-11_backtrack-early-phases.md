# Case 11: 前段フェーズの遡行共通挙動（Phase 2 → Phase 1 を主シナリオに）

## 入力

| 項目 | 値 |
|-----|---|
| 起動フレーズ | 「ログイン画面にパスワードリセット機能を追加して」 |
| 引数 | なし |
| フラグ | なし |
| 既存状態 | Python（Django）プロジェクト。Phase 2 の影響範囲調査で「パスワードリセットは別モジュールに実装済みで、実際に不足しているのはログイン画面からの導線のみ」と判明する状況 |

## 期待動作

### Phase 2: Analyze（前提誤りの発覚 = FAIL）
- 影響範囲調査で、Phase 1 で整理した完了条件（リセット機能の新規実装）が誤りだったと判明（機能は既存、不足は導線）
- 品質ゲート判定 = FAIL（前提=タスク理解の誤り）
- workflow.md 節 0.3 遡行テーブルを参照し、「Phase 2 で前提（タスク理解）の誤りが判明 → **Phase 1**」に従って遡行先を決定

### 遡行処理（Phase 2 → Phase 1 = 主シナリオ）
- Phase 1: implementation-plan.md の完了条件・作業分解を「既存リセット機能への導線追加」に修正（対話モードでは範囲変更をユーザに確認）
- 修正後、Phase 2 から通常フローを再開
- 同一フェーズへの遡行は最大 3 回。超過時は試行内容・残る問題・選択肢を提示してユーザ判断を仰ぐ

### 他の前段遡行も同一の制御で動作すること（期待動作に明記）
いずれも「該当フェーズの品質ゲート FAIL → 遡行テーブル参照 → 指定フェーズへ遡行 → 修正 → 再開、最大 3 回」という共通制御に従う:

| 発生フェーズ | 検出内容 | 遡行先（テーブル） |
|------|---------|---------|
| Phase 3 | 設計中に分析不足が判明（影響範囲の依存漏れ等） | Phase 2 |
| Phase 4 | 実装中に設計の実現不能が判明（想定 API が存在しない等） | Phase 3 |
| Phase 6 | 報告時に成果物の欠落を検出 | 該当フェーズ |

- 遡行先はメインの恣意でなく **遡行テーブルの規定** で決まる（同じトリガー分類なら同じ遡行先）
- Phase 4 以降からの遡行で実装済みコードを破棄する場合は破棄範囲をユーザに確認（非対話モードは変更を残したまま遡行し記録）

## 期待出力

| 項目 | 期待値 |
|-----|-------|
| 遡行先 | 主シナリオ = Phase 1（前提誤り）。他分類も遡行テーブルの規定どおり |
| 生成ファイル | implementation-plan.md（完了条件を修正）+ 各成果物の遡行記録 |
| 終了状態 | 成功（遡行後 PASS）または 3 回超過時のユーザ判断待ち |

## 分岐の根拠

このケースが分岐するトリガーは 前段フェーズでの品質ゲート判定 = FAIL である。workflow.md 節 0.3 遡行テーブルの前段経路（Phase 2 → 1 / Phase 3 → 2 / Phase 4 → 3 / Phase 6 → 該当）が、いずれも同一の遡行制御で動作することを 1 ケースで検証する。Phase 5 起点の遡行は case-08 / case-10 が担当する。
