# Case 08: 品質ゲート FAIL → 遡行制御

## 入力

| 項目 | 値 |
|-----|---|
| 起動フレーズ | 「CSV エクスポート機能を追加して」 |
| 引数 | なし |
| フラグ | なし |
| 既存状態 | C#（ASP.NET Core）プロジェクト。Phase 5 の impl-reviewer が「設計時に想定していなかった既存 API との出力形式不整合（High）」を指摘する状況 |

## 期待動作

### Phase 5: Self-Review（FAIL 検出）
- impl-reviewer の High 指摘により品質ゲート判定 = FAIL
- 指摘原因が **設計起因**（出力形式の設計漏れ）のため、Phase 4 ではなく **Phase 3 へ遡行** すると判断

### 遡行処理
- Phase 3: 設計を修正（既存 API との形式整合を方針に追加）し、implementation-design.md を更新
- Phase 4: 修正後の設計で再実装。実装済みコードの扱い（残して修正 / 破棄）は対話モードならユーザに確認
- Phase 5: 指摘該当箇所を再レビュー（全件再レビューはしない）
- self-review-result.md の「遡行記録」に回数・理由・修正内容を記録

### 遡行上限
- 同一フェーズへの遡行が 3 回を超えた場合、試行内容・残る問題・選択肢を提示してユーザに判断を仰ぐ
- 提示内容の具体形:
  - 試行 1〜3 の内容: 各遡行で何を変更し、なぜ FAIL が解消しなかったか（例: 試行 1 = 出力形式の整合を設計に追加 / 試行 2 = 変換層を分離 / 試行 3 = 既存 API 側にアダプタを追加）
  - 残る問題: 依然 FAIL のままの品質ゲート観点と、根本原因の仮説
  - 選択肢: (a) 方針変更（別アプローチで再設計）/ (b) スコープ縮小（当該指摘の対象を切り出して段階対応・残りは残課題化）/ (c) 中止（現状の成果物を残して報告し、コミットはしない）

## 期待出力

| 項目 | 期待値 |
|-----|-------|
| 生成ファイル | self-review-result.md に遡行記録あり、最終的に Critical / High = 0 件 |
| 終了状態 | 成功（遡行後 PASS）または 3 回超過時のユーザ判断待ち |

## 分岐の根拠

このケースが分岐するトリガーは 品質ゲート判定 = FAIL（かつ指摘原因 = 設計起因）である。workflow.md の遡行規定（Phase 5 → Phase 3/4、最大 3 回）が適用される。
