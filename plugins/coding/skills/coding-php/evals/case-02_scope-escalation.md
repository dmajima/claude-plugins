# Case 02: 変更見込み膨張による orchestrator への切替提案

## 入力

| 項目 | 値 |
|-----|---|
| 起動フレーズ | 「このバリデーションロジックを共通化して全コントローラに適用して」 |
| 引数 | なし |
| フラグ | なし |
| 既存状態 | Laravel プロジェクト。単独依頼として起動したが、規約解決・影響確認の過程で FormRequest・複数コントローラ・共通トレイト・関連テストへ波及し、変更見込みが 4 ファイル以上と判明 |

## 期待動作

### ステップ1〜2: 規約解決・FW 確認
- 通常どおり独自規約（`.php-cs-fixer.php` / `phpstan.neon` / `composer.json` 等）と `laravel/framework` を走査
- この過程で影響範囲が単一ファイルに収まらず、複数コントローラ・共通化先クラス・テストに広がることを把握

### ステップ3 手前での規模判定
- 変更見込みが 4 ファイル以上に膨らむため、言語スキル単独の想定規模を超えると判断
- 実行フローのステップ5 に定義された「変更見込みが 4 ファイル以上に膨らむ場合は `orchestrator-coding` への切替を提案する」に従う

### 切替提案
- 対話モード: 影響範囲・想定変更ファイル数を提示し、`orchestrator-coding`（Intake → Analyze → Design → Implement → Self-Review → Report の 6 フェーズ統括）への切替を提案。ユーザ承認後に切替、または単独継続の指示があれば範囲を限定して継続
- 非対話モード（`--non-interactive`）: 最も保守的な解釈として、影響が閉じる最小範囲に限定して実装し、残りの波及範囲と `orchestrator-coding` 推奨を報告に記録

## 期待出力

| 項目 | 期待値 |
|-----|-------|
| 切替提案 | `orchestrator-coding` への切替を提案（対話）／推奨を報告に記録（非対話） |
| 生成ファイル | 提案時点ではコード変更を確定しない（または最小範囲のみ）。フェーズ成果物は生成しない |
| 終了状態 | 成功（切替提案）／ユーザ判断待ち |

## 分岐の根拠

このケースが分岐するトリガーは 変更見込み = 4 ファイル以上（言語スキル単独の想定規模を超過）である。
共通化・横断適用のように影響がフェーズ統括を要する規模へ拡大した場合、単独実行モードで押し切らず `orchestrator-coding` へエスカレーションする。
