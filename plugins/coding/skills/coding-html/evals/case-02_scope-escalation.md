# Case 02: スコープ拡大による orchestrator-coding 切替提案

## 入力

| 項目 | 値 |
|-----|---|
| 起動フレーズ | 「この一覧ページに問い合わせフォームを追加して」 |
| 引数 | なし |
| フラグ | なし |
| 既存状態 | 静的 HTML サイト（`.editorconfig` あり）。問い合わせは入力 → 確認 → 完了の 3 ページ構成が慣習で、各ページが共通のヘッダ / フッタ断片を複製している |

## 期待動作

### 手順 1〜2: 規約解決・FW 確認
- case-01 と同様に独自規約（`.editorconfig` / `.htmlvalidate.json` 等）を走査し、不足はデファクトで補完する
- 対象が素の `.html` のため FW 固有構文は非該当

### 手順 3: 実装（着手時にスコープ拡大を検知）
- 問い合わせフォームの追加は入力ページ（`contact.html`）に加え、確認ページ（`contact-confirm.html`）・完了ページ（`contact-complete.html`）と、共通ヘッダのナビゲーションリンクの修正を要するため、変更見込みが 4 ファイル以上に膨らむと判明する

### 手順 5: 報告（切替提案）
- 実行フロー手順 5 の分岐に従い、`orchestrator-coding` への切替を提案する
- 現状の分析結果（適用規約サマリ・影響を受けるページ一覧・共通断片が複製されているリスク）を引き継ぎ情報として提示する
- ユーザの判断を待ち、単独での大規模変更は進めない

## 期待出力

| 項目 | 期待値 |
|-----|-------|
| 標準出力 | `orchestrator-coding` への切替提案 + 引き継ぎ情報（規約サマリ・影響ページ一覧・リスク） |
| コード変更 | 未確定（切替提案時点では大規模変更に着手しない） |
| 終了状態 | 切替提案（ユーザ判断待ち） |

## 分岐の根拠

このケースが分岐するトリガーは 変更見込みが 4 ファイル以上 である。
SKILL.md 実行フロー手順 5 の「変更見込みが 4 ファイル以上に膨らむ場合は `orchestrator-coding` への切替を提案する」に該当する。
言語スキル単独では複数ページ・共通断片に跨る影響管理・フェーズ統括を担わないため、オーケストレーターへ引き継ぐ。
