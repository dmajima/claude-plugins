# Case 11: バックアップ取得失敗時の中止

## 入力

| 項目 | 値 |
|-----|---|
| 起動フレーズ | "Claude の設定を Git から同期して" |
| 引数 | `--repo https://github.com/myaccount/claude-settings --yes` |
| フラグ | `--yes`（バックアップは既定で実施） |
| 既存状態 | バックアップ取得先（`~/.claude/.local/plugins/maintenance/backup/`）が読み取り専用、または容量不足 |

## 期待動作

### Phase 1〜4: 通常通り（設定解決〜差分検出）

### Phase 5: バックアップディレクトリ作成試行
- `New-Item -ItemType Directory` がエラーで失敗
- catch 節でエラーをユーザに通知

### Phase 6: 中止処理
- 同期適用には進まない（**fail-closed 設計**）
- `sync-config.json` も更新しない
- exit 1 で終了

## 期待出力

| 項目 | 期待値 |
|-----|-------|
| 生成ファイル | なし（バックアップ未取得） |
| 同期適用 | なし |
| 標準出力（要約） | 「バックアップ取得失敗: {エラー詳細}」「同期処理は中止されました」 |
| 終了状態 | 失敗（exit 1） |

## 分岐の根拠

このケースが分岐するトリガーは バックアップディレクトリ作成 or コピー操作の例外発生 である。バックアップが取得できない場合、ロールバック手段がないため fail-closed で中止する。

## 安全装置の意義

- 同期は不可逆な操作。バックアップなしでの実行はリスクが高い
- `--yes` 指定でもバックアップは省略不可（前提条件）
- バックアップ失敗を検知した時点で **同期処理を行わない** ことで、後戻り可能性を担保

## ユーザのリカバリ手順

1. エラーメッセージから失敗原因を特定（権限・容量等）
2. 原因解消後、同じコマンドで再実行
3. それでも失敗する場合は `--no-backup` を **明示的に** 指定（強い警告ログとともに同期実行）
