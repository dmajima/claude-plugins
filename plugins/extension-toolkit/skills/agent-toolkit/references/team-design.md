# エージェントチーム設計ルール

エージェントチーム編成における設計原則と検証ルール。`~/.claude/rules/claude/agent-teams.md` を補完する。

## 1. チームサイズの基準

| 用途 | 推奨サイズ | 最低 |
|-----|----------|-----|
| レビュー系 | 4 名 | 3 名 |
| 設計合議系 | 4 名 | 3 名 |
| 事業判断系 | 5 名 | 4 名 |
| 単純な調査・並列作業 | チームではなくサブエージェント並列 | - |

## 2. 必要観点の網羅

レビュー系チームでは、対象に応じた観点を **網羅** する必要がある。代表的な観点と担当エージェント:

### 2.1 コードレビュー

| 観点 | 担当エージェント |
|-----|----------------|
| 実装品質・正確性 | `implementation-engineer` |
| テスト・品質保証 | `test-engineer` |
| セキュリティ | `security-engineer` |
| アーキテクチャ | `architect` |

### 2.2 セキュリティレビュー

| 観点 | 担当エージェント |
|-----|----------------|
| 脅威モデリング | `security-engineer`（リード） |
| 実装上の対策 | `implementation-engineer` |
| 法的リスク | `legal-advisor` |
| インフラ層防御 | `infrastructure-engineer` |

### 2.3 設計レビュー

| 観点 | 担当エージェント |
|-----|----------------|
| アーキテクチャ判断 | `architect`（リード） |
| 実装実現性 | `implementation-engineer` |
| セキュリティ | `security-engineer` |
| プロジェクト整合 | `project-leader` |

### 2.4 機能仕様レビュー

| 観点 | 担当エージェント |
|-----|----------------|
| プロダクト価値 | `product-manager`（リード） |
| ユーザビリティ | `ux-designer` |
| 技術実現性 | `implementation-engineer` |
| テスト可能性 | `test-engineer` |

### 2.5 事業判断レビュー

| 観点 | 担当エージェント |
|-----|----------------|
| 経営戦略 | `executive`（リード） |
| プロダクト | `product-manager` |
| 営業・市場 | `sales-member` |
| 事業者要件 | `business-owner` |
| プロジェクト | `project-leader` |

## 3. 重複チェック

新規チーム作成時に既存チームとの重複を確認:

| 確認内容 | 動作 |
|---------|------|
| 同名チームが既存 | 統合 or 別名提案 |
| 構成メンバーが既存チームとほぼ同じ | 既存チームの利用を提案 |
| 観点が既存チームと重複 | 観点を分離 or 既存チーム拡張を提案 |

## 4. 専門性の相補性検証

メンバー間の専門性が重複していないか確認する:

| 検証 | 例 |
|-----|---|
| 同一領域 2 名以上 | NG（例: `implementation-engineer` × 2） |
| 重複領域あり | 役割を細分化（例: フロントエンド実装 + バックエンド実装） |
| 観点に欠けあり | メンバー追加 |

## 5. 議論ラウンドの設計

| ラウンド | 動作 |
|---------|------|
| Round 1 | リードが論点提示、各メンバーが初回評価 |
| Round 2 | メンバー間で反論・補強 |
| Round 3 | 合意形成 or トレードオフ明確化 |
| Round 4-5（必要時） | 追加調整 |

最低 3 ラウンド、上限 5 ラウンド。合意に至らない場合はトレードオフをユーザに提示。

## 6. リードエージェントの選定基準

| 用途 | 推奨リード |
|-----|----------|
| コードレビュー | `architect` または `implementation-engineer` |
| セキュリティ | `security-engineer` |
| 設計判断 | `architect` |
| 機能仕様 | `product-manager` |
| 事業判断 | `executive` |

リードはチーム全体の議論を整理し、合意形成を担う。

## 7. デファクトスタンダードの取り込み

各エージェントが参照すべき外部知識を明記する。例:

| エージェント | 参照標準 |
|------------|---------|
| `security-engineer` | OWASP Top 10 / CWE / STRIDE |
| `ux-designer` | WCAG 2.1 / Nielsen's Heuristics |
| `infrastructure-engineer` | Well-Architected Framework / SRE Book |
| `architect` | C4 Model / DDD / SOLID |
| `legal-advisor` | SPDX / GPL/MIT/Apache 互換性 |

## 8. チーム定義ファイルの配置

| 配置先 | パス |
|-------|-----|
| グローバル | `~/.claude/teams/{team-name}.md` |
| プラグイン内 | `plugins/{plugin}/teams/{team-name}.md`（任意） |

## 9. チーム検証チェックリスト

- [ ] チームサイズが 3〜5 名
- [ ] リードエージェント指定済
- [ ] メンバーの専門性が相補的（重複なし）
- [ ] 必要観点を網羅（盲点なし）
- [ ] 議論ラウンド数 3 以上
- [ ] 各メンバーのエージェント定義が存在
- [ ] スポーンプロンプトに目的・背景・期待成果物が含まれる

## 10. 禁止事項

- 同一領域のメンバーを 2 名以上含める（特殊事情がある場合のみ例外）
- 議論ラウンド数を 3 未満に設定
- リード未指定で複数メンバーが並列に意見出し（合意形成不能）
- 観点に欠けがある状態でリリース
