# レビューフレッシュ実行原則（SSOT）

`extension-toolkit` プラグイン内のすべてのレビュー処理（`extension-review` のチーム起動 / フォールバック並列起動 / 第三者レビュー全般）に適用される原則（ADR-021 準拠）。

このルールは **プラグイン内ルール** として配布される。利用者環境に依存しないため、誰がインストールしても同じレビュー品質を保証する。

---

## 1. 原則

### 1.1 フレッシュ起動の必須化

- レビュータスクは **新規 Agent インスタンス** で起動する
- 修正・実装と **同一インスタンス** がレビューを行ってはならない
- メインコンテキスト内で「自分が書いたコードを自分でレビュー」する形は禁止する
- 過去のレビュー結果（前回 APPROVE 等）を踏襲することなく、毎回ゼロベースで評価する

### 1.2 必要情報の適切な引き継ぎ

フレッシュ起動とは「白紙で投げる」ことではない。
レビューが成立するために必要な情報は **スポーンプロンプトで明示的に引き継ぐ**。

---

## 2. 必須引き継ぎ事項

レビュー起動時のスポーンプロンプトには、以下を **必ず含める**。

| 項目 | 内容 |
|-----|------|
| (a) レビュー目的 | 何のためのレビューか（公開前審査 / 設計判断 / セキュリティ確認 等） |
| (b) 担当役割 | どの観点を担当するか（実装品質 / アーキテクチャ / セキュリティ 等） |
| (c) ユーザー指摘・要件 | 直近のユーザーからの明示要求・制約 |
| (d) 対象ファイル / 範囲 | 評価対象のファイルパス・コミット範囲・スコープ境界 |
| (e) レビュー観点 | 具体的に確認すべきチェック項目 |
| (f) 出力フォーマット | 重大度（Critical / High / Medium / Low）、報告構造 |

---

## 3. 引き継いではならない事項

以下の情報は **意図的に伝えない**。先入観の温存・確証バイアスを招くため。

| 項目 | 理由 |
|-----|------|
| (i) 修正実装者の主観・自己評価 | 「これで OK」という判断は確証バイアスの温床 |
| (ii) 過去レビューの結論 | 「前回 APPROVE だった」が今回も妥当とは限らない |
| (iii) 「修正済み」「対応完了」等のメタ評価 | 評価結果を先に提示すると追認バイアスが働く |
| (iv) 修正コミットメッセージ本文 | コミットメッセージは修正者の主観を含む。**要約のみ**（変更カテゴリ・対象範囲）は可 |
| (v) 「軽微」「重要でない」等の重大度予断 | 重大度判定はレビュアーが行うべき判断 |
| (vi) 「合格にしてほしい」等の期待 | 評価の中立性を阻害 |

---

## 4. 適用範囲

### 4.1 適用される場面

- スキル・プラグインの **公開前レビュー**
- **設計判断** に対する第三者評価
- **セキュリティ審議**
- **品質ゲート判定**
- **要件適合性レビュー**
- 多角レビュー（複数専門家による評価）の各メンバー
- `extension-review` の全チーム起動 / フォールバック並列起動

### 4.2 適用外（自己検証）

以下は対象外。自身の生成物の自己点検は通常通り実施する:

- 各スキルの「実行フロー」最終ステップでの自己検証チェックリスト（[`completion-checklist.md`](completion-checklist.md)）
- 機械的なフォーマット確認（JSON valid / 行数等）
- 実装エージェントが自身の出力を確認する内部処理

---

## 5. 同一セッション・同一コンテキストの禁止

### 5.1 禁止パターン

- メインコンテキストで実装した直後に、メインコンテキストでレビュー結論を出す
- 「私が書いたこのコードは XX という観点で問題ないと判断します」と自己宣言する
- 修正セッション内で過去の修正結果を「OK」「対応済み」と評価して終わらせる

### 5.2 推奨パターン

- 修正完了後、`Agent` ツールで新規インスタンスを起動して評価依頼する
- スポーンプロンプトに上記「必須引き継ぎ事項」を明記し、「不要事項」は省く
- 複数観点の場合は **1 メッセージで複数 Agent を並列起動** し、独立した評価を並行で得る
- 結果統合時にメイン Claude が矛盾・優先度を整理する

---

## 6. 実装ガイドライン

### 6.1 スポーンプロンプトの最小骨格

```text
あなたは {役割} として、以下の対象を独立に評価してください。

【レビュー目的】
{何のための評価か}

【担当役割と観点】
{担当観点と具体的なチェック項目}

【ユーザー指摘・要件】
{直近のユーザー要求・制約}

【対象】
{ファイルパス・コミット範囲・スコープ境界}

【出力フォーマット】
Critical / High / Medium / Low の優先度別に、ファイルパス + 行番号 + 具体的な問題と修正案を提示してください。
問題なければ「APPROVE」を明記してください。

注意: 過去の議論・修正履歴・他レビュアーの結論は与えていません。これらに依らず、対象を白紙で評価してください。
```

### 6.2 並列レビューでの活用

```text
# 1 メッセージ内で複数 Agent を並列起動（フレッシュ × 独立観点）
Agent({ subagent_type: "architect", prompt: "（観点別の引き継ぎ）" })          # 並列
Agent({ subagent_type: "implementation-engineer", prompt: "..." })           # 並列
Agent({ subagent_type: "security-engineer", prompt: "..." })                 # 並列
```

各メンバーは独立フレッシュインスタンスで評価。
メイン Claude は結果統合のみ行う（評価そのものはレビュアーに委ねる）。

---

## 7. 反復実行（指摘ゼロまで）

第三者レビューで指摘が出た場合:

1. メイン Claude が指摘を統合・優先度付け
2. 修正実装（事項単位コミット推奨、バージョン更新付き）
3. **再度フレッシュなインスタンスで再レビュー**（前回の修正内容を肯定する偏りを防ぐ）
4. 指摘ゼロになるまで反復

過去の修正履歴は再レビューに引き継がない。毎回ゼロベース評価とする。

---

## 8. 品質保証への寄与

このルールは以下の品質問題を防ぐ:

| 防止する問題 | メカニズム |
|------------|----------|
| 確証バイアス | 修正者と評価者の分離 |
| 慣性的合格 | 過去結果を引き継がない |
| 仕様書の曖昧性温存 | フレッシュ視点で読み手にとっての分かりにくさを発見 |
| 重大度判定の偏り | 重大度予断を伝えない |
| 同質化（Echo Chamber） | 並列フレッシュ起動で多様性を確保 |

---

## 9. なぜプラグイン内ルールなのか（グローバル化しない理由）

| 観点 | プラグイン内ルール | グローバルルール |
|-----|----------------|--------------|
| 動作の一貫性 | **すべての利用者で同じ動作** | 利用者ごとに動作差異が発生しうる |
| 配布性 | プラグインインストールで自動的に伝搬 | 別途ルールファイルの配布が必要 |
| 環境非依存性 | 利用者環境に依存しない | `~/.claude/rules/` の整備状態に依存 |
| プラグインの自己完結性 | 独立して動作可能 | 環境セットアップが前提 |

このプラグインで提供するレビュー品質は、利用者がインストールするだけで保証されるべき。
そのため、レビュー設計に関わる本質的なルールはプラグイン内 SSOT に置く。
