# 作業完了前チェックリスト（SSOT）

各スキル・コマンドが **作業完了報告の前に必ず実施** する自己検証ルール。要件適合性 + ルール順守 + 結果不足の有無を 3 軸で確認する。

## 1. 適用範囲

`extension-toolkit` プラグイン配下の **全スキル・全コマンド** に適用。チェックリストを実施せずに作業完了報告してはならない。

## 2. 3 軸の自己検証

### 2.1 ルール順守チェック

各スキル・コマンドが従うべきルール（SSOT）に対し、生成物・変更が違反していないか確認する。

| 軸 | 確認内容 | 参照 |
|---|---------|------|
| 命名・配置規約 | ファイル名・ディレクトリ構造・frontmatter | [`conventions-naming.md`](../policies/conventions-naming.md) |
| AI 誤認回避 | 必須セクション・断定表現・条件表 | [`ai-readability.md`](../policies/ai-readability.md) |
| description 設計 | フレーズ網羅・Use when・SKIP when | [`description-guide.md`](../guides/description-guide.md) |
| ポータブルパス | ローカル絶対パス禁止・`${CLAUDE_*}` 利用 | [`path-portability.md`](../policies/path-portability.md) |
| evals 設計 | 動作分岐ありなら必須・各ケースのフォーマット | [`eval-guide.md`](../guides/eval-guide.md) |
| 検証ルール | 種別別の検証項目 | [`validation-rules.md`](validation-rules.md) |
| バージョン更新 | **必須**: 1 コミット 1 バージョン更新（マーケットプレイス自動更新検知のため）。スキル側で `plugin.json` の編集が発生した場合は必ず `version` を桁付きで更新する | [`versioning.md`](../policies/versioning.md) |
| マーケットプレイス README 同期 | `marketplace.json` を編集した場合は **必ず同一コミット** でマーケットプレイス README を同期する（ADR-019 準拠） | [`readme-policy.md`](../policies/readme-policy.md) 節 11.1 |
| ライセンス整備（プラグイン生成・改修・公開時） | プラグイン直下に `LICENSE`（MIT 標準文 + Copyright 行が埋まっている）+ `plugin.json.license == "MIT"` + README に「ライセンス」セクションが揃っているか（ADR-029 / `mit-license-toolkit` で管理）| [`license-policy.md`](../policies/license-policy.md) |
| レビューフレッシュ起動 | 第三者レビューは **新規 Agent インスタンス** で起動し、修正実装と同一コンテキストで評価しない（ADR-021 準拠）。必須引き継ぎ事項を明記し、引き継ぎ禁止事項（過去レビュー結論等）は伝えない | [`review-freshness.md`](review-freshness.md) |
| 利用者環境非依存性 | グローバルルール / グローバルエージェント / 外部ツール前提などの依存箇所を棚卸しし、明示・同梱・フォールバックのいずれかで対処（ADR-022 準拠） | [`self-containment.md`](../policies/self-containment.md) |
| ユーザ対話 | 選択は AskUserQuestion 優先 | [`user-interaction.md`](../guides/user-interaction.md) |
| 状態ファイル形式 | 構造化データは JSON/YAML | [`state-files.md`](../policies/state-files.md) |
| README 規約 | 人間向け明記・導入手順優先 | [`readme-policy.md`](../policies/readme-policy.md) |
| エージェント活用 | Explore 等の既存機能利用 | [`agent-utilization.md`](../guides/agent-utilization.md) |
| エンコーディング | 元ファイルの文字コード・改行コード保持。グローバルルール参照は ADR-022 例外（OS/Claude Code 共通ルール）として許容、不在時は UTF-8 / 元の改行コードを既定維持 | `~/.claude/rules/common/file-encoding.md`（任意参照） |
| **Python 子プロセス起動のハング対策**（Python スクリプトを呼ぶ場合 **MANDATORY**）| Python スクリプト（特に `python-pptx` を使うもの）を呼ぶ場合、`Start-Process -NoNewWindow` / `&` + redirect での直起動は禁止。**`Start-Job` 経由ラッパースクリプト**を経由する。`procedures.md` の起動例にラッパー経由が記載されているか確認 | `~/.claude/rules/tools/python-subprocess-hang-windows.md` / [`powershell-pitfalls.md`](../guides/powershell-pitfalls.md) 節 7.3 |

### 2.2 要件適合性チェック

ユーザが当初要求した内容と、生成物・変更が一致するか確認する。

| 確認項目 | 実施方法 |
|---------|---------|
| 要件のすべての項目をカバーしたか | 要件を箇条書きで再列挙し、対応する生成物・変更箇所を対応付ける |
| 要件にない不要な変更を加えていないか | 変更ファイル一覧を要件と突き合わせる |
| 要件の解釈に疑義はないか | 曖昧な箇所をユーザに確認したかチェック |

### 2.3 結果完全性チェック

生成物・変更が論理的に完結しているか確認する。

| 確認項目 | 実施方法 |
|---------|---------|
| 参照リンクが切れていない | 内部リンクを辿って到達可能か確認 |
| 分割ファイルに相互参照があるか | ファイルを分割した場合、元ファイル・新ファイル双方に相互参照リンクが入っているか確認 |
| references ファイルが 300 行以下か | 300 行超のファイルは分割必須（[`conventions-general.md`](../policies/conventions-general.md) 節 8） |
| プレースホルダ（`{...}`）が残存していない | Grep で確認 |
| 関連ファイルの整合（README + SKILL.md + evals） | 提供機能と実装の一致確認 |
| 必須ファイルが揃っている | [`validation-rules.md`](validation-rules.md) の種別別必須項目 |

### 2.4 動作デモ + ユーザ承認（MANDATORY）

静的解析・自己検証では実行時バグを検出できないことが 2026-05-18 のセッションで確認された
（`sync-settings/sync.sh` の `TrimStart` char 変換 Critical バグが、静的レビュー 6 サイクル後の
デモ実行で初めて発見された）。実装バグ流出を防ぐため、**作業完了報告の前** に
ユーザ向け動作デモを実施し、承認を取得することを必須化する（ADR-032 準拠）。

#### 2.4.1 デモ実施対象

| 対象 | 必須/任意 |
|------|----------|
| 新規スキル / 改修スキル | **必須** |
| 新規プラグイン / 既存プラグイン構成変更 | **必須** |
| 新規コマンド / 改修コマンド | **必須** |
| エージェント / チーム新規作成 | 必須（チームの実起動 1 回以上）|
| フック設定（hooks.json）の追加 | **必須**（実発火の確認）|
| README のみ / 軽微なドキュメント変更 | 任意 |
| ADR 追加のみ | 任意 |

#### 2.4.2 デモシナリオの最低要件

| 項目 | 内容 |
|------|------|
| (a) 代表的な正常系 | dry-run モードがあれば dry-run で 1 回、なければ最も典型的なフロー |
| (b) 主要分岐の動作確認 | 動作分岐ありなら最低 1 分岐は実行（理想はすべて） |
| (c) AskUserQuestion 実発火 | 対話 UI を含むなら **実際に AskUserQuestion を発火** し、選択フローを通す |
| (d) エラーパス 1 件 | バリデーション失敗・不正引数等のエラーパスを 1 件確認 |
| (e) ファイル副作用の事前提示 | 実適用前に「これから何が起きるか」をユーザに提示 |

#### 2.4.3 承認取得の手順

1. デモ実施結果（標準出力・生成ファイル・実行コマンド）をユーザに提示
2. `AskUserQuestion` で承認確認:
   - 「承認・完了報告へ進む」
   - 「追加デモ・別シナリオを実施」
   - 「不具合あり・修正へ戻る」
3. 承認後にのみ「引き渡し」セクションへ進む
4. `progress.md` にデモ実施記録（実行コマンド・結果・承認結果）を残す

#### 2.4.4 デモ実施の免責ケース

| 免責 | 条件 |
|------|------|
| README / コメントのみの変更 | コード実行を伴わない |
| ADR / SSOT ドキュメントのみの変更 | コード実行を伴わない |
| 緊急セキュリティ修正 | デモ後実施の事後検証で許容（事前承認不要、事後通知必須）|
| 利用者の明示的なスキップ指示 | 「デモ省略でよい」と明示された場合のみ |

#### 2.4.5 デモシナリオは `evals/demo.sh` 等で再現可能化する

スキル毎に `evals/demo.sh`（または同等の再現スクリプト）を用意し、
セッションを跨いで同じデモを再現できるようにする（[`B-3` テンプレート化と整合]）。

## 3. 実施タイミング

| タイミング | 動作 |
|----------|------|
| 各スキルの「実行フロー」最終ステップ「検証」 | 本ファイルのチェックリストを参照して自己検証 |
| 「引き渡し」前（**MANDATORY**） | 節 2.4 のデモ実施 + AskUserQuestion での承認取得 |
| 検証不合格 | 修正、再検証 |
| 修正不可な不適合 | ユーザに不適合内容を提示、合意の上で進行または中止 |

## 4. 記録形式

各スキルの「検証」ステップで以下を確認・記録する:

```markdown
## 作業完了前チェック結果

### ルール順守
- [x] 命名・配置規約: OK
- [x] AI 誤認回避: OK
- [ ] description 設計: 1 件不適合（{詳細}）→ 修正済
- [x] パスポータビリティ: OK
- [x] evals 設計: OK（または該当なし）
- ...

### 要件適合性
- 要件 1: {要件内容} → 対応: {対応ファイル/箇所}
- 要件 2: {要件内容} → 対応: {対応ファイル/箇所}
- ...
- 不要変更: なし（または記載）

### 結果完全性
- [x] 参照リンク全て解決
- [x] プレースホルダ残存なし
- [x] 関連ファイル整合
- [x] 必須ファイル揃い
```

ユーザへの引き渡し報告にこの結果サマリを **必ず含める** か、ない場合は理由を明示する。

## 5. 不適合時の対応フロー

| 重大度 | 対応 |
|-------|------|
| Critical（規約違反・要件未達） | 必ず修正してから報告 |
| High（推奨違反・部分要件未達） | 修正を試みる。修正困難ならユーザに提示し合意 |
| Medium / Low | 報告に含めて記録、ユーザの判断に委ねる |

## 6. チェック自動化

可能な限り機械的にチェックする:

| 項目 | 自動化方法 |
|-----|----------|
| 行数制約 | `wc -l` |
| パスポータビリティ | Grep（NG パターン） |
| プレースホルダ残存 | Grep（`{...}`） |
| JSON valid | JSON パース |
| frontmatter valid | YAML パース |

詳細は [`../skills/extension-reviewer/references/automated-checks.md`](../skills/extension-reviewer/references/automated-checks.md) を参照。

## 7. 禁止事項

- チェックリスト未実施で作業完了報告すること
- 不適合を認識しながら **ユーザに通知せず** 報告すること
- 機械的にチェック可能な項目を省略すること
- 要件適合性の確認を省略すること
- **節 2.4 の動作デモを実施せず引き渡しに進むこと**（ADR-032・免責ケースを除く）
- デモを「実行コマンドの提示」のみで済ませて **実行・実発火を伴わない** こと
- 承認取得を AskUserQuestion ではなくテキスト確認で済ませること（重要操作のため）
