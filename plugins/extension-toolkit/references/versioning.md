# バージョン管理ルール（SSOT）

プラグインの `plugin.json` の `version` フィールドを更新する際のルール。SemVer (`x.y.z`) ベース。

## 1. バージョン番号の構造

```
x.y.z
│ │ └─ パッチ番号（軽微な修正）
│ └─── マイナー番号（機能改善）
└───── メジャー番号（機能追加）
```

## 2. 更新基準

| 種別 | 更新箇所 | 例 |
|-----|---------|---|
| **機能追加** | x（メジャー） | 新スキル追加、新コマンド追加、API 互換性変更、既存機能の根本的な刷新 |
| **機能改善** | y（マイナー） | 既存スキルの拡張、新ルール追加、生成物の構造変更（後方互換あり）、新エージェント追加 |
| **軽微な修正** | z（パッチ） | バグ修正、タイポ修正、ドキュメント更新、内部実装の最適化 |

## 3. 桁繰り上がりルール

| 更新 | 動作 |
|-----|------|
| メジャー（x）更新 | y, z を `0` にリセット（例: `1.2.3` → `2.0.0`） |
| マイナー（y）更新 | z を `0` にリセット（例: `1.2.3` → `1.3.0`） |
| パッチ（z）更新 | y, x は変更しない（例: `1.2.3` → `1.2.4`） |

## 4. 初期バージョン

| 状態 | バージョン |
|-----|----------|
| 開発中・未公開 | `0.1.0` 〜 `0.x.y` |
| 初回公開（プロダクションレディ） | `1.0.0` |

`0.x.y` の段階では破壊的変更を許容するため、メジャー更新規則は緩和される（マイナー番号で破壊的変更を表現してもよい）。

### 4.1 SemVer 標準との差分注記

本ルールにおける「メジャー更新の判定基準」は **新スキル/コマンド/根本機能の追加** を含むが、SemVer 公式仕様は **後方非互換変更のみ** をメジャーとする（[https://semver.org/](https://semver.org/)）。本プラグインでは利用者の認知（プラグインの「機能セット」が変わったかどうか）を優先しており、機能追加もメジャー扱いする運用を選択している。

`1.0.0` 以降にこの解釈を継続するか、SemVer 標準（破壊的変更のみメジャー）に切り替えるかは、`1.0.0` 移行時に再判断する。判断結果は本ファイルの本節に追記する。

## 5. 判定フロー

```
変更内容の確認
  ├─ 新スキル / 新コマンド / 既存機能の刷新を含む？
  │   └─ Yes → メジャー（x）更新
  │
  ├─ 既存スキルの新機能 / 新ルール / 後方互換ある拡張？
  │   └─ Yes → マイナー（y）更新
  │
  └─ バグ修正 / タイポ / ドキュメント更新のみ？
      └─ Yes → パッチ（z）更新
```

複数の種別が混在する場合は **最も大きな更新** を採用する（例: 機能追加 + バグ修正 → メジャー更新）。

## 6. 更新タイミング（**1 コミット 1 バージョン更新必須**）

| タイミング | 担当 |
|----------|------|
| **すべてのコミット**（プラグイン内ファイル変更を含むもの） | `plugin.json` の `version` を **必ず更新** する |
| 例外なし | バグ修正・タイポ修正でも最低 patch 更新（z 部 +1） |

### なぜ 1 コミット 1 バージョン更新が必須か

| 理由 | 内容 |
|-----|------|
| マーケットプレイス自動更新の検知 | 利用者環境の `/plugin update` はバージョン番号差分で更新を判定する。バージョンが据え置きだと更新が自動取得されない |
| 利用者の参照バージョン特定 | バグ報告時に「どの version で発生したか」を `plugin.json` の version 値で同定可能 |
| 依存解決の正確性 | 他プラグインから `version` 範囲指定（`^1.2.0` 等）された場合に正しい版を解決できる |

### コミット種別ごとの推奨更新

| コミット内容 | バージョン更新 |
|------------|------------|
| 機能追加（新スキル / 新コマンド / 新 SSOT） | メジャー（x）+1 |
| 機能改善（既存スキル拡張・新ルール・後方互換ある変更） | マイナー（y）+1 |
| バグ修正・タイポ修正・ドキュメント整理・リファクタ | パッチ（z）+1 |
| 1 コミットで複数種別が混在 | 最も大きな更新を採用 |

## 7. 更新箇所

| ファイル | フィールド |
|---------|----------|
| `plugins/{plugin}/.claude-plugin/plugin.json` | `"version"` |

`marketplace.json` には version を書かない（重複管理を避けるため、`plugin.json` で一元管理する）。

## 8. ユーザへの確認

バージョン更新時は **AskUserQuestion でユーザに確認** する（[`user-interaction.md`](user-interaction.md) 参照）:

```
今回の変更内容:
- 新スキル `xxx-toolkit` を追加
- 既存スキル `yyy-toolkit` にルーティング追加
- バグ修正 2 件

提案バージョン: 1.2.0 -> 2.0.0（メジャー更新、新スキル追加のため）

このバージョン更新で進めますか？
- 1. 提案どおり 2.0.0
- 2. マイナー更新 1.3.0 にする
- 3. 別のバージョンを指定
- 4. 更新しない
```

## 9. 変更履歴は CHANGELOG ではなく Git で管理

| 管理方法 | 配置 |
|---------|------|
| 変更履歴 | Git コミット履歴 |
| バージョンタグ | `git tag v{x.y.z}`（任意、リリース時のみ） |

`CHANGELOG.md` をプラグイン内に持たない。Git コミット履歴で代替する。理由:

- 二重管理の手間を排除（[`readme-policy.md`](readme-policy.md) で README に過去履歴を書かない原則と整合）
- 真正な履歴は Git にあり、別ファイルは陳腐化しやすい

## 10. 検証

バージョン更新後、以下を確認:

- [ ] `plugin.json` の version が新バージョンになっている
- [ ] バージョン形式が `x.y.z`（数字 + `.`）
- [ ] 桁繰り上がりルール（マイナー→パッチ 0 リセット等）に従っている
- [ ] `marketplace.json` に version が記載されていない（記載されていたら削除）
- [ ] **コミット前に必ず `plugin.json` の version を更新**（1 コミット 1 バージョン更新原則）

## 11. コミット前自己検証フック（推奨）

`plugin.json` のバージョン更新漏れを防ぐため、`pre-commit` フックや CI で以下のチェックを実装することを推奨する:

```bash
# プラグイン内ファイルが変更されているのに plugin.json の version が変わっていない場合は拒否
if git diff --cached --name-only | grep -q "^plugins/extension-toolkit/" && \
   ! git diff --cached plugins/extension-toolkit/.claude-plugin/plugin.json | grep -q '"version"'; then
  echo "Error: plugin.json version must be updated for every commit." >&2
  exit 1
fi
```
