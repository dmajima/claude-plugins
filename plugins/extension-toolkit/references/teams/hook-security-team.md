# Agent Team: hook-security-team

フック設定のセキュリティ・運用観点を多角的にレビューするチーム。フック専用。

## チーム情報

| 項目 | 内容 |
|------|------|
| 目的 | Claude Code フック設定（hooks.json または settings.json の hooks）が安全に運用できるかを評価する |
| リード | `security-engineer`（グローバル） |
| メンバー（リード以外） | `implementation-engineer`（グローバル） / `infrastructure-engineer`（グローバル） |
| 人数 | 3 名（リード含む） |
| 議論ラウンド | 最低 3、上限 5 |

## 起動条件

- 新規フック設定の作成完了後
- フックが含まれるプラグインの公開前
- セキュリティ懸念が高いフックの改修後

## メンバー構成と専門性

| ID | 配布元 | 役割 | 専門性 | 主な評価軸 |
|----|--------|------|-------|----------|
| `security-engineer` | グローバル | リード | 脅威モデリング / 攻撃面 | command の安全性（コマンドインジェクション・`$(...)` / `eval` の濫用検出）/ ブロック動作 / 権限濫用 |
| `implementation-engineer` | グローバル | メンバー | 実装品質 | timeout 設定 / パスポータビリティ / 終了コード / 動的データ受け渡し時のクォート |
| `infrastructure-engineer` | グローバル | メンバー | インフラ・運用 | パフォーマンス影響 / 副作用範囲 / 失敗時の影響 |

### 必須チェック観点（コマンドインジェクション）

`security-engineer` がリードとして以下を **必ず** 検査する:

- `command` フィールド内で動的データを文字列補間していないか
- `$(...)` / `` `...` ``（コマンド置換）の使用が必要最小限か
- `eval` を使っていないか
- 動的データが必要な場合は外部スクリプトに委譲し、引数として安全に受け渡されているか

詳細は [`../../skills/hook-toolkit/references/hook-events.md`](../../skills/hook-toolkit/references/hook-events.md) の「セキュリティ設計（command の安全な書き方）」を参照。

3 名はいずれもグローバル既存エージェント。プラグイン同梱エージェントは含まない（フック評価はプラグイン特有観点が少ないため）。

### グローバルエージェント不在時のフォールバック（ADR-022 準拠）

| 不在エージェント | フォールバック |
|---------------|------------|
| `security-engineer` | `general-purpose` を `security-engineer` の専門性プロンプトで起動。脅威モデリング・command 安全性レビュー観点を明示 |
| `implementation-engineer` | `general-purpose` を `implementation-engineer` のプロンプトで起動。または `plugin-structure-reviewer`（同梱）が部分的に兼任 |
| `infrastructure-engineer` | `general-purpose` を `infrastructure-engineer` のプロンプトで起動。タイムアウト・パフォーマンス・副作用観点を明示 |

利用環境に応じて、可能な限り 3 名の独立観点を維持することを優先する。3 名揃わない場合でもセキュリティ観点（リード）は必須とする。

## 調整ガイドライン

- リード `security-engineer` が脅威モデルを提示
- 攻撃シナリオの相互検証を重視（メンバーが互いの想定を反駁し盲点を洗い出す）
- 議論ラウンド最低 3、攻撃シナリオが複雑な場合は 5 まで延長
- セキュリティ指摘は **必ずユーザ確認** を求める（自動修正対象外）

## スポーンプロンプト

ADR-021（レビューフレッシュ起動原則）に従い、過去レビュー結論・修正履歴を引き継がず、必須引き継ぎ事項のみで起動する。

```text
hook-security-team チームを作成し、以下のフック設定をセキュリティ観点で多角的にレビューしてください。

メンバー構成:
- security-engineer エージェントをリードとして、脅威モデリング・対策方針の合意形成を担当
- implementation-engineer エージェントが timeout / パスポータビリティ / 終了コードの実装妥当性を評価
- infrastructure-engineer エージェントがパフォーマンス影響・副作用・失敗時の影響を評価

対象: {{hooks.json または settings.json の hooks セクション}}
背景: {{プラグイン同梱フックか settings.json への追加か / 公開予定}}

攻撃シナリオの相互検証を含む最低 3 回の議論ラウンドを経て、
脅威一覧と対策方針を優先度付きでレポートにまとめてください。
セキュリティ指摘は重大度を Critical / High / Medium / Low で明示してください。

注意: 過去の議論・修正履歴・他レビュアーの結論は与えていません。これらに依らず、対象を白紙で評価してください。
「修正済み」「対応完了」等のメタ評価を前提とせず、現時点のファイル内容のみで判断してください。
```
