# 作業完了前チェックリスト（SSOT）

各スキル・コマンドが **作業完了報告の前に必ず実施** する自己検証ルール。要件適合性 + ルール順守 + 結果不足の有無を 3 軸で確認する。

## 1. 適用範囲

`extension-toolkit` プラグイン配下の **全スキル・全コマンド** に適用。チェックリストを実施せずに作業完了報告してはならない。

## 2. 3 軸の自己検証

### 2.1 ルール順守チェック

各スキル・コマンドが従うべきルール（SSOT）に対し、生成物・変更が違反していないか確認する。

| 軸 | 確認内容 | 参照 |
|---|---------|------|
| 命名・配置規約 | ファイル名・ディレクトリ構造・frontmatter | [`conventions.md`](conventions.md) |
| AI 誤認回避 | 必須セクション・断定表現・条件表 | [`ai-readability.md`](ai-readability.md) |
| description 設計 | フレーズ網羅・Use when・SKIP when | [`description-guide.md`](description-guide.md) |
| ポータブルパス | ローカル絶対パス禁止・`${CLAUDE_*}` 利用 | [`path-portability.md`](path-portability.md) |
| evals 設計 | 動作分岐ありなら必須・各ケースのフォーマット | [`eval-guide.md`](eval-guide.md) |
| 検証ルール | 種別別の検証項目 | [`validation-rules.md`](validation-rules.md) |
| バージョン更新 | **必須**: 1 コミット 1 バージョン更新（マーケットプレイス自動更新検知のため）。スキル側で `plugin.json` の編集が発生した場合は必ず `version` を桁付きで更新する | [`versioning.md`](versioning.md) |
| マーケットプレイス README 同期 | `marketplace.json` を編集した場合は **必ず同一コミット** でマーケットプレイス README を同期する（ADR-019 準拠） | [`readme-policy.md`](readme-policy.md) 節 11.1 |
| ユーザ対話 | 選択は AskUserQuestion 優先 | [`user-interaction.md`](user-interaction.md) |
| 状態ファイル形式 | 構造化データは JSON/YAML | [`state-files.md`](state-files.md) |
| README 規約 | 人間向け明記・導入手順優先 | [`readme-policy.md`](readme-policy.md) |
| エージェント活用 | Explore 等の既存機能利用 | [`agent-utilization.md`](agent-utilization.md) |
| エンコーディング | 元ファイルの文字コード・改行コード保持 | `~/.claude/rules/common/file-encoding.md` |

### 2.2 要件適合性チェック

ユーザが当初要求した内容と、生成物・変更が一致するか確認する。

| 確認項目 | 実施方法 |
|---------|---------|
| 要件のすべての項目をカバーしたか | 要件を箇条書きで再列挙し、対応する生成物・変更箇所を対応付ける |
| 要件にない不要な変更を加えていないか | 変更ファイル一覧を要件と突き合わせる |
| 要件の解釈に疑義はないか | 曖昧な箇所をユーザに確認したかチェック |

### 2.3 結果完全性チェック

生成物・変更が論理的に完結しているか確認する。

| 確認項目 | 実施方法 |
|---------|---------|
| 参照リンクが切れていない | 内部リンクを辿って到達可能か確認 |
| プレースホルダ（`{...}`）が残存していない | Grep で確認 |
| 関連ファイルの整合（README + SKILL.md + evals） | 提供機能と実装の一致確認 |
| 必須ファイルが揃っている | [`validation-rules.md`](validation-rules.md) の種別別必須項目 |

## 3. 実施タイミング

| タイミング | 動作 |
|----------|------|
| 各スキルの「実行フロー」最終ステップ「検証」 | 本ファイルのチェックリストを参照して自己検証 |
| 「引き渡し」前 | 検証で不合格項目があれば修正、再検証 |
| 修正不可な不適合 | ユーザに不適合内容を提示、合意の上で進行または中止 |

## 4. 記録形式

各スキルの「検証」ステップで以下を確認・記録する:

```markdown
## 作業完了前チェック結果

### ルール順守
- [x] 命名・配置規約: OK
- [x] AI 誤認回避: OK
- [ ] description 設計: 1 件不適合（{詳細}）→ 修正済
- [x] パスポータビリティ: OK
- [x] evals 設計: OK（または該当なし）
- ...

### 要件適合性
- 要件 1: {要件内容} → 対応: {対応ファイル/箇所}
- 要件 2: {要件内容} → 対応: {対応ファイル/箇所}
- ...
- 不要変更: なし（または記載）

### 結果完全性
- [x] 参照リンク全て解決
- [x] プレースホルダ残存なし
- [x] 関連ファイル整合
- [x] 必須ファイル揃い
```

ユーザへの引き渡し報告にこの結果サマリを **必ず含める** か、ない場合は理由を明示する。

## 5. 不適合時の対応フロー

| 重大度 | 対応 |
|-------|------|
| Critical（規約違反・要件未達） | 必ず修正してから報告 |
| High（推奨違反・部分要件未達） | 修正を試みる。修正困難ならユーザに提示し合意 |
| Medium / Low | 報告に含めて記録、ユーザの判断に委ねる |

## 6. チェック自動化

可能な限り機械的にチェックする:

| 項目 | 自動化方法 |
|-----|----------|
| 行数制約 | `wc -l` |
| パスポータビリティ | Grep（NG パターン） |
| プレースホルダ残存 | Grep（`{...}`） |
| JSON valid | JSON パース |
| frontmatter valid | YAML パース |

詳細は [`../skills/extension-reviewer/references/automated-checks.md`](../skills/extension-reviewer/references/automated-checks.md) を参照。

## 7. 禁止事項

- チェックリスト未実施で作業完了報告すること
- 不適合を認識しながら **ユーザに通知せず** 報告すること
- 機械的にチェック可能な項目を省略すること
- 要件適合性の確認を省略すること
