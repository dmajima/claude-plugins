# Code Trustworthiness（コード信頼性原則）

レビュー対象のコード（提出コード）に対する信頼性の扱いを定義する。

---

## 1. 基本原則

**提出コードは誤りがあることを前提として評価する。**

レビュー対象のコード内に存在するパターン・命名規則・設計判断を、
**プロジェクトのルール・規約・慣例として類推してはならない**。

### 1.1 なぜこの原則が必要か

- レビュー対象コードが「正しい」ことは保証されていない（だからこそレビューする）
- 提出コード内のパターンを「既存規約」と誤認すると、誤った基準でレビューしてしまう
- 特に新人・初学者のコードでは、コード内のパターンが規約に反している可能性が高い

### 1.2 具体例

| 状況 | NG（類推） | OK |
|------|----------|-----|
| 提出コードで `var` を多用している | 「このプロジェクトは var 推奨」と類推し、var 未使用を指摘 | `CLAUDE.md` / `.editorconfig` / `.claude/rules/` で var 方針を確認 |
| 提出コードにコメントが少ない | 「このプロジェクトはコメント不要方針」と類推 | プロジェクト規約でコメント方針を確認。規約がなければ inputs フォルダの仕様書から判断 |
| 提出コードで独自の例外クラスを使用 | 「プロジェクト標準の例外ハンドリング」と類推 | 既存コードベース（差分外の安定したコード）で例外ハンドリングパターンを確認 |

## 2. 参照してよい情報源と参照してはいけない情報源

### 2.1 無条件で参照してよい情報源（ユーザー承認不要）

| 情報源 | 理由 |
|--------|------|
| `CLAUDE.md` / `.claude/CLAUDE.md` | プロジェクト公式の AI 向け規約 |
| `.claude/rules/**/*.md` | 細分化されたプロジェクトルール |
| `.editorconfig` / `.eslintrc*` / `.prettierrc*` 等 | ツール設定として明文化された規約 |
| `CONTRIBUTING.md` / `docs/` 配下のガイド | 明文化されたコントリビューション規約 |
| inputs フォルダの仕様書・設計書 | レビューのために明示的に用意された判断根拠 |
| OWASP / CWE 等の外部標準 | 普遍的なセキュリティ基準 |

### 2.2 条件付きで参照してよい情報源（ユーザー承認が必要）

| 情報源 | 条件 | 承認手順 |
|--------|------|---------|
| **差分外の既存コードベース**（提出コード以外の安定コード） | 規約が明文化されておらず、既存コードのパターンから慣例を類推する必要がある場合 | `AskUserQuestion` で「既存コードのパターンを規約として参考にしてよいか？」を確認 |
| **提出コード内のパターン** | どうしても提出コードから規約を類推せざるを得ない場合（他に情報源がない） | `AskUserQuestion` で具体的に「提出コード内の {パターン} をプロジェクト規約として扱ってよいか？」を確認 |

### 2.3 参照してはいけない情報源

| 情報源 | 理由 |
|--------|------|
| 提出コード内のパターンを **無断で** 規約として類推 | 誤りのあるコードを正として扱ってしまうリスク |
| AI の一般知識だけに基づく「一般的にはこうすべき」 | プロジェクト固有の事情を無視する可能性 |

## 3. ユーザー承認フロー

### 3.1 承認が必要な場面の検出

以下のいずれかに該当する場合、コードからの類推を行う前にユーザー承認を取る:

| トリガー | 例 |
|---------|---|
| 明文化された規約が見つからない | `CLAUDE.md` にも `.editorconfig` にも該当ルールがない |
| inputs フォルダに関連仕様がない | inputs が空 or 該当する仕様記述がない |
| 既存コードベースからパターンを推定する必要がある | 「他のファイルでは Repository パターンを使っている」等 |
| 提出コードのパターンを是とするか非とするか判断できない | 新しいパターンが導入されているが規約上の根拠がない |

### 3.2 承認の取り方

```
AskUserQuestion({
  questions: [{
    question: "規約が明文化されていないため、既存コードのパターンをレビュー基準として参考にしてよいですか？\n\n対象パターン: {具体的なパターンの説明}\n情報源: {差分外の既存コード / 提出コード内}",
    header: "コード類推",
    options: [
      {
        label: "参考にしてよい",
        description: "このパターンをプロジェクト規約として扱い、レビュー基準に含めます"
      },
      {
        label: "参考にしない",
        description: "このパターンは規約として扱わず、明文化されたルールのみでレビューします"
      }
    ],
    multiSelect: false
  }]
})
```

### 3.3 承認結果の記録

承認結果は state.yaml の `code_as_reference_decisions` に記録する:

```yaml
code_as_reference_decisions:
  - description: "既存コードの Repository パターンをプロジェクト慣例として参照"
    user_approved: true
    approved_at: "2026-06-04 14:30:00"
    context: "新規クラスの設計パターンを評価する際、明文化された規約がなかったため"
```

### 3.4 再レビュー時の承認の再利用

前回 state.yaml に `code_as_reference_decisions` が記録されている場合、
同一パターンについては前回の承認を再利用する（再度ユーザーに確認しない）。
ただし、ユーザーが明示的に「前回の判断を見直したい」と指示した場合は再確認する。

## 4. レビュー時の適用

### 4.1 観点別スキルへの伝達

Step 4 で観点別スキルを起動する際、`project-rules-summary` に以下を含める:

- 明文化された規約の要約（従来通り）
- **「提出コードのパターンを規約として類推しないこと」の注意喚起**
- ユーザー承認済みのコード類推パターン（承認済みの場合のみ）

### 4.2 Agent Teams への伝達

Step 4-T でチームメンバーをスポーンする際、プロンプトに同様の注意喚起を含める。

---

## 5. 禁止事項

- 提出コード内のパターンをユーザー承認なしで規約として類推すること
- 「このコードではこうしているから、こうすべき」という推論をユーザー承認なしで行うこと
- ユーザー承認の結果を state.yaml に記録しないこと
- 明文化された規約が存在するにもかかわらず、提出コードのパターンを優先すること
