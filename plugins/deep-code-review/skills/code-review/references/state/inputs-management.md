# Inputs Management（仕様書・設計書管理）

レビュー対象ブランチに関連する仕様書・設計書・要件定義を `inputs` フォルダで管理し、
レビューの「あるべき姿」の判断根拠とする仕組みを定義する。

---

## 1. 目的

- レビュー時に「何を実現すべきか」の判断根拠を明確化
- 1ブランチ1機能の前提で、ブランチに紐づく仕様情報を蓄積
- ユーザーヒアリング結果を構造化保持し、レビュー間で一貫性を保つ
- レビュアー（AI）が仕様不明のまま「コードの書き方」だけを評価するのを防ぐ

---

## 2. ディレクトリ構造

```
.claude/.local/plugins/deep-code-review/
└── {branch_name}/                    # ブランチ名（"/" はそのままディレクトリ階層化）
    ├── inputs/                       # 仕様書・設計書フォルダ
    │   ├── spec.md                   # 機能仕様（ユーザー提供 or ヒアリング結果）
    │   ├── design.md                 # 設計書（画面遷移・API仕様・DB設計等）
    │   ├── constraints.md            # 制約事項・非機能要件
    │   ├── acceptance-criteria.md    # 受入条件
    │   └── {その他のユーザー提供資料}
    ├── {yyyyMMdd_HHmmss}/            # レビュー実施フォルダ
    │   └── state.yaml
    └── ...
```

### 注意

- inputs フォルダ内のファイル名・構成は固定ではない。上記は推奨構成例
- ユーザーが独自のファイル名で提供した資料はそのまま配置する
- サブフォルダで分類してもよい（例: `inputs/api/`, `inputs/ui/`）

---

## 3. inputs フォルダのライフサイクル

### 3.1 初回レビュー時

1. **inputs フォルダの存在確認**: `.claude/.local/plugins/deep-code-review/{branch_name}/inputs/` の有無を確認
2. **フォルダが存在しない場合**: セクション 4 の「ヒアリングフロー」を実行
3. **フォルダが存在する場合**: 中身を読み込み、レビューの判断根拠として使用

### 3.2 再レビュー時

1. inputs フォルダを必ず読み込む
2. ユーザーから仕様変更の指示があった場合は inputs を更新する
3. 前回のレビューで仕様面の指摘があった場合も inputs を更新する

### 3.3 ブランチマージ後

inputs フォルダは手動削除を原則とする。マージ後に不要になればユーザーが削除する。

---

## 4. ヒアリングフロー（inputs 未作成時）

inputs フォルダが存在せず、かつ `spec=<path>` 引数も指定されていない場合、
レビュー開始前にユーザーにヒアリングし、「あるべき姿」を定義する。

### 4.1 仕様情報の取得方法選択

inputs フォルダが未作成の場合、まず `AskUserQuestion` で仕様情報の取得方法を選択させる:

| 選択肢 | 動作 |
|--------|------|
| 外部チケットから取得 | チケットリンク（Backlog / JIRA / Azure Boards 等）を検出し、API 経由でチケット内容を取得して inputs に構造化保存 |
| 仕様書パスを指定 | ユーザーが指定したファイルを読み込み inputs に保存 |
| 口頭で説明 | セクション 4.2 のヒアリング項目で聞き取り |
| 仕様確認不要 | inputs 作成をスキップ（コード品質・規約観点のみでレビュー） |

呼び出し例（4 選択肢・単一選択）:

```
AskUserQuestion({
  questions: [{
    question: "レビューの判断根拠となる仕様情報をどのように取得しますか？",
    header: "仕様情報",
    options: [
      { label: "外部チケットから取得", description: "検出したチケットリンク（Backlog / Azure Boards / GitHub Issues）から内容を取得して仕様として保存します" },
      { label: "仕様書パスを指定", description: "ローカルの仕様書・設計書ファイルのパスを指定して読み込みます" },
      { label: "口頭で説明", description: "変更の目的・期待動作・制約を対話で聞き取り、仕様メモとして保存します" },
      { label: "仕様確認不要", description: "仕様との整合チェックを行わず、コード品質・規約観点のみでレビューします" }
    ],
    multiSelect: false
  }]
})
```

**外部チケット自動検出**: チケットリンクを以下の情報源から探索し、パターンに一致する URL を自動検出する:

| 文脈 | 探索する情報源 |
|------|--------------|
| PR レビュー（`pr-review` 経由） | PR description・PR コメント |
| ブランチ / ファイル指定レビュー（非 PR 文脈） | 対象ブランチのコミットメッセージ（`git log <base>...HEAD`）・ブランチ名に含まれるチケット ID（例: `feature/PROJ-123-add-discount`） |

| サービス | URL パターン | API 取得方法 |
|---------|------------|-------------|
| Backlog | `*.backlog.jp/view/PROJ-NNN` | Backlog REST API（`apiKey` 認証。credentials-manager で管理） |
| Azure Boards | `dev.azure.com/.../workitems/NNN` | `az boards work-item show`（認証済みの場合） |
| GitHub Issues | `github.com/.../issues/NNN` | `gh issue view`（認証済みの場合） |

検出した場合は「外部チケットから取得」を推奨選択肢として提示する。**いずれの情報源からもチケットリンク・ID を検出できなかった場合は「外部チケットから取得」を選択肢から除外**し、3 選択肢（仕様書パス指定 / 口頭で説明 / 仕様確認不要）で提示する（選択後に空振りする体験を防ぐため）。

### 4.2 ヒアリング項目（口頭説明時）

`AskUserQuestion` または自然言語で以下を確認する:

| 項目 | 質問例 | 必須/任意 |
|------|--------|----------|
| 機能概要 | 「このブランチで実装する機能の概要を教えてください」 | 必須 |
| 対象ユーザー・画面 | 「どの画面・APIが対象ですか？」 | 必須 |
| 主要な要件 | 「実現すべき主要な要件は何ですか？」 | 必須 |
| 受入条件 | 「完了とみなす条件は？（受入条件があれば）」 | 任意 |
| 制約・非機能要件 | 「パフォーマンス・セキュリティ等の制約はありますか？」 | 任意 |
| 既存仕様書の有無 | 「仕様書や設計書はありますか？パスがあれば教えてください」 | 必須 |

### 4.4 ユーザーが仕様書パスを提供した場合

指定されたパスのファイルを読み込み、inputs フォルダにコピーまたは要約を保存する。

### 4.5 ヒアリングをスキップする場合

ユーザーが明示的に「仕様確認不要」「コードだけ見て」と指示した場合は、
ヒアリングをスキップし、inputs フォルダを作成しない。
この場合、state.yaml の `inputs_used` は空リストとし、
統合サマリの集計セクションに「仕様書未参照（ユーザー指示）」と記載する。

## 5. inputs の構造化ルール

### 5.1 AI エージェントが理解できる形式

inputs フォルダ内のファイルは **AI エージェントが構造的に理解できる Markdown 形式** で記述する。

```markdown
# 機能仕様: {機能名}

## 概要
{機能の目的・背景を1-3行で}

## 対象
- 画面: {対象画面名}
- API: {対象APIエンドポイント}
- DB: {対象テーブル}

## 要件
1. {要件1: 具体的な振る舞いの記述}
2. {要件2}
3. ...

## 受入条件
- [ ] {条件1}
- [ ] {条件2}

## 制約
- {制約1: パフォーマンス・セキュリティ等}

## 備考
- {ヒアリング日時: YYYY-MM-DD}
- {情報源: ユーザーヒアリング / 既存仕様書 / PR description 等}
```

### 5.2 情報源の明記

各ファイルには情報源を必ず明記する:

| 情報源 | 記載例 |
|--------|--------|
| ユーザーヒアリング | `情報源: ユーザーヒアリング (2026-06-04)` |
| 既存仕様書から転記 | `情報源: docs/specs/order-feature.md からの転記` |
| PR description から抽出 | `情報源: PR #123 description から構造化` |
| コードコメントから推定 | `情報源: コードコメントからの推定（ユーザー未確認）` |

## 6. inputs の更新

### 6.1 仕様変更時

ユーザーから「仕様が変わった」「要件を追加する」等の指示があった場合:

1. 該当する inputs ファイルを更新する
2. 更新履歴を備考セクションに追記する
3. 次回レビューで更新後の仕様に基づいて評価する

### 6.2 レビュー中の仕様面の指摘

レビューで「仕様の不明点」「仕様の矛盾」が検出された場合:

1. ユーザーに確認する
2. 確認結果を inputs に反映する
3. 反映した旨を state.yaml の `inputs_used` に記録する

---

## 7. レビューでの inputs 活用

### 7.1 Step 2 での読み込み

Step 2（変更内容の把握＋プロジェクト規約読込）で inputs フォルダの全ファイルを読み込み、
内容を以下に反映する:

| 反映先 | 方法 |
|--------|------|
| 観点別スキルへの args | `spec_summary` キーワード引数に要約を含める |
| 統合サマリの集計セクション | 「参照仕様書」行に inputs ファイル一覧を記載 |
| state.yaml | `inputs_used` に使用したファイルを記録 |

### 7.2 仕様整合性の評価

inputs が存在する場合、`code-review-implementation` の仕様整合性チェック（SKILL.md の既存機能）と同等の確認を実施する:

- **実装漏れ**: inputs に記載があるが実装されていない機能・要件
- **仕様逸脱**: inputs と異なる挙動・命名・I/F
- **仕様矛盾**: inputs と実装の根本的な乖離

---

## 8. ユーザー個別指示の優先

inputs フォルダの内容とユーザーの個別指示が矛盾する場合は、
**ユーザーの個別指示を優先** する。

| 状況 | 対応 |
|------|------|
| inputs に「機能A は必須」と記載、ユーザーが「機能A は今回スコープ外」と指示 | ユーザー指示を優先し、機能A をスコープ外として扱う |
| inputs にない要件をユーザーが口頭で追加 | inputs を更新し、追加要件を反映する |
| inputs の記載が古く、ユーザーが最新の仕様を伝えた | inputs を更新し、最新仕様を反映する |

---

## 9. セッション作業領域 inputs/ との棲み分け

プラグインの inputs フォルダとセッション作業領域の `inputs/` は目的・ライフサイクルが異なる。

| 項目 | プラグイン inputs | セッション作業領域 inputs |
|------|-----------------|----------------------|
| パス | `.claude/.local/plugins/deep-code-review/{branch}/inputs/` | `.claude/.local/work/{session}/inputs/` |
| ライフサイクル | ブランチ単位で永続化（ブランチマージまで保持） | セッション単位（セッション終了で参照が切れる） |
| 用途 | ブランチ横断で再利用する仕様書・設計書・要件定義 | レビュータスク固有の一時資料（スクリーンショット・差分ログ等） |
| 管理主体 | deep-code-review プラグイン | セッション作業領域の一般規約 |
| 更新 | 仕様変更時にレビュー間で更新 | セッション内でのみ参照・更新 |

レビュー実行時は **プラグイン inputs を「あるべき姿」の判断根拠** として優先参照する。セッション作業領域の inputs はスクリーンショット等の一時的な補助資料として扱う。

---

## 10. 禁止事項

- inputs フォルダが存在するのに読み込まずにレビューを開始すること
- inputs の内容を無視して「コードの書き方」だけを評価すること
- ユーザーのヒアリング結果を inputs に保存せず、メモリやコンテキストだけで保持すること
- inputs ファイルを自動削除すること（手動削除のみ）
- ヒアリング不要の判断をユーザーに確認せず AI が独断で行うこと
