## 1. 出力フォーマット（必須・固定型）

### 1.1 全体構成（順序厳守）

統合サマリは **必ず以下の順序** で出力する。任意セクションも含め、`<details>` ブロックは省略せず本文に「該当なし」を残すことで読み手の判別性を確保する。

```markdown
# 🤖 [deep-code-review-plugin] PR レビューサマリー （第 <N> 回）

> **レビュー結果**: <OK（Ready to Merge） | NG・再レビュー不要（Needs Attention） | NG・再レビュー要（Needs Work）>
> **対応必須**: Critical <X> 件 / High <X> 件 / Medium <X> 件
> **改善提案**: <X> 件 ／ **スコープ外**: <X> 件
> **実施日時**: <YYYY-MM-DD HH:MM>（<タイムゾーン>） ／ **対象 head SHA**: `<sha7>`
> **レビュー対象**: <PR #<N> | branch-diff (<base>...HEAD) | file-list: ...>
> **レビューモード**: <標準 | 簡易>

<details><summary>1. 対応が必要な指摘 （<X> 件 <状態記号>）</summary><h2>1. 対応が必要な指摘 （<X> 件）</h2>...</details>
<details><summary>2. 改善提案 （<X> 件 <状態記号>）</summary><h2>2. 改善提案 （<X> 件）</h2>...</details>
<details><summary>3. スコープ外指摘 （<X> 件 <状態記号>）</summary><h2>3. スコープ外指摘 （<X> 件）</h2>...</details>
<details><summary>4. 観点別の指摘なし</summary><h2>4. 観点別の指摘なし</h2>...</details>
<details><summary>5. 観点間の見解の差異</summary><h2>5. 観点間の見解の差異</h2>...</details>
<details><summary>6. 既存指摘の解消判定 （<X> 件 ／ 再レビュー時のみ）</summary><h2>6. 既存指摘の解消判定 （<X> 件 ／ 再レビュー時のみ）</h2>...</details>
<details><summary>7. 未確認事項・制約</summary><h2>7. 未確認事項・制約</h2>...</details>
<details><summary>8. 集計</summary><h2>8. 集計</h2>...</details>
<details><summary>9. レビュー実施環境（PR レビュー時のみ）</summary><h2>9. レビュー実施環境（PR レビュー時のみ）</h2>...</details>
```

> 各 `<details>` の実体（`<summary>` 直後の `<h2>` 再掲・内部本文の HTML 記法・改行位置）は `template/review-summary.md` を参照。上記は順序確認用の **1 行簡略表記** であり、`...` 部に各セクション本文が入る（実出力の改行位置はテンプレートに従う。template が常に優先）。
> `<状態記号>`（セクション 1〜3 の `<summary>` のみ）: 件数 >0 は「⚠」、件数 0 は「✓ + 状態語」（セクション 1 は `0 件 ✓ 指摘なし`、セクション 2・3 は `0 件 ✓ 該当なし`）。`<h2>` 再掲側には付記しない。規範は `template/review-summary.md` 冒頭を参照。

### 1.2 ヘッダブロック（必須）

サマリの先頭は **必ず** 以下のヘッダブロックで始める。1 行目はタイトル（`# 🤖 [deep-code-review-plugin] PR レビューサマリー （第 <N> 回）`）、続く `> ...` の引用ブロックがメタデータ。

| 項目 | 必須 | 説明 |
|------|------|------|
| 第 N 回 | ✓ | 同一 PR / 同一スコープに対する **通番**。初回は 1、再レビューは 2, 3 と進める |
| **レビュー結果** | ✓ | **総合判定 + 再レビュー要否を統合した単一フィールド**。値は次の 3 種:<br>・`OK（Ready to Merge）`<br>・`NG・再レビュー不要（Needs Attention）`<br>・`NG・再レビュー要（Needs Work）` |
| 対応必須 件数 | ✓ | Critical / High / Medium の各件数 |
| 改善提案 件数 | ✓ | 採用件数（最大 10 件） |
| スコープ外 件数 | ✓ | スコープ外指摘の件数 |
| 実施日時 | ✓ | `YYYY-MM-DD HH:MM`（タイムゾーン明記） |
| 対象 head SHA | ✓ | PR レビュー時は PR 最新コミットの 7 桁 SHA |
| レビュー対象 | ✓ | PR 番号 / `branch-diff (base...HEAD)` / file-list 等 |
| レビューモード | ✓ | `標準` / `簡易` |

> **重要**: `総合判定` と `再レビュー要否` は **「レビュー結果」という単一の統合フィールド** で表現する（別フィールドへの分割は禁止）。サマリーヘッダ・完了報告・PR コメント本文で同一の値を使う。

### 1.3 件数ルール

| 区分 | 取り扱い |
|------|---------|
| 対応が必要な指摘（Critical / High / Medium） | **全件記載**（切り捨て不可） |
| 改善提案（Low / Suggestions） | **最大 10 件まで**。同一カテゴリは 1 件にグルーピングしてまとめる。10 件を超える場合は「その他の改善候補」として件数のみ示し、ユーザーが希望した場合に詳細化 |
| スコープ外指摘 | 件数制限なし。ただしノイズになる軽微な記載は避ける |
| 同一指摘の重複 | `severity-ranking.md` のルールで 1 件にまとめる |

### 1.4 集計セクションの必須項目

集計セクションに以下を **必ず明記** する（透明性のため）:

| 項目 | 例 |
|------|------|
| 実施日時 | `2026-04-27 14:30 (JST)` |
| レビューモード | `標準` / `簡易` |
| 参加観点別スキル | `5 種（impl, testing, security, architecture, frontend）` |
| 参加エージェント | `10 名（impl, test, sec, linter, runner, perf, dep, arch, dba, web）` |
| 比較ブランチ | `origin/develop`（自動判定）/ `master`（CLAUDE.md 指定）/ `PR #45`（PRレビュー時）等 |
| 対象 head SHA | `a3c4d5e (a3c4d5ef0123...)` |
| 参照規約ファイル一覧 | `CLAUDE.md, .claude/rules/coding/csharp.md, .claude/rules/security/auth.md, .editorconfig` |
| 検出言語・FW と適用観点プロファイル | `TypeScript（主・languages/typescript.md）, React（frameworks/react.md）, SQL: PostgreSQL（副・languages/sql.md）`。未対応言語がある場合は `Go（観点プロファイル未収録）` のように明記 |
| 参照仕様書一覧 | `docs/specs/order-feature.md`（spec 引数で指定された場合のみ。未指定時は `（仕様書未指定）`） |
| 件数集計 | Critical/High/Medium/改善提案/スコープ外 の各件数 |
| 低信頼のため除外 | `2 件`（信頼度 60 未満で足切りした件数。0 件時は `0 件`。C24） |
| test-runner ステータス | `GREEN` / `RED` / `SKIPPED` |
| レビュー対象 | `branch-diff`（origin/develop...HEAD）/ `PR #45` / `file-list: src/Order/Order.cs` 等 |
| Agent Teams 採用パターン | `quality-assurance` / `security-compliance` / `system-design` / `data-quality-extended` / `frontend-quality-extended` / `不採用（サブエージェント方式）` |

## 1.5 Finding ID 採番規則（必須）

検出した **すべての指摘・改善提案・スコープ外指摘**（軽微なものを含む）に、ユーザーが ID で修正指示できる **一意の Finding ID** を付与する。

### 規則

| 規則 | 内容 |
|------|------|
| フォーマット | `CR-NNN`（CR = Code Review、NNN = 3 桁ゼロ詰めの連番） |
| 採番範囲 | 統合サマリ全体で **連続採番**（Issues / Suggestions / Scope-out を区別せず通番） |
| 採番開始 | `CR-001` から開始 |
| 採番順序 | Issues（致命度高い順）→ Suggestions（Impact×Effort 降順）→ Scope-out（重要度順）の **記載順** |
| 採番責任 | **オーケストレーター（`code-review`）が Step 6（優先度ランキング）後に一括採番**。観点別スキル・エージェントは ID を採番しない |
| 再レビュー | 第 N 回再レビューは **前回 `finding-thread-map.json` の最大 ID 番号 + 1 から採番開始**。前回 ID は引き継がず、解消判定セクションで「過去 Finding ID（前回）」として参照。第 1 回は CR-001 から、第 2 回以降は前回最終 ID + 1 から |
| 命名衝突 | コード側に `CR-XXX` のような既存マーカーがある場合のみ、別プレフィクス `REV-NNN` を使用 |
| 表記場所 | (1) サマリー詳細補足の見出し `<h4>CR-NNN: <タイトル></h4>`（HTML 記法） / (2) サマリー表の `ID` 列 / (3) PR インラインコメント本文冒頭（`## [CR-NNN] ...` Markdown H2） / (4) サマリースレッドの目次 / (5) 完了報告 |

### 採番例

```
CR-001  [Critical] SQL インジェクション可能性 → セクション 1（対応が必要な指摘）
CR-002  [High]     Null ハンドリング不足     → セクション 1（対応が必要な指摘）
CR-003  [Medium]   エラーメッセージ未整備     → セクション 1（対応が必要な指摘）
CR-004  [Impact: HIGH] N+1 クエリ            → セクション 2（改善提案）
CR-005  [Impact: MED]  早期 return リファクタ → セクション 2（改善提案）
CR-006  [Scope-out] Repository パターン移行   → セクション 3（スコープ外指摘）
```

### ユーザーが ID で修正指示する例

```
ユーザー: 「CR-001 を修正したい。修正案のとおり実装して」
ユーザー: 「CR-005 はスコープ外として了承。本 PR では対応しない」
ユーザー: 「CR-002, CR-003 は次の PR で対応するので、本 PR ではコメントだけ残して」
```

ユーザーは ID だけで該当指摘を一意に特定でき、修正指示・優先度判断・コメント追記・スコープ判断が容易になる。

## 2. 指摘・改善提案ごとの必須項目

統合サマリの セクション1〜セクション3 は **2 段構成**:

- **A. サマリー表（必須・全件記載）**: ID / 致命度 / カテゴリ / タイトル / 該当箇所 等を表形式で一覧化。ID は PR インラインコメントへの **明示リンク**
- **B. 詳細補足（インライン未投稿の指摘のみ）**: PR にインラインコメントを投稿していない指摘について詳細（該当コード / 指摘内容 / 求める修正 / 理由・根拠 等）を記述。投稿済みの指摘は PR コメント側で詳細が読めるため重複記述しない

### 2.1 「対応が必要な指摘」の項目

#### 2.1.1 サマリー表（A）の列

| 列 | 説明 |
|---|---|
| **ID** | `[CR-NNN](<inline-comment-url>)` 形式の **明示リンク**。インライン未投稿時はリンクなしのプレーンテキスト |
| 致命度 | Critical / High / Medium |
| 信頼度 | 0〜100（`severity-ranking.md` セクション 7。60 未満は足切り済みのため通常この表には現れない） |
| カテゴリ | セキュリティ / データ破損 / 機能停止 / パフォーマンス / 保守性 / 規約 / 依存 / テスト 等 |
| タイトル | 指摘の 1 行要約 |
| 該当箇所 | `<ファイルパス>:<開始行>-<終了行>` |
| 規約・根拠 | OWASP / CWE / プロジェクト規約パス / 仕様書パス 等（短縮可） |
| 担当 | 検出した専門エージェント（複数の場合はカンマ区切り） |

#### 2.1.2 詳細補足（B）の項目（**インライン未投稿時のみ**）

| 項目 | 説明 |
|---|---|
| 該当コード | サマリー（`<details>` 内）では `<pre><code class="language-<lang>">` で該当行を引用（前後 2〜3 行のコンテキスト推奨・`<` `>` `&` は HTML エスケープ） |
| 指摘内容 | 何が問題か（1〜3 行で具体的に） |
| 求める修正 | どう直すべきか（コード例があれば併記） |
| 理由・根拠 | なぜその修正が必要か（OWASP / CWE / プロジェクト規約 / 過去事例 / リスク等の引用） |
| 仕様検討 | 仕様判断が要る場合のみ。論点・候補 A/B・推奨・確認先を記載 |
| 関連コミット | 履歴参照が必要な場合のみ。`<a href="<commit-url>"><sha7></a>` 形式の明示リンク |

### 2.2 「改善提案」の項目

#### 2.2.1 サマリー表（A）の列

| 列 | 説明 |
|---|---|
| **ID** | `[CR-NNN](<inline-comment-url>)` 形式の明示リンク。インライン未投稿時はリンクなし |
| Impact | HIGH / MED / LOW |
| Effort | HIGH / MED / LOW |
| カテゴリ | 可読性 / 保守性 / 命名 / 軽微リファクタ 等 |
| タイトル | 提案の 1 行要約 |
| 該当箇所 | `<ファイルパス>:<開始行>-<終了行>` |
| 担当 | 検出したエージェント |

#### 2.2.2 詳細補足（B）の項目（**インライン未投稿時のみ**）

| 項目 | 説明 |
|---|---|
| 該当コード | コードスニペット |
| 提案内容 | どう変えると良くなるか |
| 修正案 | コード例（任意） |
| 理由・根拠 | なぜ改善が望ましいか |
| 関連コミット | 履歴参照が必要な場合のみ。明示リンク化 |

### 2.3 「スコープ外指摘」の項目

#### 2.3.1 サマリー表（A）の列

| 列 | 説明 |
|---|---|
| **ID** | `[CR-NNN](<inline-comment-url>)` 形式の明示リンク。インライン未投稿時はリンクなし |
| カテゴリ | 既存技術的負債 / 別機能改善 / 仕様の余地 等 |
| タイトル | スコープ外項目の 1 行要約 |
| 該当箇所 | `<ファイルパス>:<開始行>-<終了行>`（参考情報） |
| スコープ外と判断した理由 | PR の目的・タイトル / 仕様書の範囲 / 既存実装の課題 等から外れる旨を明記 |

#### 2.3.2 詳細補足（B）の項目（**インライン未投稿時のみ**）

| 項目 | 説明 |
|---|---|
| 該当コード（参考） | コードフェンスでスニペットを引用 |
| 所見 | 本 PR では対応しないが、将来検討に値する理由・対応指針 |
| 関連コミット | 履歴参照が必要な場合のみ。`[<sha7>](<commit-url>)` 形式で明示リンク化（TFS / GitHub 各々の commit URL を使う） |

> **重要**: スコープ外指摘では **「別 PR で対応してください」「別途 PR を起票してください」と書かない**。
> 別 PR 対応の推奨は修正指示のノイズになるため、`scope-out-policy` の規範に従う。詳細は `${CLAUDE_PLUGIN_ROOT}/references/scope-out-policy.md` 参照。

### 2.4 必須項目を満たせない場合の扱い

- 担当エージェントが該当コード・行番号を返さない場合は、メイン側で差分から補完する
- 補完できない場合は明示的に「該当行不明（推定: <ファイル名>）」と記載
- 致命度がエージェント側で曖昧な場合は `severity-ranking.md` の評価語マッピングに従って本スキル側で再評価
- 信頼度がエージェント側で未付与の場合は `severity-ranking.md` セクション 7.1 の定義に照らして本スキル側で推定値を付与（U15 / C24）

### 2.5 コードスニペット引用の規範（必須）

| ルール | 内容 |
|------|------|
| 引用ブロック必須 | **インラインコメント（Markdown 文脈）**: `` ``` `` コードフェンスで囲む。**サマリー（`<details>` 内・HTML 文脈）**: `<pre><code>` で囲み、コード内の `<` `>` `&` を HTML エスケープする（自動リンク化・HTML 解釈・Markdown 装飾を防ぐ） |
| 言語識別子明記 | コードフェンスは `` ```csharp `` 等、`<pre><code>` は `class="language-csharp"` 等。不明時は省略可 |
| 範囲一致 | コメント本文で示す引用は **指摘箇所の `start_line`〜`end_line` と一致** させる |
| 過大引用禁止 | ファイル全文・関数全体の貼り付けは禁止。前後 2〜3 行のコンテキストに留める |
| 自動リンク防止 | スニペット中の `#123` `@user` 等はコードフェンス / `<pre><code>` 内ならエスケープ不要。Markdown 文脈のフェンス外は `\#` / `\@` でエスケープ、HTML タグ間テキストは `#` を使わない表現に言い換える（詳細: `${CLAUDE_PLUGIN_ROOT}/references/comment-sanitization.md` セクション 5.5 / 5.5.7） |
| PR インラインコメント時 | `pulls/<N>/comments` または ADO `threadContext.rightFileStart/rightFileEnd` の行番号を **指摘箇所と完全一致** させる |

### 2.6 PR インラインコメントへの URL（リンク方針・必須）

サマリースレッド セクション1-A / セクション2-A / セクション3-A の表で `ID` 列を PR インラインコメントへの **明示リンク** にする際の URL 形式:

#### TFS / Azure DevOps

```
https://<host>/.../pullrequest/<N>?_a=files&path=<file-path>&discussionId=<thread-id>
```

| パラメータ | 必須 | 内容 |
|----------|------|------|
| `_a=files` | ✓ | Files タブで開く（discussion を表示） |
| **`path=<file-path>`** | **✓** | **`/` 始まりのリポジトリルート相対パス**（例: `/plugins/deep-code-review/skills/pr-review/SKILL.md`）。**省略するとサーバ側でファイルが特定できず該当インラインコメントへ正しく遷移しない** |
| `discussionId=<thread-id>` | ✓ | 投稿先スレッドの ID（API レスポンスの `id` フィールド） |

URL エンコードが必要な文字（空白・日本語・特殊記号）はエンコードする。

#### GitHub

```
https://github.com/<owner>/<repo>/pull/<N>#discussion_r<comment-id>
```

| パラメータ | 内容 |
|----------|------|
| `#discussion_r<comment-id>` | 投稿後の `pulls/comments/{id}` の ID をフラグメントとして指定 |

#### 表記（サマリー表は HTML）

```html
<tr>
    <td><a href="https://tfs.example.com/.../pullrequest/52?_a=files&amp;path=/plugins/deep-code-review/skills/pr-review/SKILL.md&amp;discussionId=193">CR-001</a></td>
    <td>High</td>
    <td>規約</td>
    <td>...</td>
    <td>...</td>
</tr>
```

リンクは `<a href="<URL>">CR-NNN</a>` 形式の HTML リンク（`<details>` 内では Markdown リンクがレンダリングされないため。href 内の `&` は `&amp;` にエスケープ）。インラインコメント未投稿時は `CR-NNN` プレーンテキストでリンクを張らない。
