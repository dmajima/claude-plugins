# case-09 DB 制約・トランザクション削除の回帰検出（U16: データ層の防御削除）

マイグレーション / データアクセス処理のリファクタリングの差分の削除側（`-` 行）で、既存の DB 制約（外部キー・NOT NULL）やトランザクション境界が失われた回帰を dba が指摘するケース。新規のスキーマ設計上の問題ではなく、既存のデータ整合性・原子性の防御がリファクタで削られた回帰（U16）を検証する。

## 入力

| 項目 | 内容 |
|-----|------|
| 委譲 args | `<差分スコープ（マイグレーション + データアクセス処理のリファクタリング）> <プロジェクト規約サマリ> mode=standard` |
| 起動形態 | 委譲（code-review オーケストレーターから Skill ツール経由） |
| 変更分類 | リファクタリング（スキーマ簡素化・データアクセス層整理） |
| 差分内容 | マイグレーションの削除側（`-` 行）で外部キー制約（`FOREIGN KEY ... REFERENCES`）と `NOT NULL` 制約が除去され、データアクセス処理の削除側で複数更新を束ねる明示的なトランザクション境界（`BeginTransaction()` ... `Commit()` / `using var tx` / `@Transactional`）が除去されている。追加側（`+` 行）では同等の制約・トランザクション境界が再導入されていない |

## 分岐の根拠

`${CLAUDE_PLUGIN_ROOT}/references/skill-rules-matrix.md` U16（差分の削除側で既存の防御コード（例外処理・入力検証・リソース解放・a11y 属性・認可・エラー表示 UI）が失われていれば回帰として指摘する）、`${CLAUDE_PLUGIN_ROOT}/references/universal-rules.md` U16「対象とする防御コード」（入力検証・境界チェック・ガード節 / リソース解放（`using` / `finally` 等の後始末・整合性担保））・「判定」（削除行の防御が追加行で再導入されていなければ回帰・意図と区別できない場合は信頼度中程度で意図確認）、references/checklist.md セクション A U16。ドメイン固有の回帰パターンとして、外部キー・NOT NULL は DB レベルでのデータ整合性ガード（U16 の境界チェック・入力検証に相当）、トランザクション境界は複数更新の原子性を担保する後始末（U16 のリソース解放・`finally` に類する整合性防御）にあたり、その削除を dba 観点（SKILL.md「前提」の観点表: マイグレーション安全性・データ整合性）で回帰として評価する。

**既存ケースとの差別化**: case-01 は委譲経路の DB 変更あり（architect + dba）の通常フロー、case-05 は「DB スキーマ変更をレビューして」トリガーでの dba 起動を主眼とするのに対し、本ケースは削除側（`-` 行）の DB 制約・トランザクション境界消失検出という U16 固有の分岐を検証する。silent-failure（新規コードの握りつぶし）ではなく、リファクタで既存防御が削られるケースを扱う点で他観点と別物。

## 期待動作

- 差分に DB スキーマ / マイグレーション変更が含まれると判定し、architect / dba の 2 エージェントを 1 メッセージ内で並列起動する（SKILL.md「実行フロー」手順 2〜3 / checklist.md O1）
- dba が差分の削除側（`-` 行）を精査し、外部キー制約・`NOT NULL` 制約・明示的なトランザクション境界が失われていないか確認する（universal-rules.md U16 / checklist.md セクション A U16）
- 削除された防御が追加側（`+` 行）で同等に再導入されていない場合、回帰（regression）として指摘する（universal-rules.md U16「判定」）
- 具体的には、外部キー制約の消失を「参照整合性の後退の回帰」、`NOT NULL` の消失を「NULL 混入リスクの回帰」、トランザクション境界の消失を「複数更新の原子性喪失（部分コミット）の回帰」として指摘する（universal-rules.md U16「対象とする防御コード」・SKILL.md「出力フォーマット」の dba セクション）
- 新規コードの設計問題観点とは切り分け、あくまで「リファクタで既存のデータ層防御が削られた」回帰として位置づける（universal-rules.md U16 規範）
- 意図的削除（正規化変更に伴い制約を別テーブルへ移設した等の正当理由）と区別できない場合は、信頼度を中程度にし「回帰の可能性・意図確認」として提示する（universal-rules.md U16「判定」/ U15 信頼度付与）
- 各指摘に重要度・信頼度・スコープ内/外フラグを付与する（checklist.md U11 / U15 / O5）
- 中間レポートは「## アーキテクチャ観点レビュー結果」+「### architect」「### dba（DB変更あり時のみ）」の構造で返却する（SKILL.md「出力フォーマット」/ checklist.md C-Auto-1 / C-Auto-2）
- Finding ID（CR-NNN）の採番・Verdict 判定は行わない（checklist.md O9。オーケストレーター責務）
