# レビュー基準（規約）の優先順位解決

レビューの評価基準となる規約の優先順位解決ルール。「プロジェクト独自規約が常にデファクト規約より優先される」ことを保証する SSOT。
`code-review` オーケストレーターが Step 2（プロジェクト規約読込）で適用し、解決結果を「適用規約サマリ」として観点別スキル・エージェントに引き渡す。

## 1. 優先順位（5 段階・上位が勝つ）

| 優先 | 規約源 | 例 |
|------|--------|-----|
| 1 | **ユーザー明示指示**（当該セッション） | 「今回は命名規則の指摘は不要」「この PR では性能観点を重点的に」 |
| 2 | **機械設定ファイル** | `.editorconfig` / `eslint.config.js` / `.eslintrc*` / `.prettierrc*` / `pyproject.toml [tool.ruff]` / `.php-cs-fixer.php` / `phpcs.xml` / `.stylelintrc*` / `tsconfig.json`（strict 等） |
| 3 | **文書規約** | レビュー対象リポジトリの `CLAUDE.md` 階層 / `.claude/rules/**` / `docs/` 配下の規約 / `CONTRIBUTING.md` / スタイルガイド |
| 4 | **既存コードの一貫した慣習** | 変更対象ファイル周辺・同一モジュールで一貫して使われているパターン |
| 5 | **言語観点プロファイルのデファクト規約** | `${CLAUDE_PLUGIN_ROOT}/references/languages/*.md` の準拠規約（Microsoft 規約 / PEP 8 / PSR-12 等） |

- 解決は **項目単位のオーバーライド**: 上位の規約源が言及していない項目は、下位の規約源で補完する（全置換ではない）
- 優先度 2 と 3 が矛盾する場合は **機械設定（2）を優先** する（ビルド・CI で強制されるため）

## 2. レビューでの適用ルール

### 2.1 指摘の根拠明記

規約・スタイルに関する指摘には、**どの規約源に基づくか** を根拠として明記する:

```markdown
[Medium] OrderService.cs:42 プライベートフィールドの命名規則違反
- 根拠: .editorconfig の dotnet_naming_rule（優先度 2: 機械設定）
```

```markdown
[Low] utils.py:15 snake_case 推奨
- 根拠: PEP 8（優先度 5: デファクト。プロジェクト独自規約なし）
```

### 2.2 デファクト規約と独自規約の衝突

プロジェクト独自規約（優先度 1〜4）がデファクト規約（優先度 5）と異なる場合:

- **独自規約への準拠を「正」として評価** する（デファクト違反を指摘しない）
- 例: プロジェクトがタブインデントを `.editorconfig` で規定していれば、言語プロファイルの「スペース推奨」を根拠にした指摘は出さない

### 2.3 既存慣習（優先度 4）の取り扱い上の注意

- 既存コードの慣習は「一貫している」場合のみ規約源として扱う（1〜2 箇所の例では慣習と断定しない）
- **提出コード（レビュー対象の差分自体）は規約源にしない** — 提出コードは誤りがあることを前提とする（コード信頼性原則 U14）。差分内のパターンを「このプロジェクトの慣習」として類推してはならない
- 既存慣習がデファクトから乖離しており、かつ文書化されていない場合は、指摘ではなく「規約の文書化提案」として Suggestions に記載してよい

### 2.4 未対応言語での適用

観点プロファイル（優先度 5）が存在しない言語では、優先度 1〜4 のみで評価する。詳細は `${CLAUDE_PLUGIN_ROOT}/references/language-detection.md` セクション 4 を参照。

### 2.5 欠落系指摘（「無いこと」の指摘）での兄弟コード確認

「認可属性が無い」「入力検証が無い」「CSRF トークン検証が無い」等、**あるべきコントロールの欠落** を指摘する場合は、差分行に接地しているだけで High を付けず、以下を確認して重要度・信頼度を決める:

1. **差分外の兄弟コードの同一欠落を確認**: 同一ファイル・同一層の既存メソッド（差分外）が同じコントロールを持っているか。既存の兄弟コードも同じ欠落を持つ場合、その欠落は **既存負債** の可能性が高い
2. **グローバル設定の確認**: 認可なら `Program.cs` のフォールバックポリシー / `RequireAuthorization()`、CSRF ならグローバルミドルウェア等、コントロール がグローバルに担保されていないか
3. **判定**:
   - 既存負債（兄弟コードも同一欠落 + グローバル担保なし）→ **スコープ外指摘** に寄せるか、既存負債である旨を明記して重要度を調整
   - 新規コード固有のリスクが実質的に高い（状態変更 API の新設・外部公開の新設・新規に機密を扱う等）→ 高リスクである理由を明記した上で Issues に High で載せてよい（例: 新規 POST の状態変更エンドポイントは既存の GET より高リスク）
   - グローバル設定が確認できない → 未確認事項に「グローバル設定次第で実露出が変わる」と明記し、信頼度を控えめにする

これにより「差分行に接地しているだけの投機的 High」を防ぎ、兄弟コードの既存欠落を見ない過大評価を避ける。

## 3. 適用規約サマリへの記録

オーケストレーターは Step 2 で解決結果を「適用規約サマリ」に記録し、観点別スキルへの委譲引数に含める。下流（観点別スキル・エージェント）は **このサマリのみ** を規約根拠とし、独自に規約源を再解釈しない。

```markdown
## 適用規約サマリ

### 言語・フレームワーク検出結果
（language-detection.md セクション 3 Step 5 の表）

### 規約源の解決結果
| 項目 | 適用規約 | 規約源（優先度） |
|------|---------|----------------|
| C# 命名 | .editorconfig の dotnet_naming_rule | 機械設定（2） |
| C# インデント | スペース 4 | .editorconfig（2） |
| コミット規約 | Conventional Commits | CONTRIBUTING.md（3） |
| TS strict | strict: true | tsconfig.json（2） |
| その他未規定項目 | languages/csharp.md, languages/typescript.md のデファクト | 言語プロファイル（5） |

### ユーザー指示（優先度 1）
- （当該セッションでの明示指示があれば記載。なければ「なし」）
```

## 4. 禁止事項

- プロジェクト独自規約の確認を省略して、言語プロファイルのデファクトだけで規約指摘を出すこと
- 提出コード（レビュー対象差分）内のパターンを規約源として類推すること（U14 違反）
- 優先度の低い規約源を根拠に、優先度の高い規約源への準拠コードを「違反」と指摘すること
- 適用規約サマリに記録せず、観点別スキルごとに独自の規約解釈を行うこと
