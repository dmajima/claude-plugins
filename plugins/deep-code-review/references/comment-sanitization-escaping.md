## 5. 注意事項

- `sed` 実装は GNU sed（Git for Windows 付属の `usr/bin/sed.exe` 等）を前提とする。BSD sed では `-E` の挙動が一部異なる
- 文字クラス内の `-` は **末尾に配置** する（先頭/末尾以外だと範囲記号として解釈される実装あり）
- 検出されないパターンが見つかったら追記する（オープンセット）
- HTML エンティティ（`&#x6a;avascript:` 等）でのバイパス対策が必要な場合は、sed の前段で `sed 's#&#x?[0-9a-f]+;##gi'` を加える等の追加対応を検討

## 5.5 ホスト固有の予約文字エスケープ（厳守）

PR ホスティングサービスの **Markdown レンダラ** は特定の文字パターンを **自動リンク** に変換する。
コメント本文中に「説明として書いた `#136`」が **無関係な Work Item / Issue へのリンクに化ける** ことを防ぐため、以下のエスケープ規則を必ず適用する。

> **厳守ルール**: PR / Issue / Work Item にコメント・スレッドを投稿する **すべての経路** で、本セクションのエスケープが適用済みであることを `comment-sanitization.md` の **投稿前チェックリスト**（セクション 5.6）で確認すること。チェックリスト未通過の本文を API 投稿してはならない。

### 5.5.1 自動リンク化の対象パターン

| ホスト | パターン | 自動変換先 | 例 |
|--------|---------|-----------|------|
| Azure DevOps / TFS | `#<数字>` | Work Item へのリンク | `#123` → Work Item #123 |
| Azure DevOps / TFS | `!<数字>` | （一部バージョン）PR へのリンク | `!45` → PR !45 |
| Azure DevOps / TFS | `@<英数字>` | ユーザーメンション | `@taro` → @taro へのメンション |
| Azure DevOps / TFS | `<discussionId>` がコメントアンカー | URL の `#<数字>` 形式（既存コメントへの参照） | `#1777289222` のような長桁数字も Work Item パーサに拾われ得るため、**意図しない数字列は常にエスケープ** |
| GitHub | `#<数字>` | Issue / PR へのリンク | `#123` → Issue #123 |
| GitHub | `GH-<数字>` | 旧 Issue 参照 | `GH-123` → Issue #123 |
| GitHub | `@<英数字>` | ユーザー / 組織メンション | `@octocat` → @octocat |
| GitHub | `@<org>/<team>` | チームメンション | `@github/security` |
| GitHub | `<owner>/<repo>#<数字>` | 他リポジトリ参照 | `octocat/Hello-World#1` |
| GitHub | コミット SHA（7+ 文字） | コミットへのリンク | `a3c4d5e` |

### 5.5.2 エスケープ規則（必須）

| ケース | 動作 |
|--------|------|
| **意図的なリンク** | 必ず明示的な Markdown リンク `[<表示テキスト>](<URL>)` で記述する。例: `[#146](https://.../pullrequest/46?_a=files&discussionId=146)` |
| **説明文中の意図しない `#<数字>`** | **`\#` でエスケープ** する。例: `\#123 件の指摘` |
| **意図しない `@<英数字>`** | **`\@` でエスケープ** する。例: `\@username の挙動` |
| **意図しない `!<数字>`（Azure 限定）** | **`\!` でエスケープ** する |
| **コミット SHA を文章内に含める場合（GitHub 限定）** | バッククォートで囲む: `` `a3c4d5e` `` （リテラル化） |
| **Work Item / Issue 番号を「対象」として参照する場合** | 必ず **明示リンク** を生成する。`#123` を裸書きしない |
| **件数表記の `#` （ハッシュ記号）** | 「No.123」「123 件」「件数: 123」のように **そもそも `#` を使わない** 表現を優先。`\#` エスケープは可だが、表記の意図がぶれる |
| **コードシンボル中の `@` `!` `#`**（例: `@param`, `cls!member`, C#マクロ）| インラインコード（`` ` `` 囲み）またはコードフェンスで囲む |

### 5.5.3 実装パターン: 自動リンク変換と保護プレースホルダ

サニタイズスクリプトで自動エスケープする場合、**意図的な Markdown リンク `[...](...)` 内のテキストは保護** する必要がある（リンクテキスト内の `#` をエスケープすると Markdown が壊れる）。

```bash
# 1. Markdown リンク `[xxx](yyy)` を一時プレースホルダに退避
# 2. 残りの本文で予約文字をエスケープ
# 3. プレースホルダを復元

SAFE=$(printf '%s' "$RAW" | python3 -c '
import sys, re
text = sys.stdin.read()
# Markdown リンクを退避
links = []
def stash(m):
    links.append(m.group(0))
    return f"\x00LINK{len(links)-1}\x00"
text = re.sub(r"\[[^\]]+\]\([^)]+\)", stash, text)
# 予約文字をエスケープ
# lookbehind の文字クラス [\\\w] は「リテラル \ またはワード文字」（raw string 内の \\ = 正規表現のリテラル \）
text = re.sub(r"(?<![\\\w])#(\d+)", r"\\#\1", text)        # #<数字>
text = re.sub(r"(?<![\\\w])@([A-Za-z0-9_./-]+)", r"\\@\1", text)  # @<word>
text = re.sub(r"(?<![\\\w])!(\d+)", r"\\!\1", text)        # !<数字>（Azure）
# プレースホルダを復元
def restore(m):
    return links[int(m.group(1))]
text = re.sub(r"\x00LINK(\d+)\x00", restore, text)
sys.stdout.write(text)
')
```

`python3` が利用不可な環境では、サニタイズスクリプト作成者が **手動で `\#` / `\@` / `\!` をヒアドキュメント内に記述** する。

### 5.5.4 既知の例外と制限

- **コードフェンス内（`` ` `` または ` ``` ` で囲まれた範囲）**: Azure / GitHub ともに自動リンク変換を **行わない**。コードブロック内の `#123` はそのままで OK
- **URL の一部としての `#` / `@`**: URL 内のフラグメント (`#section`) や `user@host` 形式はリンク変換されない
- **メールアドレス**: `user@example.com` 形式は自動リンク化されるが、これは多くの場合意図通り
- **Markdown リンクテキスト内の `]`**: セクション 5.5.3 の python3 stash 正規表現 `r"\[[^\]]+\]\([^)]+\)"` は、リンクテキストに `]` を含むケース（例: `[fix [issue]](url)` のような入れ子）では stash されず予約文字エスケープが誤適用される可能性がある。**入れ子の角括弧を含むリンクテキストは避ける**こと
- **URL 内の閉じ括弧 `)`**: 同様に `[text](https://example.com/foo(bar))` のような URL に `)` を含むケースでは早期終了する。**URL 内に閉じ括弧を含む場合は事前にエスケープ**するか、URL を別の形式（リファレンス形式リンク等）に変更する
- 完全に堅牢な実装は CommonMark / GFM の本格パーサ（Python の `markdown-it-py` 等）が必要だが、本サンプルは **9 割以上のケースをカバー** する実用的な近似実装

### 5.5.5 適用タイミング

`comment-sanitization.md` のサニタイズパターン（セクション 3-4）と **連続適用** する。順序:

1. 機密文字列の伏字化（セクション 4）
2. 予約文字のエスケープ（本セクション）
3. 投稿前チェックリスト（セクション 5.6）の通過確認
4. 最終的に `jq --rawfile` で JSON に組み込み API 投稿

### 5.5.6 OK / NG 例

| 区分 | 例 |
|------|------|
| ❌ NG（自動リンクに化ける） | `#123 と #456 を確認しました` → Work Item #123 / #456 へのリンクに変換される |
| ✅ OK（エスケープ済み） | `\#123 と \#456 を確認しました` → 文字列としてそのまま表示 |
| ✅ OK（明示リンク化） | `[Work Item \#123](https://.../workItem/123) と [Work Item \#456](https://.../workItem/456) を確認しました` |
| ❌ NG（メンション化） | `@taro さんに確認依頼` → `@taro` へのメンション通知 |
| ✅ OK | `\@taro さんに確認依頼` または `担当者: taro さんに確認依頼` |
| ❌ NG（行番号と称した数字が Work Item にリンク） | `OrderService.cs の #123 行目` |
| ✅ OK | `OrderService.cs の 123 行目` または `` `OrderService.cs:123` `` |
| ✅ OK（コードフェンス内は変換されない） | <code>``` <br>// 変更箇所: OrderService.cs#L123 <br>``` </code> |
| ❌ NG（コミット SHA がリンクに） | `修正コミット a3c4d5e を参照` |
| ✅ OK | `` 修正コミット `a3c4d5e` を参照 `` |

### 5.5.7 HTML ブロック（`<details>` 内）における特殊文字の取り扱い

レビューサマリーの H2 セクションは `<details><summary>` 折り畳み + 内部 HTML 記法で出力される（`template/review-summary.md` 参照）。HTML ブロック内は Markdown 文脈と規則が異なるため、以下を適用する。

#### 自動リンク化エスケープ（`\#` / `\@` / `\!`）の適用範囲

| 文脈 | エスケープ | 理由 |
|------|----------|------|
| Markdown 文脈（タイトル行・ヘッダブロック・インラインコメント本文） | **適用する**（5.5.2 のとおり） | Markdown レンダラが自動リンク変換するため |
| HTML タグ間のテキスト（`<td>...</td>` / `<li>...</li>` 等） | **Markdown 文脈用の `\#` エスケープは適用しない**。レンダラによっては `\` が除去されず `\#123` と生表示されるため。意図しない `#<数字>` 等は「123 件」「No.123」のように **`#` を使わない表現に置き換える**。意図的な参照は `<a href="...">` の明示リンクにする | HTML ブロック内では `\` エスケープが Markdown として解釈されない場合がある |
| `<code>` / `<pre><code>` 内 | **エスケープ不要**（コードフェンス内と同様に自動リンク変換されない） | 5.5.4 のコードフェンス例外と同等 |

#### `<` `>` `&` の HTML エスケープ要否

| 文脈 | 要否 | 規則 |
|------|------|------|
| HTML タグ間のテキストにリテラルの `<` `>` `&` を含める場合 | **必須** | `&lt;` / `&gt;` / `&amp;` にエスケープする（例: `List<T>` → `List&lt;T&gt;`）。未エスケープだと後続がタグと解釈され表示が壊れる |
| `<pre><code>` 内のコードスニペット | **必須** | コード内の `<` `>` `&` も HTML エンティティにエスケープする（Markdown コードフェンスと異なり `<pre><code>` 内でも HTML タグが解釈されるため） |
| テンプレートのプレースホルダ（`<X>` / `<理由>` 等） | 差し替え時に判断 | プレースホルダ自体は出力時に実値へ差し替える。差し替え後の実値に `<` `>` `&` が含まれる場合は上記規則でエスケープする |

## 5.6 投稿前チェックリスト（必須）

PR / Issue / Work Item にコメント・スレッドを投稿する **直前** に、以下を全項目通過することを確認する。1 つでも未通過なら投稿を中止し、本文を修正してから再投稿する。

### 5.6.0 チェックリストの実行タイミング（必須）

本チェックリストは以下のタイミングで **各コメントごとに** 実行する:

1. コメント本文の生成完了後
2. jq での JSON body 構築前
3. curl での API 投稿前

3 段階のうち、**段階 2（jq での JSON body 構築前）を必須** とする。段階 1・3 は追加確認として実施を推奨する。

### 5.6.0.1 呼び出し元スキルでの参照義務

`pr-review` 等のコメント投稿スキルの SKILL.md の Step 7（コメント投稿ステップ）に、本チェックリストの実行を **必須ステップとして記載** すること。`references` 内の記載だけでは実行漏れが発生するため、SKILL.md のメインフローに「投稿前に `comment-sanitization.md` セクション 5.6 チェックリストを通過させること」の一文を含めること。

### 5.6.1 サニタイズチェックリスト

```
[ ] (S1) 機密文字列の伏字化を適用済み（セクション 3〜4）
[ ] (S2) 危険スキームリンク（javascript:/data:/vbscript:/file:）が本文に存在しない
[ ] (S3) `<img>` タグおよび外部画像 Markdown が本文に存在しない
[ ] (S4) 本文中の意図しない `#<数字>` が `\#` でエスケープされている、または明示リンク化されている
[ ] (S5) 本文中の意図しない `@<英数字>` が `\@` でエスケープされている、または明示リンク化されている
[ ] (S6) Azure DevOps 投稿時、本文中の意図しない `!<数字>` が `\!` でエスケープされている
[ ] (S7) GitHub 投稿時、コミット SHA を裸書きせず `` ` `` 囲みまたは明示リンク化されている
[ ] (S8) 意図的に Work Item / Issue / PR へリンクする箇所はすべて明示 Markdown リンク `[表示](URL)` 形式
[ ] (S9) コードフェンス外で `#`/`@`/`!` を含む識別子を引用する場合はインラインコード `` ` `` で囲んでいる
```

### 5.6.2 コード引用チェックリスト

```
[ ] (C1) すべてのコード引用がコードフェンス（``` または ` ` ）内に置かれている
[ ] (C2) コードフェンスに言語識別子（csharp / ts / vue / sql / xml / bash / json 等）を明記している
[ ] (C3) 引用範囲が「指摘箇所として示す行範囲（start_line〜end_line）」と一致している
[ ] (C4) 引用に過剰な前後コンテキストを含めていない（前後 2〜3 行を上限）
[ ] (C5) PR インラインコメントを投稿する場合、API の `start_line`/`line` または `rightFileStart`/`rightFileEnd` が引用範囲と完全一致している
[ ] (C6) ファイル全文・関数全体・無関係領域の貼り付けが含まれていない
```

### 5.6.3 投稿先指定チェックリスト

```
[ ] (P1) インラインコメントは `threadContext.filePath` または `path` が **正しい指摘ファイル** を指している
[ ] (P2) 範囲指定が **正しい指摘行** を指している（オフバイワンや diff 行ずれが起きていない）
[ ] (P3) サマリーコメント（PR 全体宛）は `threadContext == null` または filePath なしで投稿している
[ ] (P4) 既存自著スレッドへの reply の場合、`parentCommentId` または対象コメント ID が一致している
```

### 5.6.4 自動チェックの実装案（任意）

`comment-posting.md` の Step 7 実装側で、以下のような簡易チェックを追加すると安全性が高まる:

```bash
# 本文 SAFE が確定した時点で、以下のいずれかにマッチしないことを確認
violation=0
echo "$SAFE" | grep -nE '(^|[^\\\\\w])#[0-9]+([^a-zA-Z0-9_]|$)'        && violation=$((violation+1))
echo "$SAFE" | grep -nE '(^|[^\\\\\w])@[A-Za-z0-9_./-]+'                 && violation=$((violation+1))
echo "$SAFE" | grep -nEi '<img\b'                                         && violation=$((violation+1))
echo "$SAFE" | grep -nEi '\[[^]]+\]\((javascript|data|vbscript|file):'    && violation=$((violation+1))
[ "$violation" -gt 0 ] && { echo "ERROR: サニタイズチェック未通過。投稿を中止します。"; exit 1; }
```

> 上記は **コードフェンス外** のパターン違反を検出する簡易ガード。コードフェンス内の文字列は許容したい場合、別途プレースホルダ退避が必要。
