# 別 PR 推奨の禁止・スコープ外指摘の取り扱い・PR 外への影響禁止（プラグイン共通）

`deep-code-review` プラグインで生成するレビュー結果（PR コメント・統合サマリ・観点別スキルの返却本文）における **別 PR 対応の推奨方針** と、**プラグイン自身が PR 外のリソースを操作しない** という影響範囲制約を定義する。

> **位置付け**: `${CLAUDE_PLUGIN_ROOT}/references/scope-out-policy.md`（プラグイン直下 references）に配置。各スキル・観点別スキル・エージェントから片方向で参照される。

---

## 1. 原則

レビュー指摘・改善提案の中で **別 PR / 別チケット / 別ブランチでの対応を推奨してはならない**。
別 PR 推奨は修正指示のノイズになり、PR 作成者に「結局どこまで本 PR で直すべきか」の判断を強いる。

| 区分 | 行動 |
|------|------|
| 本 PR の仕様・スコープ内の指摘 | **本 PR で対応を求める**。「別 PR で対応してください」とは書かない |
| 本 PR の仕様・当初スコープ外と判断した指摘 | **「スコープ外指摘」として明記** し、本 PR では対応を求めない |
| 「将来検討」「いずれ対応」レベルの観察 | スコープ外指摘の所見として記載（別 PR を求めない・別チケットを起票しない） |

別チケット化・別 PR 起票の判断は、**本 PR 作成者・PdM・プロジェクトリードが行う**。レビュアー（本プラグイン）はその判断を強制しない。

---

## 1.5 PR 外への影響禁止（プラグイン自身の操作制約・MANDATORY）

レビューの **指摘・提案を実行する過程** において、**PR 以外のリソースに影響を与える操作を行ってはならない**。
プラグインが自動的に Work Item / Issue / Boards カード等を作成・変更すると、PR 作成者やプロジェクト管理者の合意なしにバックログを汚染し、追跡不能な作業項目を量産するリスクがある。

### 1.5.1 禁止される操作（例示・包括的）

以下のような **PR の枠を越える書き込み操作** をプラグイン自身が実行することを禁止する。

| 区分 | 禁止される具体例 |
|------|-----------------|
| Issue / Work Item の作成 | GitHub Issues の作成 / Azure DevOps Work Item の作成 / TFS Work Item の作成 / Jira Issue の作成 / Backlog 課題の作成 |
| Issue / Work Item の更新 | 既存 Work Item / Issue のステータス変更・assignee 変更・コメント追加・ラベル付け |
| Boards / カンバン操作 | GitHub Projects のカード追加・移動 / Azure Boards のカード追加・移動 / Jira ボードの操作 |
| 別ブランチ / 別 PR の作成 | レビュー目的で別 PR を起票する / レビュー指摘から派生して別ブランチを切る |
| リポジトリ設定の変更 | ブランチ保護ルールの変更 / Webhook 追加 / コラボレーター追加 |
| 通知・チャット投稿 | Slack / Teams / Discord 等への通知 / メール送信 |
| 外部システムへの登録 | チケット管理システム・タスク管理 SaaS・CRM 等への登録 |
| Wiki / Pages の編集 | リポジトリ Wiki / GitHub Pages / Azure DevOps Wiki への書き込み |

### 1.5.2 許可される操作（PR の枠内）

以下は本プラグインのスコープ内であり、引き続き許可される。

| 区分 | 許可される操作 |
|------|---------------|
| PR 自体への書き込み | PR スレッドへのコメント・インラインコメント投稿 / 既存自著スレッドへの reply / 解消確認時の status 更新（auto-resolve 既定。`auto-resolve=false` 指定時を除く） |
| ローカル git 操作（読み取り中心） | `git fetch` / `git worktree add`（PR ブランチを分離ディレクトリに配置）/ `git diff` / レビュー後の **worktree 削除 or 維持** |
| 外部リソースの **読み取り** | description 内リンクの fetch（`safe-external-fetch.md` のホワイトリスト遵守） / 仕様書ファイルの Read |
| ローカル作業領域への書き込み | `.claude/.local/work/{...}/` 配下のセッションファイル（`work-directory.md` 準拠） |

### 1.5.3 例外（ユーザーの明示要求）

ユーザーが **明示的に** 「このレビュー結果を Work Item にまとめて」「Issue 化して」と指示した場合に限り、**ユーザー確認の上で** 該当する MCP・CLI 経由の操作を実行できる。
ただし以下を遵守すること:

- 操作対象（リポジトリ・プロジェクト・ボード ID）と内容（タイトル・本文・assignee）を **事前にユーザーに提示し承認を得る**
- 失敗時に部分的に作成された Work Item / Issue を残さない（ロールバックまたは状況報告）
- 操作の実行ログを完了報告（`pr-review` Step 8）に明記する

明示要求がない限り、**Work Item / Issue / Boards への書き込みはデフォルトで実行しない**。

### 1.5.4 観点別スキル・エージェントへの適用

観点別スキル（`code-review-implementation` / `code-review-testing` / `code-review-security` / `code-review-architecture` / `code-review-frontend`）と、それらが内部で起動するエージェント（`agents/*.md`）も、本制約に従うこと。

具体的には:

- レビュー指摘を返却するだけでよく、Issue / Work Item を起票しない
- `allowed-tools` に Work Item / Issue 作成系コマンド（`gh issue create` / `az boards work-item create` 等）を **追加しない**
- 観点別スキルのレビュー結果に「Issue を作成しました」「Work Item #123 を起票しました」のような **実行報告を含めない**（実行していないため）

### 1.5.5 完了報告での明示

`pr-review` Step 8 の完了報告には以下を必ず含める:

- 「PR 外のリソース（Work Item / Issue / Boards 等）への書き込みは行っていない」旨の宣言
- 例外的にユーザー要求で実行した場合は、対象リソースと操作内容を明記

## 2. スコープ外と判断する基準

以下のいずれかに該当する場合のみ、レビュー結果から「スコープ外指摘」として分離する。

| 基準 | 例 |
|------|------|
| PR タイトル / 説明 / 仕様書の範囲外 | PR が「ログ機能追加」なのに、無関係な認証モジュールの命名を指摘 |
| 既存実装の課題（PR 差分が触れていない箇所） | PR で触れていない既存ファイルの設計改善 |
| 仕様判断が必要で本 PR の合意済み範囲を超える | 機能仕様の根本変更（PdM 判断必須） |
| 大規模リファクタリングが必要で他多数 PR と競合する | コーディング規約全面適用（別取り組みで実施すべき） |

> **判断基準が曖昧な場合は「対応必須」側に倒す**（false positive を許容）。本 PR で軽微に直せる範囲はスコープ外にしない。

## 3. スコープ外指摘の必須記載項目

スコープ外指摘は **統合サマリの「## 3. スコープ外指摘」セクション** に記載する（テンプレート: `${CLAUDE_PLUGIN_ROOT}/skills/code-review/references/template/output/review-summary.md`）。

各項目で以下を明記する:

| 項目 | 説明 |
|------|------|
| スコープ外と判断した理由 | PR の目的 / 仕様書の範囲 / 既存実装の課題等のいずれに該当するか |
| 該当箇所 | `<ファイルパス>:<開始行>-<終了行>`（参考情報） |
| 提案カテゴリ | 既存技術的負債 / 別機能改善 / 仕様の余地 等 |
| 該当コード（参考） | コードフェンスでスニペットを引用 |
| 所見 | 本 PR では対応しないが、将来検討に値する理由・対応指針 |

### 3.1 記載してよい表現

- 「本 PR のスコープ外と判断したため、本 PR では対応を求めません」
- 「将来的に検討余地のある事項として記録します」
- 「PdM・プロジェクトリードの判断で別取り組みとされる可能性があります」

### 3.2 記載してはならない表現

- ❌ 「別 PR で対応してください」
- ❌ 「別途 PR を起票してください」
- ❌ 「次のスプリントで別チケット化してください」
- ❌ 「以下を別途修正する PR を出してください」
- ❌ 「Issue を作成してください」（PR 作成者・PdM に判断を強制している）

---

## 4. 観点別スキル・エージェントへの適用

観点別スキル（`code-review-implementation` / `code-review-testing` / `code-review-security` / `code-review-architecture` / `code-review-frontend`）と、それらが内部で起動するエージェント定義（`agents/*.md`）は、本ルールに従って指摘を返却すること。

具体的には:

- 指摘・提案の本文に「別 PR」「別チケット」「Issue 起票」などの文言を入れない
- 本 PR スコープ外と判断した指摘は **「スコープ外」フラグ付き** で返却し、オーケストレーターが集計セクションでまとめる
- 「将来検討」レベルの観察は所見として返し、対応を強制しない

## 5. 例: スコープ外指摘の OK / NG

### 5.1 ❌ NG（別 PR 推奨を含む例）

```markdown
### 改善提案 #3

OrderService 全体を Repository パターンに移行すべきです。
別 PR で対応してください。
```

### 5.2 ✅ OK（スコープ外として記載）

```markdown
## 3. スコープ外指摘 （1 件）

### 3-1. OrderService の Repository パターン移行

| 項目 | 内容 |
|---|---|
| スコープ外と判断した理由 | 本 PR は注文確定機能の追加が目的であり、既存 OrderService の設計移行は範囲外。PdM 判断が必要。 |
| 該当箇所 | `src/order/OrderService.cs`（既存実装全体） |
| 提案カテゴリ | アーキテクチャ・既存技術的負債 |

**所見**

注文確定の追加機能とは独立に、OrderService 全体の Repository パターン移行を将来検討する余地があります。本 PR では対応を求めません。
```

## 6. 禁止事項

### 6.1 文言レベルの禁止（レビュー結果本文）

- レビュー結果の本文に「別 PR で対応してください」等の **別 PR 推奨文言** を書くこと
- スコープ外指摘を「対応必須の指摘」セクションに混入させること（本 PR の修正対象を曖昧にする）
- スコープ外と判断した理由を明示せずに分離すること（読み手が判断理由を追跡できない）
- スコープ外指摘でも「いつまでに別 PR を出すべきか」など期限を強制する記載をすること

### 6.2 操作レベルの禁止（PR 外への影響）

- ユーザー明示要求なしで Work Item / Issue / Boards カード等を作成すること
- ユーザー明示要求なしで既存 Work Item / Issue のステータス・assignee・ラベル等を変更すること
- ユーザー明示要求なしで別ブランチ / 別 PR を作成すること
- ユーザー明示要求なしで Slack / Teams / メール等に通知を送信すること
- ユーザー明示要求なしでリポジトリ設定（ブランチ保護・Webhook・権限等）を変更すること
- ユーザー明示要求なしで Wiki / Pages / 外部システムへ書き込みすること
- 観点別スキル・エージェントの `allowed-tools` に Work Item / Issue 作成系コマンドを追加すること

## 7. 適用契約

本ファイルは **プラグイン共通のスコープ外指摘ポリシー** を規定する。
個別スキル・観点別スキル・エージェントは本ファイルの規定に準拠することを宣言したうえで利用する。

本ファイルから個別スキルへの参照は意図的に持たない（共通モジュールがクライアントを知る必要はない）。
利用側スキルは自身の references から本ファイルへ片方向で参照する。
