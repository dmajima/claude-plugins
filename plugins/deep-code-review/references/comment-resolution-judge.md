# 解消判定アルゴリズム（プラグイン共通）

PR の未解決コメントが **コードの最新差分で解消されているか** を自動判定するための **ホスト非依存の判定アルゴリズム**。

> **位置付け**: `pr-review` 配下から **プラグイン共通 references/ に昇格済み**。`safe-external-fetch.md` / `comment-sanitization.md` / `http-error-handling.md` と同様に、複数スキル（pr-review および将来の GitLab / Bitbucket 対応スキル）が片方向で参照する Cross-Cutting Concern として扱う。
>
> **昇格理由**（`${CLAUDE_PLUGIN_ROOT}/references/roadmap.md` セクション 3 の判定基準を満たす）:
> - **Cross-Cutting Concern**: コード差分解析という横断的関心事
> - **複数スキル参照**: pr-review および将来の他 PR ホスト対応スキルから利用される
> - **規則性**: 「規範 + 実装サンプル」の構造でホスト非依存
> - **片方向参照可能**: 共通モジュールが個別スキルを知らない設計が成立

---

## 0. 設計方針（pr-review との責務分離）

本アルゴリズムは「コードの差分解析を行うレビュードメイン」であり、PR I/O アダプタ層（pr-review）の責務外として **共通モジュール** に切り出された。

### 責務分離

| 責務 | 担当 |
|------|------|
| 解消判定アルゴリズム本体（コード修正系/テスト追加系/ドキュメント系） | **本ファイル（プラグイン共通）** |
| ホスト固有の API 呼び出し（スレッド一覧取得・status 更新） | `pr-review` スキル |
| reply 文面のテンプレート（Pattern A/C） | `pr-review/references/re-review-flow.md` セクション 3 |
| 安全方針（auto-resolve 既定 / 自著限定） | `pr-review/references/comment-status-policy.md` |

### インターフェース仕様

呼び出し側（pr-review 等）は以下のシグネチャで本アルゴリズムを実装する:

```
入力:
  - comment_body:  string  (コメント本文)
  - file_path:     string  (例: src/Foo.cs)
  - line:          int     (例: 42)
  - head_sha:      string  (PR の最新 head SHA)
  - diff:          string  (head SHA における該当箇所の git diff)

出力（JSON）:
  {
    "category": "code" | "test" | "doc" | "design" | "question",
    "resolved": true | false,
    "evidence": "<判定根拠の自然言語説明>"
  }
```

### 移譲を行ったメリット

- **GitLab / Bitbucket 対応時のロジック重複なし**: pr-review はホスト I/O、本ファイルはホスト非依存の判定として明確に分離
- **観点別スキル（implementation / testing / documentation）の知見** をそのまま判定に活用できる構造的余地が確保された
- **pr-review が真の「I/O アダプタ層」** となり、SRP に準拠した責務分離が完成

### 互換性

- 現行ユーザーへの API 変更なし（`Skill(skill: "pr-review", args: "<PR-id>")` の入力は不変）
- 結果の reply 文面は `pr-review/references/re-review-flow.md` セクション 3 の 4 パターンテンプレートを継続使用

## 1. 対象とする状態

### 1.1 GitHub

レビュースレッド（`reviewThread`）の `isResolved` フィールド。

| `isResolved` | 解釈 |
|--------------|------|
| `false` | 未解決（active） |
| `true` | 解決済み（resolved） |

操作: `resolveReviewThread` / `unresolveReviewThread` mutation。

### 1.2 Azure DevOps / TFS

Thread の `status` フィールド。

| `status` | 解釈 |
|----------|------|
| `active` | 未解決（active） |
| `pending` | 保留 |
| `fixed` | 解消（コード修正で対応済み） |
| `wontFix` | 対応しない |
| `closed` | クローズ |
| `byDesign` | 仕様どおり（解消扱い） |

操作: PATCH で `{"status": "fixed"}` 等に更新。

未解決 = `active` / `pending`、解消 = `fixed` / `closed` / `byDesign`、保留 = `wontFix`（解消ではない）。

## 2. 解消判定ロジック

未解決コメントが解消済みかを判定する 3 ステップ。

### Step 1: コメント分類

コメント本文を分析して、以下のカテゴリに分類する。

| カテゴリ | 例 | 解消判定方法 |
|---------|------|------------|
| **コード修正系** | 「変数名を変更して」「メソッド分割して」「nullチェック追加して」 | 当該行のコードが変更されているか確認 |
| **テスト追加系** | 「ユニットテストを追加して」「エッジケースのテストが必要」 | 関連テストファイルに該当テストが追加されているか |
| **ドキュメント系** | 「README 更新して」「コメント追加して」 | 該当ドキュメントが更新されているか |
| **設計・仕様系** | 「この設計だと拡張性が低い」「仕様確認して」 | **自動判定不能** → 保守的に未解決のままにする |
| **質問系** | 「これはなぜこうしている？」 | **自動判定不能** → 保守的に未解決のままにする |

### Step 2: 自動判定可能カテゴリの確認

#### コード修正系の判定

1. コメントの `path:line` を取得（GitHub: `path` + `line`、Azure DevOps: `threadContext.filePath` + `rightFileStart.line`）
2. PR の最新 head SHA でその箇所のコードを取得
3. コメント時点のコードと最新コードを比較（コメントの作成時点 SHA は GitHub では `original_commit_id`、Azure DevOps では `pullRequestThreadContext.changeTrackingId` から推定）
4. **行が変更されている** または **対象識別子（変数名・メソッド名）がコメント指摘どおりに変わっている** ことを確認
5. 確認できれば **解消候補** とする

#### テスト追加系の判定

1. コメントから対象メソッド名・クラス名を抽出
2. テストファイルパス（`*Tests*.cs` / `*.test.ts` / `__tests__/` 等）の差分を確認
3. 対象メソッド名を含むテストメソッド（`[Test]` / `it('...', ...)` / `def test_...` 等）が **追加されている** ことを確認
4. 確認できれば **解消候補** とする

#### ドキュメント系の判定

1. コメントから対象ドキュメント（README・CHANGELOG・docs/）を推定
2. 該当ドキュメントの差分を確認
3. **追加・変更されている** ことを確認
4. 確認できれば **解消候補** とする

### Step 3: 保守的な扱い

**判定が曖昧な場合は解消とみなさない**。

- 自動判定が困難なカテゴリ（設計・仕様・質問系）は **触らない**（false negative を許容）
- コード修正系でも、変更内容がコメント指摘と一致していない可能性がある場合は **触らない**
- 確実に解消されたものだけステータスを更新する

## 3. ユーザーへの報告（auto-resolve / dry-run 共通）

ステータス更新したコメントは **必ずユーザーに報告** する。

```markdown
## 未解決コメントの解消確認

### 解消としてステータス更新したコメント（{N}件）
1. `<file>:<line>` — 「<コメント要約>」 → resolved
2. `<file>:<line>` — 「<コメント要約>」 → fixed
...

### 自動判定できず未解決のまま残したコメント（{M}件）
1. `<file>:<line>` — 「<コメント要約>」 → 設計判断系のため自動判定不能
2. `<file>:<line>` — 「<コメント要約>」 → 修正状況が不明瞭
...
```

ユーザーは個別に判断し、必要があれば手動でステータス変更する。

## 4. 判定方針

LLM による解消判定は数値的な確信度ではなく **定性的な根拠** で行う。

| 方針 | 内容 |
|------|------|
| 確信レベル | 「コード差分から解消が明確に確認できる」場合のみ解消候補とする。曖昧な場合は未解決のまま残す |
| 自動判定対象カテゴリ | コード修正系 / テスト追加系 / ドキュメント系 のみ |
| 自動判定除外カテゴリ | 設計判断系 / 質問系 / 仕様確認系（人間判断必須） |

本ファイルは pr-review 配下から **プラグイン共通 references/** に昇格済みで、ホスト非依存の判定アルゴリズムとして確立している。

## 5. 適用契約

本ファイルは **プラグイン共通の解消判定アルゴリズム規範** を規定する。
PR ホスト対応スキル（`pr-review` / 将来の GitLab / Bitbucket 対応スキル）は、本ファイルの規定（カテゴリ分類 / 自動判定対象 / 保守的な扱い / 判定方針）に準拠を宣言したうえで利用すること。

依存方向（共通 references から個別スキルへの参照を持たない一方向）の SSOT は同ディレクトリ `CLAUDE.md`「原則」。

利用例（個別スキル側で参照される想定）:
- PR ホスト対応スキル（pr-review 等）の安全方針・再レビューフロー定義から「解消判定の規範として本ファイルを参照」
- 観点別レビュースキル（implementation / testing / documentation）の判定実装で「カテゴリ分類アルゴリズムを引用」
