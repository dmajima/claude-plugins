# Case 05: last-push.json が無い（基準点なし・存在有無の比較に留める）

## 入力

| 項目 | 値 |
|-----|---|
| 起動フレーズ | "デザインのずれを確認して"（または `/design-status`） |
| 引数 | なし |
| フラグ | なし |
| 既存状態 | 下記「前提の内訳」のとおり |

### 前提の内訳

| 区分 | 内容 |
|-----|------|
| 設定 | `.claude/design-bridge.json` あり。design-system 認可済み |
| 環境 | `jq` あり。venv 構築済み。`.gitignore` に `.claude/.local/` 登録あり |
| `last-push.json` | **存在しない**（このリポジトリからまだ一度も `bridge-push` していない。あるいは状態ディレクトリを手動で削除した） |
| `pending.tsv` | ユニーク 2 件（`mock` の `mocks/S001_login.html` / `mock` の `mocks/S002_home.html`） |
| ローカル `mocksDir` | `_tokens.html`、`S001_login.html`、`S002_home.html` の 3 件 |
| リモート `list_files` の戻り | `foundations/_tokens.html`、`screens/S001_login.html`、`screens/S005_search.html` の 3 件（別の端末または別の利用者が push した可能性がある） |

## 期待動作

### Phase 1: 導入状態と環境の確認

- `.claude/design-bridge.json` を読み、導入済みと判定する（**未導入とは区別する**）
- `jq` / venv / `.gitignore` 登録を確認する。いずれも問題なし

### Phase 2: ローカル側の未反映を集計

- `pending.tsv` を読み、重複排除のうえ種別ごとに集計する（`mock` 2 件）
- `dismissed` は無いため、通知停止の注記は出さない

### Phase 3: リモートとの照合（基準点なし）

1. `last-push.json` を読もうとして不在を検出する → **基準点なし** と判定する
2. `list_files` でリモートのパス一覧を取得する
3. 基準点が無いため「記録されたハッシュとローカル現物のハッシュの比較」は成立しない。照合は **存在有無の比較に留める**
4. `get_file` を呼ばない

`get_file` を呼ばない理由を報告に添える。

- 基準点が無い以上、内容が異なると分かっても **どちらが新しいかを判定できない**
- 記録が無いリモートファイルは全件が「記録なし」に該当するため、そのまま取得すると全件取得になり、トークンと時間を浪費する

### Phase 4: 分類して報告

| パス | 分類 | 根拠 |
|-----|-----|------|
| `mocks/_tokens.html` / `mocks/S001_login.html` | 基準点なし（両側に存在） | 対応するリモートファイルはあるが、新旧を判定できない |
| `mocks/S002_home.html` | ローカルのみ | リモートに対応が無い |
| `screens/S005_search.html` | リモートのみ | ローカルに対応が無い。別経路で追加された可能性 |

- 全体として **基準点が無いためドリフトの方向を判定できない** ことを最初に明示する。「一致」「差分なし」とは報告しない
- 推奨アクションとして、**一度 `bridge-push` を実行して基準点（`last-push.json`）を作る** ことを提案する
- 補足として、`bridge-push` はローカル内容での上書きになるため、リモートのみに存在する `screens/S005_search.html` が意図せず削除候補になりうることを添える。取り込みたい内容が無いかを `bridge-pull` で先に確認する選択肢も示す（いずれもユーザー判断であり、本スキルは実行しない）
- 未反映 2 件（`mock`）の推奨アクションは `bridge-push` である旨も併記する

### Phase 5: 読み取り専用の遵守

- `last-push.json` を **作成しない**（基準点を作るのは `bridge-push` の責務であり、本スキルが空の記録を置いてはならない）
- ローカルファイル・リモートファイルのいずれも変更しない
- `finalize_plan` / `write_files` / `delete_files` を呼ばない
- `pending.tsv` / `block-count` / `dismissed` を削除・変更しない
- `clear_pending.sh` を呼ばない
- 提案した `bridge-push` / `bridge-pull` を勝手に実行しない

## 読み取り専用の検証ポイント

- 実行後も `.claude/.local/plugins/design-bridge/last-push.json` が存在しないこと
- `pending.tsv` / `block-count` / `dismissed` が実行前後で不変であること
- `get_file` の呼び出しが 0 回であること
- 「一致」「ドリフトなし」と誤って報告していないこと

## 分岐の根拠

このケースが分岐するトリガーは `last-push.json` の存在 = なし である。SKILL.md 実行フロー 3 の「`last-push.json` を読む（無ければ「基準点なし」として、照合は存在有無の比較に留める）」、および分類表の「基準点なし: `last-push.json` が無く、どちらが新しいか判定できない → 一度 `bridge-push` して基準点を作る」に対応する。

`DesignSync` にはリモート変更の通知機構が無いため、`last-push.json` が唯一の比較基準である。これが欠けている状態では、内容を取得しても「違う」ことしか分からず、「どちらが新しいか」は決められない。したがって全件取得に走らず、判定不能であることを正直に報告し、基準点を作る操作へ誘導するのが正しい振る舞いになる。

## エッジケース

| 状況 | 動作 |
|-----|------|
| `last-push.json` はあるが JSON として壊れている | 基準点なしとして扱い、本ケースと同じ経路をとる。壊れている旨も報告する |
| `last-push.json` の `projectId` が設定の `projectId` と異なる | 基準点として使えないため基準点なしとして扱い、紐付けが変わった可能性を報告する |
| 基準点なしかつリモートが空 | ローカルのモックを全件「ローカルのみ」と分類し、`bridge-push` を提案する |
| 基準点なしで `--local` 指定 | 手順 3 を飛ばすため基準点の有無に触れない（出力は `case-02_local_only.md` と同じ形になる） |
