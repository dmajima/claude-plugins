# Case 02: `--local` 指定（ローカル情報のみ・リモート照合なし）

## 入力

| 項目 | 値 |
|-----|---|
| 起動フレーズ | "/design-status --local"（自然言語なら「ローカルだけでいいので未反映を見せて」） |
| 引数 | `--local` |
| フラグ | `--local` |
| 既存状態 | 下記「前提の内訳」のとおり |

### 前提の内訳

| 区分 | 内容 |
|-----|------|
| 設定 | `.claude/design-bridge.json` あり（導入済み） |
| 環境 | `jq` は **未導入**。`.claude/.local/plugins/design-bridge/.venv` は **未構築**。`.gitignore` に `.claude/.local/` の登録 **あり** |
| `pending.tsv` | 物理 4 行・ユニーク 3 件（`mock` 2 件 / `spec` 1 件）。うち 1 行は同じパスの重複 |
| `block-count` | 不在 |
| `dismissed` | あり（上限到達により通知が止まっている） |
| ユーザースコープ設定 | `~/.claude/.local/plugins/design-bridge/user-config.json` なし（`blockLimit` は既定の 3） |

`pending.tsv` の実体は次のとおり（`<kind>` と相対パスを TAB で区切る）。

```text
mock	mocks/S001_login.html
spec	specs/screens/S002_home.md
mock	mocks/S004_report.html
mock	mocks/S001_login.html
```

## 期待動作

### Phase 1: 導入状態と環境の確認

- `.claude/design-bridge.json` を読み、導入済みと判定する
- リモート照合を行わないため `projectId` は参照しない
- 環境の健全性を確認し、保護が効いていない点を報告対象に加える。この確認は `--local` でも省略しない（手順 3 のみがスキップ対象である）

| 確認 | 本ケースの結果 | 報告する意味 |
|-----|--------------|------------|
| `jq` の有無 | 無し | `watch` 設定が読めず、既定の監視対象（`specs` の `.md` / `mocks` の `.html`）に縮退している |
| `.venv` の有無 | 無し | `bridge-push` のスクリーンショット生成が動かない。`bridge-init` の venv 構築を案内する |
| `.gitignore` の `.claude/.local/` 登録 | あり | 問題なし（登録が無い場合は状態ファイルがコミットされる恐れを報告する） |

### Phase 2: ローカル側の未反映を集計

- `.claude/.local/plugins/design-bridge/pending.tsv` を読み、`<kind>` と相対パスに分解する
- 重複は `sort -u` 相当で排除する。物理 4 行に対して報告はユニーク 3 件とする
- 空行は件数に数えない
- 種別ごとに件数とパスを集計し、推奨アクションを添える

| 種別 | 件数 | 推奨アクション |
|-----|-----|--------------|
| `mock` | 2 | `bridge-push` |
| `spec` | 1 | `bridge-mock` で再生成、または変更不要なら `bridge-push` |

- `block-count` と `dismissed` を読む。`dismissed` があるため、**上限到達により Stop フックの通知が止まっている**（内容が変わるまで再通知されない）ことを報告する

### Phase 3: リモート照合のスキップ

- `--local` 指定のため、SKILL.md 実行フロー手順 3 を丸ごと飛ばす
- `last-push.json` を読まない（手順 3 の 1 番目に属するため）
- `list_files` を呼ばない
- `get_file` を呼ばない
- 認可状態の確認も行わない（未認可でも結果は変わらない）

### Phase 4: 報告

- 未反映パスの一覧とユニーク件数（3 件）を種別付きで提示する
- 通知が止まっている旨と、その意味（未反映は残っているが Stop フックは応答終了をブロックしない）を伝える
- 環境の健全性で問題があった 2 点（`jq` 未導入・venv 未構築）を提示する
- **リモート照合を行っていないため、リモート先行・リモートのみ・一致・基準点の有無はいずれも未確認である** ことを明示する（照合したい場合は `--local` なしでの再実行を案内する）

### Phase 5: 読み取り専用の遵守

- `pending.tsv` を削除・更新しない（重複行の排除は報告上の集計であって、ファイルの書き換えではない）
- `block-count` / `dismissed` を削除・リセットしない（カウンタ操作は Stop フックと `bridge-push` の責務）
- `clear_pending.sh` を呼ばない
- venv を構築しない。`jq` を導入しない。`.gitignore` を編集しない（いずれも案内に留める）

## 期待出力

| 項目 | 期待値 |
|-----|-------|
| 生成ファイル | なし |
| 変更ファイル | なし |
| 削除ファイル | なし（`pending.tsv` / `dismissed` とも残存） |
| DesignSync 呼び出し | なし |
| 標準出力（要約） | 「未反映: 3 件（mock 2 / spec 1）」＋種別付きパス一覧 / 「上限到達により通知が止まっています」 / 「`jq` 未導入のため監視対象が既定へ縮退しています」 / 「venv 未構築のため `bridge-push` のスクリーンショット生成が動きません」 / 「リモート照合は未実施（`--local`）」 |
| 終了状態 | 成功（ローカル情報のみ・照合は意図的に未実施） |

## 読み取り専用の検証ポイント

- 実行後も `pending.tsv` の内容・行数（物理 4 行）が変わっていないこと
- 実行後も `dismissed` が残っていること
- `.venv` が作られていないこと
- ネットワーク呼び出し（`list_files` / `get_file`）が 0 件であること

## 分岐の根拠

このケースが分岐するトリガーは `--local` = 指定あり である。SKILL.md「実行モード判定」の 1 行目、および「実行フロー」手順 3 冒頭の「`--local` 指定時はこの手順を飛ばす」に対応する。スキップされるのは手順 3 だけであり、手順 1 の環境健全性チェックと手順 2 のローカル集計は通常どおり実施される。

## エッジケース

| 状況 | 動作 |
|-----|------|
| `pending.tsv` が不在または空 | 「未反映はありません」と報告する。照合は行わないため、それ以上の調査もしない |
| `dismissed` が不在 | 通知が止まっている旨の注記は出さない。`block-count` があれば現在値のみ報告する |
| `dismissed` はあるが `pending.tsv` の内容がその後変わっている | `dismissed` の存在は事実として報告する。ハッシュ一致による再通知可否の判定は Stop フックの責務であり、bridge-status は状態の提示に留める |
| 環境の健全性に問題が無い | 3 項目とも問題なしとして簡潔に報告する（省略してもよいが、`--local` でもチェック自体は行う） |
