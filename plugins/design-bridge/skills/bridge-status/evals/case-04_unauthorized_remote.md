# Case 04: 未認可（リモート照合不可・ローカル情報のみ報告）

## 入力

| 項目 | 値 |
|-----|---|
| 起動フレーズ | "同期状況を見せて"（または `/design-status`） |
| 引数 | なし |
| フラグ | なし |
| 既存状態 | 導入済み（`.claude/design-bridge.json` あり）。`/design-login` による design-system 認可が未実施、または認可が失効している。環境は健全（`jq` あり・venv あり・`.gitignore` 登録あり）。`pending.tsv` はユニーク 2 件（`mock` 1 / `spec` 1）。`last-push.json` あり（記録 5 件。うち 1 件はローカル現物と食い違う） |

## 期待動作

### Phase 1: 導入状態と環境の確認

- `.claude/design-bridge.json` を読み、導入済みと判定して続行する（**未導入とは区別する**）
- `jq` / venv / `.gitignore` 登録を確認する。いずれも問題なし

### Phase 2: ローカル側の未反映を集計

- `pending.tsv` から未反映のパス一覧を得て、重複排除のうえ種別ごとに集計する（`mock` 1 件 / `spec` 1 件）
- `block-count` / `dismissed` を読み、通知が止まっているかを確認する（本ケースでは `dismissed` 無し）

### Phase 3: リモート照合の試行と失敗

1. `last-push.json` を読む。これはローカルファイルの読み出しであり、認可を要しない
2. `--local` 指定が無いため照合を試み、`list_files` を呼ぶ
3. **認可エラーで失敗する**

失敗後の振る舞いは次のとおり。

| 項目 | 動作 |
|-----|------|
| リトライ | 繰り返さない。認可はスキル側で自動解決できない |
| `get_file` | 呼ばない（照合対象を確定できないため） |
| 認可の取得 | 代行しない（ログイン操作を肩代わりしない） |
| オフラインで分かる範囲 | `last-push.json` の記録とローカル現物のハッシュ比較は実施できるため、基準点の有無・最終 push 日時・記録と食い違うローカルファイル（1 件）までは報告する |

### Phase 4: ローカル情報のみで報告

- 未反映パスの一覧と件数を種別付きで提示する
- **リモート照合ができなかったこと** と、その理由（design-system 認可が無い）を明示する
- リモート先行・リモートのみ・一致の各分類は **未確認** であることを明示する。**「ドリフトなし」とは言わない**
- 記録と食い違うローカルファイル 1 件は「ローカル先行の候補」として提示してよいが、リモート側が同じファイルを更新していないことは確認できていない旨を添える
- `/design-login` による認可を案内し、認可後の再実行を促す
- ローカル先行・ローカルのみについては、ローカル情報の範囲で `bridge-push` を提案してよい

### Phase 5: 読み取り専用の遵守

- 照合失敗を理由に `pending.tsv` / `block-count` / `dismissed` / `last-push.json` を削除・更新しない
- 書き込み系 DesignSync（`finalize_plan` / `write_files` / `delete_files`）を呼ばない
- `clear_pending.sh` を呼ばない
- 認可を取得する操作を勝手に行わない

## 期待出力

| 項目 | 期待値 |
|-----|-------|
| 生成ファイル | なし |
| 変更ファイル | なし |
| 削除ファイル | なし（`pending.tsv` / `last-push.json` とも残存） |
| DesignSync 呼び出し | `list_files` を 1 回試行して失敗。`get_file` および書き込み系は 0 件 |
| 標準出力（要約） | 「未反映: 2 件（mock 1 / spec 1）」＋パス一覧 / 「リモート照合はできませんでした（design-system 未認可）」 / 「リモート先行・リモートのみ・一致は未確認です」 / 「基準点あり（最終 push: <日時>）。記録と食い違うローカルファイル 1 件」 / 「`/design-login` で認可後に再実行してください」 |
| 終了状態 | 部分完了（ローカル情報のみ報告・リモート照合は未実施） |

## 読み取り専用の検証ポイント

- 失敗パスでも `pending.tsv` / `block-count` / `dismissed` / `last-push.json` が残っていること（エラー処理に便乗した削除をしない）
- `git status --porcelain` が実行前後で不変であること
- 認可失敗を「ドリフトなし」「一致」と誤って報告していないこと

## 分岐の根拠

このケースが分岐するトリガーは design-system 認可 = 未完了 である。SKILL.md「前提」2 の「リモート照合を行う場合は design-system 認可が済んでいること（未認可ならローカル側の情報のみ報告する）」に対応する。

bridge-status は読み取り専用スキルであるため、認可が無くても中断せず、分かる範囲を報告して終わる。書き込みを伴う `bridge-pull` が認可エラーで中断する（`bridge-pull` の case-06）のとは扱いが異なる。ただし「分かる範囲」を超えて断定しないことが本ケースの要点であり、未確認の分類を「差分なし」と丸めてはならない。

## エッジケース

| 状況 | 動作 |
|-----|------|
| `--local` が併用されている | そもそも照合を試みないため認可の有無は結果に影響しない（出力は `case-02_local_only.md` と同じになる） |
| `list_files` が認可以外の理由で失敗（ネットワーク断・一時障害等） | 同様にローカル情報のみで報告し、失敗理由を添える。未反映記録は保持する |
| `projectId` に対応するプロジェクトがリモートに存在しない | 照合不能として報告し、`bridge-init` での紐付け見直しを案内する |
| 認可はあるが `list_files` が空を返す | 認可エラーではないため `case-03_full_drift_check.md` の「リモートにファイルが 1 件も無い」エッジケースとして扱う |
| 未認可かつ `last-push.json` も無い | 基準点なしとして報告する（`case-05_no_baseline.md`）。このときオフライン比較の材料も無いため、報告は未反映一覧と環境健全性のみになる |
