# Case 06: 認可エラー（ローカルを一切変更せず /design-login を案内して中断）

## 入力

| 項目 | 値 |
|-----|---|
| 起動フレーズ | 「Claude Design の変更を取り込んで」 |
| 引数 | なし |
| フラグ | なし（対話モード） |
| 既存状態 | `.claude/design-bridge.json` あり。`/design-login` による design-system 認可が未実施、または認可が失効している。作業ツリーはクリーン。`last-push.json` あり。`pending.tsv` に `mock` 1 行 |

## 期待動作

### Phase 1: 明示指示の確認

- 取り込み方向が明示されているため、方向確認には分岐せず実行に進む

### Phase 2: 作業ツリーの確認

- `git status` を確認する。`mocksDir` 配下に未コミット変更が無いため警告せず続行する
- この時点までに行うのはローカルの読み取りのみで、書き込みは発生していない

### Phase 3: 照合の試行と認可エラー（本ケースの中心）

1. `last-push.json` を読み、基準点を得る（ローカルファイルの読み出しであり、認可を要しない）
2. `list_files` を呼ぶ
3. **認可エラーが返る**

認可エラーを検出した時点で、次のとおり振る舞う。

| 項目 | 動作 |
|-----|------|
| 後続処理 | `get_file` へ進まない（照合対象を確定できない） |
| リトライ | 繰り返さない。認可はスキル側で自動解決できない |
| 認可の代行 | 行わない（ログイン操作をスキルが肩代わりしない） |
| ローカルファイル | モック HTML・設計書・スクリーンショットのいずれも作成・更新・削除しない |
| 状態ファイル | `pending.tsv` / `block-count` / `dismissed` / `last-push.json` を変更しない |
| `clear_pending.sh` | 呼ばない |
| 部分適用 | 行わない。「一部だけ取り込んで残りは次回」という中途半端な状態を作らない |

### Phase 4 以降: 実施しない

- 差分の提示・`AskUserQuestion` による承認・書き戻し・整合の取り直しのいずれも実施しない

### 報告

- design-system の認可が無いためリモートと照合できなかったことを報告する
- `/design-login` による認可を案内し、認可後の再実行を促す
- **ローカルには一切変更を加えていない** ことを明示する
- 未反映記録はそのまま残っており、`bridge-push` の対象として生きていることを添える
- 変更せずに状態だけ確認したい場合は `bridge-status` を案内してよい（未認可でもローカル側の情報は報告できる）

## 期待出力

| 項目 | 期待値 |
|-----|-------|
| ユーザへの確認 | なし（`AskUserQuestion` を発火しない。確認する対象が確定していない） |
| `DesignSync` 呼び出し | `list_files` を 1 回試行して失敗。`get_file` および書き込み系は 0 件 |
| 生成・更新・削除ファイル | なし |
| 状態ファイル | `pending.tsv` / `block-count` / `dismissed` / `last-push.json` とも実行前後で不変 |
| 標準出力（要約） | 「design-system の認可がないため取り込めません」「`/design-login` で認可してから再実行してください」「ローカルには変更を加えていません」 |
| 終了状態 | 中断（失敗。ただしローカルは健全） |

## 検証ポイント

- 実行前後で `git status --porcelain` が変化しないこと
- 実行前後で `.claude/.local/plugins/design-bridge/` 配下のファイル一覧とタイムスタンプが変化しないこと
- 認可エラーを「リモートに差分なし」と誤って報告していないこと

## 分岐の根拠

このケースが分岐するトリガーは `DesignSync` の応答 = 認可エラー である。SKILL.md の前提 3「design-system 認可が済んでいること。認可エラー時は `/design-login` を案内して中断し、ローカルは一切変更しない」、および重要な制約「認可エラー・承認拒否のときはローカルを一切変更しない」に対応する。

bridge-pull はローカル正本を書き換える例外操作であるため、照合が完了していない状態で部分的に書き戻すと、「どこまでリモートを反映したのか分からないローカル」が残る。読み取り専用の `bridge-status` が未認可でもローカル情報のみ報告して続行するのに対し、bridge-pull が中断するのはこの違いによる。
