# Case 02: `--local` 指定（ローカルの未反映一覧のみ・リモート照合なし）

## 入力

| 項目 | 値 |
|-----|---|
| 起動フレーズ | "/design-status --local"（自然言語なら「ローカルだけでいいので未反映を見せて」） |
| 引数 | `--local` |
| フラグ | `--local` |
| 既存状態 | 導入済み（`.claude/design-bridge.json` あり、`blockLimit` は未設定＝既定 3）。`pending.txt` に 3 行。`block-count` の値が `3`（上限到達） |

## 期待動作

### Phase 1: 導入状態の確認
- `.claude/design-bridge.json` を読み、導入済みと判定する
- リモート照合を行わないため `projectId` は参照しない

### Phase 2: ローカル側の未反映を集計
- `.claude/.local/plugins/design-bridge/pending.txt` を読み、未反映のパス一覧と件数を得る
- 空行は件数に数えない
- `.claude/.local/plugins/design-bridge/block-count` を読み、連続ブロック回数を得る

### Phase 3: リモート照合のスキップ
- `--local` 指定のため、SKILL.md 実行フロー手順 3 を丸ごと飛ばす
- `list_files` を呼ばない
- `get_file` を呼ばない
- 認可状態の確認も行わない（未認可でも結果は変わらない）

### Phase 4: 報告
- 未反映パスの一覧と件数（3 件）を提示する
- 連続ブロック回数が上限（3 回）に達しており、Stop フックが次回の応答終了を許可する状態である旨を併せて伝える
- 未反映に対する推奨アクションとして `design-push` を提案する
- **リモート照合を行っていないため、リモート先行・リモートのみは未確認である** ことを明示する（全件照合したい場合は `--local` なしでの再実行を案内する）

### Phase 5: 読み取り専用の遵守
- `pending.txt` を削除・更新しない
- `block-count` を削除・リセットしない（上限到達の表示は報告のみで、カウンタ操作は Stop フックと `design-push` の責務）

## 期待出力

| 項目 | 期待値 |
|-----|-------|
| 生成ファイル | なし |
| 変更ファイル | なし |
| 削除ファイル | なし（`pending.txt` / `block-count` とも残存） |
| DesignSync 呼び出し | なし |
| 標準出力（要約） | 「未反映: 3 件」＋パス一覧 / 「連続ブロック 3 回（上限 3 回）: 次回の応答終了は許可されます」 / 「リモート照合は未実施（`--local`）」 / 「`design-push` で反映できます」 |
| 終了状態 | 成功（ローカル情報のみ・照合は意図的に未実施） |

## 読み取り専用の検証ポイント

- 実行後も `.claude/.local/plugins/design-bridge/pending.txt` の内容・行数が変わっていないこと
- 実行後も `.claude/.local/plugins/design-bridge/block-count` が `3` のままであること
- ネットワーク呼び出し（`list_files` / `get_file`）が 0 件であること

## 分岐の根拠

このケースが分岐するトリガーは `--local` = 指定あり である。SKILL.md「実行モード判定」の 1 行目、および「実行フロー」手順 3 冒頭の「`--local` 指定時はこの手順を飛ばす」に対応する。

## エッジケース

| 状況 | 動作 |
|-----|------|
| `pending.txt` が不在または空 | 「未反映はありません」と報告する。照合は行わないため、それ以上の調査もしない |
| `block-count` が不在 | 連続ブロック 0 回として扱い、上限到達の注記は出さない |
| `block-count` が上限未満（例: `1`） | 「連続ブロック 1 回（上限 3 回）」と現在値のみ報告し、「次回通過を許可する状態」とは言わない |
| `blockLimit` が設定に無い | 既定値 3 で判定する |
