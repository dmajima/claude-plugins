# Case 05: push 失敗（pending.txt を削除しない）

## 入力

| 項目 | 値 |
|-----|---|
| 起動フレーズ | 「Claude Design に反映して」 |
| 引数 | なし |
| フラグ | なし（対話モード） |
| 既存状態 | `.claude/design-bridge.json` あり。認可済み・venv 構築済み。`pending.txt` に 3 件。`get_project` と `list_files` は成功し計画も確定するが、`write_files` がエラーを返す（ネットワーク断・サイズ超過・一時的な拒否などを想定） |

## 期待動作

### Phase 1-4: 対象決定からバンドル作成まで
- case-01 と同様に進行する。スクリーンショットの再生成、設計書の画面イメージ更新、バンドル作成までは正常に完了する
- この時点ではローカル側の成果物（スクショ・設計書）は更新済みだが、Claude Design への反映はまだ行われていない

### Phase 5: DesignSync による push（失敗）
- `get_project` → `list_files` → 計画提示 → `finalize_plan` までは成功し `planId` を得る
- `write_files` がエラーを返す
- エラー内容（どのファイルが送れなかったか）を把握する
- 一部のファイルだけ成功している場合は、成功したパスと失敗したパスを区別する

### Phase 6: 未反映記録のクリアを行わない（本ケースの中心）
- **`pending.txt` を削除しない**
- **`block-count` を削除しない**
- 完全失敗の場合は `pending.txt` を一切変更しない
- 一部成功の場合のみ、`pending.txt` から **成功したエントリだけ** を取り除く。失敗したエントリは必ず残す
- 不変条件: 反映が確認できていないパスは、いかなる場合も `pending.txt` に残る

### Phase 7: 報告
- push が失敗したことと、失敗したファイル一覧を明示する
- 未反映のまま残っていること、Stop フックが再度ブロックしうることを伝える
- 原因に応じた再実行（同一 `planId` での分割送信、時間をおいての再試行など）を案内する
- 「反映しました」という成功報告は行わない

## 期待出力

| 項目 | 期待値 |
|-----|-------|
| 残存ファイル | `.claude/.local/plugins/design-bridge/pending.txt`（失敗分のエントリを保持したまま存在する） |
| 残存ファイル | `.claude/.local/plugins/design-bridge/block-count`（存在していれば削除されない） |
| 標準出力（要約） | push 失敗の明示、失敗ファイル一覧、未反映のまま残っている旨 |
| 終了状態 | 失敗（完全失敗）または部分完了（一部成功時）。成功とは報告しない |
| 後続の挙動 | 次の応答終了時に Stop フックが再度ブロックしうる（`blockLimit` まで） |

## 分岐の根拠

このケースが分岐するトリガーは `write_files` の結果 = 失敗 である。SKILL.md の「push が失敗した場合は削除しない（未反映のまま Stop フックで再度ブロックさせる）」および procedures.md の「push が完全に成功した場合にのみ `pending.txt` と `block-count` を削除する」に基づく。

これは design-push における **最重要の安全性要件** である。失敗時に記録を消すと、未反映の変更が Stop フックに検出されなくなり、「反映済みのつもりで未反映」という design-bridge が防ごうとしている状態そのものを作り出してしまう。
