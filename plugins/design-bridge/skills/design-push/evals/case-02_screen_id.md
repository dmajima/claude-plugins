# Case 02: 画面 ID 指定（非対話モード・対象限定）

## 入力

| 項目 | 値 |
|-----|---|
| 起動フレーズ | 「S002_home だけ Claude Design に反映して」 |
| 引数 | `S002_home` |
| フラグ | なし（引数指定により非対話モード） |
| 既存状態 | `.claude/design-bridge.json` あり。認可済み・venv 構築済み。`pending.txt` には `S001_login` と `S002_home` の両方が記録されているが、ユーザーは後者だけを指定している |

## 期待動作

### Phase 1: 導入確認と対象決定
- 引数で画面 ID が指定されているため、実行モード判定表により非対話モードとして進行する
- 対象決定表により、対象は `S002_home` の設計書・モックのみとする。`pending.txt` の他のエントリ（`S001_login`）は対象に含めない

### Phase 2: スクリーンショットの再生成
- `capture.py` を `--only S002_home` 付きで `Bash` ツール経由で起動する
- 対象外の画面のスクリーンショットは再生成しない

### Phase 3: Markdown の画面イメージ更新
- `S002_home` の設計書の画面イメージセクションのみ更新する
- `S001_login` の設計書には触れない

### Phase 4: バンドルの作成
- バンドルを作り直し、`screens/S002_home.html` のみを配置する
- `@dsCard` マーカーが無ければ付与する

### Phase 5: DesignSync による push
- `get_project` → `list_files` の順で読み取り、追加 / 更新 / 削除を判定する
- **非対話モードでも push 計画の提示は省略しない。** 対象 1 件の計画を提示する
- `finalize_plan` → `write_files`（`localPath` 指定）の順で送る

### Phase 6: 未反映記録の部分クリア
- `S002_home` に対応するエントリのみを `pending.txt` から削除する
- `S001_login` のエントリは未反映のまま残すため、`pending.txt` 自体は削除しない
- `pending.txt` が非空のまま残るため `block-count` も削除しない

### Phase 7: 報告
- 反映したカード（`screens/S002_home.html`）と、未反映のまま残った対象（`S001_login`）を明示する
- 残りを反映するには引数なしで再実行するよう案内する

## 期待出力

| 項目 | 期待値 |
|-----|-------|
| ユーザへの確認 | push 計画の提示（非対話モードでも省略しない） |
| 生成ファイル | `specs/assets/S002_home.png`、バンドル内 `screens/S002_home.html` |
| 更新ファイル | `S002_home` の設計書の画面イメージセクションのみ |
| 残存ファイル | `pending.txt`（`S001_login` のエントリが残る） |
| 標準出力（要約） | 反映 1 件と、未反映として残った 1 件の明示 |
| 終了状態 | 成功（部分反映） |

## 分岐の根拠

このケースが分岐するトリガーは 引数 = 画面 ID である。実行モード判定表の「引数で対象を指定」に該当して非対話モードになり、対象決定表の「引数で画面 ID 指定」に該当して対象が当該画面に限定される。対象外のエントリが `pending.txt` に残るため、Phase 6 は全削除ではなく部分削除になる。
