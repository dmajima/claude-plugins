# Case 02: トンマナ・基礎レイアウト未整備（雛形生成の可否を確認）

## 入力

| 項目 | 値 |
|-----|---|
| 起動フレーズ | 「ログイン画面のモックを作って」 |
| 引数 | なし |
| フラグ | なし |
| 既存状態 | `.claude/design-bridge.json` あり。`specsDir` に `S001_login.md` あり。`mocksDir/_tokens.html` と `mocksDir/_layout.html` が両方とも無い |

## 期待動作

### Phase 1: 対象の決定
- 対象画面が引数で指定されていないため、対話で対象画面を確認する
- `specsDir` の設計書一覧をもとに `S001_login` を対象として確定する

### Phase 2: 基盤の確認
- `_tokens.html` と `_layout.html` が無いことを検出する
- 先にトンマナと基礎レイアウトを生成してよいかユーザに確認する
- 承認された場合、`mocksDir/_tokens.html`（色・タイポグラフィ・余白・コンポーネント定義）と `mocksDir/_layout.html`（全画面共通の骨格）の雛形を生成する
- 拒否された場合は画面モックを生成せず、基盤の用意が必要である旨を案内して終了する

### Phase 3〜4: 設計書の読み取りとモック生成
- 生成した雛形のトークンを参照して `mocksDir/S001_login.html` を生成する
- 画面ごとに独自の色やサイズを導入しない
- 先頭行に `<!-- @dsCard group="画面" -->` を置き、外部 CDN への参照を含めない

### Phase 5: 未反映としての記録
- 生成した 3 ファイル（`_tokens.html` / `_layout.html` / `S001_login.html`）は、いずれも `mocksDir` 配下の `.html` であるため、PostToolUse フックが `pending.tsv` に `mock` 種別で記録する
- スキルは `pending.tsv` を直接編集しない

### Phase 6: 報告
- 雛形として生成したトンマナ・レイアウトは暫定である旨と、仮置きした箇所を報告する
- `design-push` での反映を案内する

## 期待出力

| 項目 | 期待値 |
|-----|-------|
| 生成ファイル | `<mocksDir>/_tokens.html`、`<mocksDir>/_layout.html`、`<mocksDir>/S001_login.html`（いずれも承認時） |
| 未反映記録 | `pending.tsv` に `mock` 種別の行が 3 件追記される（書き手は PostToolUse フック） |
| 標準出力（要約） | 基盤が未整備であった旨、生成した雛形の内容概要、画面モックの生成結果、雛形が暫定であること、仮置きした箇所、`design-push` での反映案内 |
| 終了状態 | 成功（雛形生成を拒否された場合は未生成で終了） |

## 禁止事項（このケースで起きてはならないこと）

- 確認なしに `_tokens.html` / `_layout.html` を生成すること
- 基盤が無いまま画面モックだけを生成し、画面固有のスタイルを直接書き込むこと
- 雛形が暫定であることを報告せずに完了扱いにすること
- `pending.tsv` を直接編集すること

## 分岐の根拠

このケースが分岐するトリガーは「実行フロー 2 の基盤確認 = `_tokens.html` と `_layout.html` が無い」である。基盤が無い状態で画面モックを作ると、画面ごとに独自スタイルが生まれ、重要な制約「トンマナを無視した独自スタイルを画面モックに持ち込まない」に反するため、先に基盤生成の可否を確認する経路に入る。

実行フロー 2 の確認は実行モードで条件付けられていない。したがって画面 ID を引数で指定した非対話起動（case-01 の入力形）であっても、基盤が欠けていればこの確認は同じく入る。非対話になるのは対象画面の決定（Phase 1）までであり、基盤生成の可否は確認を省略できない。

一方、`--tokens` / `--layout` による単体指定は雛形生成そのものを目的とする別経路で、確認を挟まず画面モック生成へも進まない（case-05）。
