# Case 05: `--tokens` 単体指定（トンマナ雛形のみ生成）

## 入力

| 項目 | 値 |
|-----|---|
| 起動フレーズ | `/design-mock --tokens` |
| 引数 | なし（画面 ID を指定しない） |
| フラグ | `--tokens` |
| 既存状態 | `.claude/design-bridge.json` あり。`mocksDir/_tokens.html` が無い。`specsDir` の設計書の有無は問わない（トンマナ生成時は前提 2 の対象外） |

## 期待動作

### Phase 1: 対象の決定
- 実行モード判定表の `--tokens` 行に従い **非対話** として扱う
- 対象画面を決めない。画面モック生成へ進まないため、`specsDir` の設計書は参照しない
- 設計書が無くても中断しない（前提 2 の但し書き「トンマナ生成時は不要」）

### Phase 2: 雛形の生成
- `mocksDir/_tokens.html` が無いことを確認し、トンマナの雛形を生成する
- 生成内容は色・タイポグラフィ・余白・コンポーネント定義のトークン群とする
- 非対話のため、生成の可否をユーザに確認しない
- `--tokens` はトンマナのみを対象とするため、`_layout.html` は生成しない（基礎レイアウトは `--layout`）

### Phase 3: 画面モックの生成
- **実行しない。** `--tokens` は雛形のみを生成し、画面モック生成へは進まない

### Phase 4: 未反映としての記録
- 生成した `_tokens.html` は `mocksDir` 配下の `.html` であるため、PostToolUse フックが `pending.tsv` に `mock` 種別で記録する
- スキルは `pending.tsv` を直接編集しない

### Phase 5: 報告
- 生成した雛形のパスと内容概要、雛形が暫定である旨を提示する
- 次のアクションとして、基礎レイアウトが必要なら `--layout`、画面モックが必要なら画面 ID 指定での実行、反映は `design-push` であることを案内する

## 期待出力

| 項目 | 期待値 |
|-----|-------|
| 生成ファイル | `<mocksDir>/_tokens.html` のみ |
| 生成しないもの | `<mocksDir>/_layout.html`、画面モック HTML |
| 未反映記録 | `pending.tsv` に `mock` 種別の行が 1 件追記される（書き手は PostToolUse フック） |
| 標準出力（要約） | 生成した雛形のパスと内容概要、暫定である旨、次のアクション（`--layout` / 画面 ID 指定 / `design-push`） |
| 終了状態 | 成功 |

## 禁止事項（このケースで起きてはならないこと）

- `--tokens` 指定にもかかわらず画面モックまで生成すること
- `--tokens` 指定で `_layout.html` まで併せて生成すること
- 非対話経路で生成の可否を `AskUserQuestion` で確認すること
- 既存の `_tokens.html` がある場合に無確認で上書きすること（本ケースの前提では不在だが、存在する場合は case-03 と同じく確認が必要）
- 設計書が無いことを理由に中断すること（前提 2 はトンマナ生成時には適用されない）

## 分岐の根拠

このケースが分岐するトリガーは「実行モード判定 = `--tokens`」である。判定表はこのフラグを非対話に分類し、「トンマナ / 基礎レイアウトの雛形のみを生成し、画面モック生成へは進まない」と定めている。`--layout` 単体指定も同じ構造で、生成対象が `_layout.html` に変わるだけである。

case-02 との違いは 2 点ある。case-02 は画面モック生成の途中で基盤欠如を検出する経路のため、生成の可否を確認したうえで雛形を作り、そのまま画面モック生成へ続行する。本ケースはフラグによって雛形生成そのものが目的となるため、確認を挟まず、続行もしない。
