# test-review 判定基準・指摘統合規則

`test-review` スキルの指摘重要度の定義・PASS / NEEDS REVISION 判定基準・指摘統合規則の定義場所。
欠陥重要度（defect.severity = 本番影響度）の SSOT は `${CLAUDE_PLUGIN_ROOT}/references/severity-policy.md`。本書の「指摘重要度」とは**別概念**である（1.1 章）。

---

## 1. 指摘重要度（Critical / High / Medium / Low）

### 1.1 欠陥 severity との区別（重要）

| 概念 | 対象 | 定義場所 |
|------|------|---------|
| **指摘重要度**（本書） | test-review が出すレビュー指摘の**対応必要度**（成果物・実績記録の欠陥ではなく、テスト成果物の問題の重さ） | 本ファイル 1.2 章 |
| **欠陥 severity** | テスト実行で検出した欠陥（status: fail の defect）の**本番影響度** | `severity-policy.md`（本書には複製しない） |

- 結果文脈で「severity 妥当性」を検証する際の判定基準は severity-policy.md を参照。その検証結果として出す指摘（「severity が過小」等）の重さは本書の指摘重要度で表す

### 1.2 指摘重要度の定義

| 重要度 | 定義（この指摘を放置した場合に起きること） | 例（設計文脈） | 例（結果文脈） |
|--------|------------------------------------------|---------------|---------------|
| `Critical` | そのまま実行・報告すると、誤った結果・環境破壊・重大な見落としが**確定的に**発生する | 破壊的操作（データ削除等）が preconditions / steps に未明示 / 要件の主要機能が全くケース化されていない / 本番環境 URL が環境前提に紛れている | 再現手順が第三者再現不能（fail の記録として成立しない）/ defect の必須 3 点セット欠落 / severity の重大な過小評価（critical 相当を low と判定） |
| `High` | 網羅性・実現性・信頼性の重大な欠落があり、実行・報告の価値を大きく損なう | 主要機能の境界値・異常系が欠落 / steps が Playwright 実行可能性基準を満たさず実行不能 / depends_on の循環・深い依存で大量 blocked が確実 | 原因分類が誤っており報告が誤誘導する / severity の過大・過小評価（1 段階超のずれ）/ エビデンスが主張を裏付けていない |
| `Medium` | 品質・効率を下げるが、実行・報告は成立する | expected の曖昧さ（機械判定困難）/ 検証データの明記不足 / postconditions の復元漏れ（影響が限定的なもの） | 再現手順の軽微な不足（環境情報の一部欠落）/ severity の 1 段階のずれ（境界的なケース） |
| `Low` | 軽微な改善余地 | title・表現の改善 / ケース粒度の好み / 優先度付けの提案 | エビデンス命名の改善 / 記録表現の統一 |

## 2. PASS / NEEDS REVISION 判定基準（設計文脈のみ）

### 2.1 基本判定

| 判定 | 条件 |
|------|------|
| `NEEDS REVISION` | 統合後の指摘に **Critical または High が 1 件以上**ある |
| `PASS` | 上記以外（Medium / Low のみ、または指摘なし） |

### 2.2 補則

- **信頼度下限**: 信頼度 **40 未満**の指摘は判定のカウント対象外とし、「参考指摘」としてレポートに別掲する（根拠の弱い指摘で承認を止めない。ただし隠さない）
- **判定に含めないもの**: 参考指摘 / レビュー範囲外への指摘（scope 外のケース・ソースコードへの指摘）/ 未確認事項
- **未確認事項の扱い**: 判定対象外だがレポートへの列挙は必須。エージェントが入力不足で評価できなかった観点（例: 環境情報未提供で実現性が評価不能）が主要観点に及ぶ場合は、PASS でもその旨を承認の但し書きとして明記する
- PASS は「レビュー観点で実行に進める品質」を意味し、テスト対象の品質やリリース可否の判断ではない
- 結果文脈では本ゲートを**適用しない**（4 章）

### 2.3 判定後の動作

| 判定 | 動作 |
|------|------|
| PASS | レビュー対象ケースの `review_status` を `approved` 化（手順・書き換え範囲は review-procedures.md 3.4 章）。以降ケース内容を変更すると revision +1 で draft に戻る（`yaml-schema-cases.md` 3 章） |
| NEEDS REVISION | test-cases.yaml へ書き込まない。差し戻し事項（修正指示リスト）を返却する。修正ループの実行・上限管理はオーケストレータ（`execution-policy.md` 1.1 章） |

## 3. 指摘統合規則（両文脈共通）

| 規則 | 内容 |
|------|------|
| 重複排除 | 同一対象（ケース ID / 欠陥）かつ同一趣旨の指摘は最も的確な 1 件に統合し、出所エージェントを併記する |
| 統合時の重要度・信頼度 | 重要度は統合元の**最高値**を採用する。信頼度は最も高い値を基本とし、複数エージェントが独立に同趣旨を指摘した場合は根拠が補強されたものとして上方修正してよい（修正した場合は統合による旨を付記） |
| 矛盾の扱い | エージェント間で矛盾する指摘は両論を保持し、判定では重要度の高い側を採用しつつ、両論をレポートに明記する（ユーザー判断の材料） |
| ランキング | 重要度降順 → 信頼度降順で並べる |
| 信頼度なしの指摘 | 信頼度が付与されていない指摘はそのまま採用せず、根拠から本スキルが信頼度を見積もって付与する（付与できない場合は参考指摘とする） |
| スコープ外の指摘 | レビュー範囲外（scope 外ケース・ソースコード・他フェーズの責務）への指摘は判定から除外し、必要なら「スコープ外所見」として別掲する |

## 4. 結果文脈の評価規準

結果文脈は PASS / NEEDS REVISION の判定を行わず、検証結果と引き継ぎ事項を返す（実行のやり直し・報告可否の判断はオーケストレータとユーザーが行う）。

引き継ぎ事項の必須項目:

| 項目 | 内容 |
|------|------|
| 報告書への注記事項 | 原因分類の結果（テストケース不備由来の fail はその旨）・ユーザー影響の所見・その他報告書に注記すべき事項。これらはオーケストレータが results_manager.py の `annotate` サブコマンドで注釈として登録し、報告書生成時に「所見・注記」として機械出力される（test-report による手動転記は行わない） |
| エビデンス補完の要否 | 3 点セット要件（`evidence-policy.md` 1 章）を満たさない defect の一覧と不足項目（最終バリデーションで生成中断になる前に補完させる材料） |
| severity 補正案 | 対象 case_id / 現行値 → 提案値 / 根拠（severity-policy.md のどの基準に照らしたか）。**実績への反映は本スキルでは行わない**（test-results.yaml は読み取り専用） |
| ケース起因の fail | 原因分類が「テストケース不備」の fail は、test-design での修正候補（対象ケース ID と修正方向）として明示する |

## 5. 禁止事項

- 欠陥 severity の enum 値・判定基準を本書に複製すること（SSOT は severity-policy.md）
- 指摘重要度と欠陥 severity を混同すること（1.1 章）
- エージェントの所見をそのまま総合判定として採用すること（判定は統合後の指摘から本スキルが行う）
- 信頼度 40 未満の参考指摘を根拠に NEEDS REVISION とすること・逆に参考指摘を隠して PASS の見かけを整えること
- 結果文脈で test-results.yaml の severity・記録を書き換えること（補正は提案のみ）
- 未確認事項を判定対象から外したことを理由に、レポートから省略すること
