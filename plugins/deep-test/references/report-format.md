# 報告書フォーマット規約（report-format）

テスト報告書（Excel / Markdown）の構成・スタイル・生成方式の SSOT。
`test-report` スキルが本規約に従い、実績 YAML（test-results.yaml / test-cases.yaml）から報告書を生成する。

---

## 1. 共通原則

| 項目 | 規範 |
|------|------|
| ファイル数 | 報告は **1 ファイル**（Excel `.xlsx` または Markdown `.md`） |
| 形式選択 | 対話時: AskUserQuestion で Excel / Markdown を選択。非対話時: **Markdown 既定**（execution-policy.md 非対話既定値表） |
| 複数レベルの一括報告 | 複数テストレベルを同時実施した場合も 1 ファイル内で一括報告する（Excel: シート分け / Markdown: セクション分け） |
| 集計規則 | ケースごとの**最新 run 結果（latest）**を採用。過去 run は推移情報として扱う（詳細は retest-policy.md） |
| 再生成 | 実績 YAML が SSOT のため、報告書は何度でも再生成可能。同名ファイルは上書きしてよい（報告書は派生物） |
| 出力先 | セッション作業領域直下（最終成果物）。パス規約は data-locations.md 参照 |
| 機微情報 | 転載時のマスキング必須（evidence-policy.md） |
| 事前検証 | 生成前に最終バリデーション（evidence-policy.md 二段バリデーションの最終段: validate + scope 突合）を通過していること。未通過での生成は禁止 |
| 禁止記号 | セクション記号（U+00A7）を使用しない。図解が必要な場合は mermaid 記法を使用する |

## 2. ファイル命名

```
test-report_{target-slug}_{yyyyMMdd}.xlsx （Markdown 形式は同名で拡張子 .md）
```

例: `test-report_orderapp-web_20260717.xlsx`

- `{yyyyMMdd}` は報告書生成日。同日に複数回生成した場合は上書きでよい（セクション 1 再生成の原則）

## 3. Excel 構成

### 3.1 シート構成

| シート | 内容 |
|-------|------|
| サマリ | 対象・実行日・run 情報・レベル別集計表・NG 一覧・未確認事項・総合判定・免責注記（セクション 3.2） |
| 推移 | run 横断の status 推移表（セクション 3.3） |
| レベル別シート | **実施レベルのみ**作成。ケース単位の実行結果明細（セクション 3.4） |

レベル別シートのシート名（表示名）:

| level | シート名 |
|-------|---------|
| unit | ユニット |
| functional | 単体 |
| integration-internal | 内部結合 |
| integration-external | 外部結合 |
| system | システム |
| uat | 受入(UAT) |
| performance | 性能 |
| security | セキュリティ |

- レベル定義・用語注記の SSOT は test-levels.md（本表は報告書上の表示名のみを定める）

### 3.2 サマリシート

上から順に以下のブロックを配置する。

| ブロック | 内容 |
|---------|------|
| 基本情報 | 対象（target）・報告書生成日・実行日・run 情報（run_id / mode / environment）。直下に**エビデンスパス基準注記**（下記）を必ず出力する |
| レベル別集計表 | 行 = 実施レベル、列 = **対象数 / pass / fail / blocked / skipped / na / 自動 / 手動**（latest 集計。自動 = `executed_by` が `playwright-mcp` / `playwright-test` / `test-framework` / `api` の件数、手動 = `human-assisted` の件数）。最下行に合計。表の直下に**手動内訳注記**（下記定型文）を必ず出力する |
| NG 一覧 | fail ケースの一覧: ケース ID・レベル・タイトル・severity・エビデンス参照（詳細はレベル別シートへ） |
| 未確認事項 | skipped ケースの一覧: ケース ID・レベル・reason（0 件の場合も「なし」と明記。「未実施を問題なしと書かない」原則の出口）。latest に test-cases.yaml 未定義の実績 ID がある場合は「ケース定義に存在しない実績 ID」として併記する（黙殺しない） |
| 所見・注記 | 未確認事項ブロックの下に annotations（annotate 追記分）の表: 出所・対象（case_id / run_id。両方 null は「全体」）・本文。0 件の場合は表ごと省略 |
| 総合判定 | 下表の 3 値判定 |
| 免責注記 | セクション 6 の 6 項目 |

エビデンスパス基準注記（両形式のサマリ部に必ず出力する定型文）:

> エビデンス参照はテスト実績データディレクトリ基準の相対パスであり、本報告書からの相対リンクではない。基準ディレクトリは test-results.yaml の実パスから導出して注記に明示する（導出不能時は「既定配置の場合 `.claude/.local/plugins/deep-test/{target-slug}/`」とフェイルセーフ表記）。

（参考・報告書には出力しない運用知識）エビデンス実体は報告書（セッション作業領域）とは別ディレクトリにあり、外部共有時は `archive_evidence.sh` で evidence 一式をまとめる（data-locations.md 7 章）。

手動内訳注記（両形式でレベル別集計表の直下に必ず出力する定型文。件数 X / Y は latest 採用の実施ケースを test-cases.yaml の `automation` で機械集計した値）:

> 手動内訳: manual-assist X 件 / exploratory Y 件。human-assisted の結果は人間の実施・申告に基づく。

総合判定:

| 判定 | 条件 |
|------|------|
| PASS | latest 集計で fail = 0 かつ blocked = 0 かつ skipped = 0（na は対象外として併記） |
| FAIL | fail が 1 件以上 |
| INCOMPLETE | fail = 0 だが blocked または skipped が 1 件以上（未確認が残る） |

- 総合判定は実績の機械的集計であり、**リリース可否・受入可否の判断は人間が行う**（免責注記と併せて明記する）

### 3.3 推移シート

| ブロック | 内容 |
|---------|------|
| run 集計推移（上段） | 行 = run（run_id・実行日時・mode）、列 = pass / fail / blocked / skipped / na 件数。時系列昇順 |
| ケース別推移（下段） | 行 = ケース ID、列 = run（時系列昇順）、セル = 当該 run での status（未実行は空欄） |

### 3.4 レベル別シート（列定義）

| # | 列 | 内容 |
|---|-----|------|
| 1 | ケース ID | test-cases.yaml の id |
| 2 | revision | 実行時点のケース revision（case_revision） |
| 3 | タイトル | ケース名 |
| 4 | 優先度 | high / medium / low |
| 5 | 実行手順 | steps（番号付きを改行で連結） |
| 6 | 期待結果 | expected |
| 7 | 実際結果 | actual |
| 8 | status | pass / fail / blocked / skipped / na（latest） |
| 9 | 実行主体 | executed_by（`playwright-mcp` / `playwright-test` / `test-framework` / `api` / `human-assisted`。`human-assisted` は人間の実施・申告に基づく記録） |
| 10 | reason | blocked / skipped / na の理由 |
| 11 | 実行時間(秒) | duration_sec（秒）。値が 0（0.0）の場合は `<0.01` と表示する（記録値は変更しない） |
| 12 | エビデンス参照 | **相対パス文字列**（複数件は改行区切り。ハイパーリンク化・画像埋め込みは行わない） |
| 13 | NG 詳細 | fail 行のみ: 再現手順・検証データ・severity・補足情報 = defect.extras のキー・値（マスキング適用済み。500 文字超の値は先頭 500 文字 + 「…（省略）」に切り詰め） |
| 14 | 補足情報（extras） | results[] 直下 `extras` のキー・値（status を問わず。pass 行の実測値等の構造化情報。マスキング・切り詰めは列 13 と同一規則） |

- ユニット / 単体のシートには、シート先頭（表の直上）に用語注記を 1 行付す（ユニット = コードレベルの自動テスト（テストフレームワーク実行） / 単体 = 実アプリの画面・機能単位テスト（Playwright 実行）。他レベルのシートには不要。文言の SSOT は test-levels.md）
- **results[] 直下 `extras` の転載**: 列 14「補足情報（extras）」の転載規則（status を問わず・pass 行の実測値等の構造化情報が該当・列 13 と同一のマスキング/切り詰め）は、Markdown のレベル別テーブル末尾列「補足情報（extras）」にも同様に適用する

### 3.5 スタイル定義

| 項目 | 定義 |
|------|------|
| ヘッダ行 | 背景 = 濃紺（#1F3864）、文字 = 白（#FFFFFF）・太字。全シート共通 |
| セル書式 | 折り返して全体を表示（wrap text）・縦位置は上詰め。罫線は表範囲に細実線 |
| ウィンドウ枠固定 | 各シートでヘッダ行を固定。レベル別シートはヘッダ行 + ケース ID 列を固定（B2 固定） |

列幅目安（レベル別シート）: ケース ID 16 / revision 9 / タイトル 32 / 優先度 9 / 実行手順 45 / 期待結果 35 / 実際結果 35 / status 10 / 実行主体 12 / reason 25 / 実行時間(秒) 10 / エビデンス参照 40 / NG 詳細 50 / 補足情報（extras） 40

status 列の条件付き書式（推移・レベル別シート共通）:

| status | 塗りつぶし | 文字色 |
|--------|-----------|-------|
| pass | 緑系 #C6EFCE | #006100 |
| fail | 赤系 #FFC7CE | #9C0006 |
| blocked | 橙系 #FCE4D6 | #974706 |
| skipped | 灰系 #D9D9D9 | #404040 |
| na | 薄灰 #F2F2F2 | #808080 |

印刷レイアウト（A4 横）:

| 項目 | 定義 |
|------|------|
| 用紙・向き・拡大縮小 | A4・横（landscape）。横 1 ページに収める（fitToWidth = 1、縦は成り行き fitToHeight = 0） |
| タイトル行 | ヘッダ行を各ページ先頭にリピート印刷 |
| 印刷範囲 | 各シートのデータ範囲に設定（余白セルを含めない） |
| 改ページ | レベル別シートは行数が多い場合も自動改ページに委ね、シート単位でレベルが分かれていること自体を区切りとする |

### 3.6 生成方式

| 項目 | 規範 |
|------|------|
| ライブラリ | openpyxl による**全コード生成方式**（シート数・行数が可変のため、テンプレートファイルは採用しない） |
| 画像 | スクリーンショットは**埋め込まない**。エビデンス参照列に相対パス文字列で記載する（ファイル肥大・破損リスク回避） |
| 生成スクリプト | `test-report` スキルの `${CLAUDE_PLUGIN_ROOT}/skills/test-report/references/scripts/report/generate_excel.py` が担当（読み込み・集計は同ディレクトリの共通モジュール `report_model.py` に一元化し、Markdown 版と共有する）。実行手順・venv セットアップは同スキルの references に従う |
| 入力 | 生成スクリプト（共通モジュール report_model.py）が test-results.yaml / test-cases.yaml を直接読み込み、latest 採用・deprecated 除外・レベル集計を機械集計する（LLM の手動転記は行わない） |

## 4. Markdown 構成

1 ファイルに以下の章立て（この順序）で出力する。

| # | 章 | 内容 |
|---|-----|------|
| 1 | サマリ | 対象・実行日・run 情報・レベル別集計表（対象数 / pass / fail / blocked / skipped / na / 自動 / 手動）・総合判定（セクション 3.2 と同一基準）。基本情報の直下に**エビデンスパス基準注記**、レベル別集計表の直下に**手動内訳注記**（いずれもセクション 3.2 の定型文）を必ず出力する |
| 2 | 推移 | run 横断の集計推移表。必要に応じてケース別推移マトリクス |
| 3 | レベル別セクション | **実施レベルのみ**。セクション 3.4 と同じ項目を表形式で記載 |
| 4 | NG 詳細 | fail ケースごとの小見出しで: 再現手順（番号付きリスト）・検証データ（入力値・期待値・実際値）・severity・**エビデンスパス**（コード span 表記）・補足情報（defect.extras のキー・値。セクション 3.4 と同じ切り詰め規則） |
| 5 | 未確認事項 | skipped ケースの一覧（ケース ID・レベル・reason）。0 件でも「なし」と明記。latest に test-cases.yaml 未定義の実績 ID がある場合は「ケース定義に存在しない実績 ID」として併記する。章末尾に「所見・注記」小節（セクション 3.2 と同じ出所・対象・本文の表。0 件なら小節ごと省略） |
| 6 | 免責注記 | セクション 6 の 6 項目 |

- エビデンスは Excel と対称な**コード span のパス文字列表記**で記載する（例: `` `evidence/R20260717-143000/TC-FUNC-002/02_submitted.png` ``）。報告書の出力先（セッション作業領域）とエビデンス実体（テスト実績データディレクトリ）は別ツリーにあり相対リンクとして解決できないため、`[name](path)` のリンク構文は使用しない
- ユニット / 単体のセクションには、見出し直下に用語注記を 1 行付す（セクション 3.4 と同一文言。他レベルのセクションには不要）
- 表の列構成は Excel（セクション 3.4）と揃え、形式間で情報量の差を作らない。禁止記号（U+00A7）を使用しない点はセクション 1 の共通原則に従う

## 5. 集計・転載の共通規則

| 項目 | 規則 |
|------|------|
| 採用結果 | ケースごとの最新 run 結果（latest）。詳細規則は retest-policy.md |
| severity 表記 | critical / high / medium / low（判定基準は severity-policy.md。報告書内で独自基準を定義しない） |
| データ取得 | 集計値は生成スクリプト（report_model.py）が実績 YAML から機械集計した値を用いる（LLM による手計算・手動転記を禁止） |
| マスキング | エビデンス・再現手順・検証データ・所見・注記本文の転載時は evidence-policy.md のマスク形式を必須適用 |
| 所見・注記 | 実行結果に影響しない注釈（annotations）。追記は results_manager.py の annotate サブコマンド経由のみ（スキーマは yaml-schema-results.md 7 章）。0 件なら小節・表とも省略 |

## 6. 免責注記（両形式必須）

報告書には以下 6 項目の免責注記を必ず含める（Excel: サマリシート末尾 / Markdown: 最終章）。

| 項目 | 注記内容 |
|------|---------|
| UAT | UAT 支援は検証支援であり、**受入判断は人間**（発注者・業務部門）が実施する |
| 性能 | 性能テストは**単一セッションの応答時間計測が中心**であり、多重負荷試験は外部負荷ツール検出時のみの条件付き実施である |
| セキュリティ | セキュリティテストは **OWASP 観点の動的チェック**であり、ペネトレーションテストの代替ではない |
| 再テスト | **ng-only 再テストは回帰テストの代替ではない**（修正の副作用検出には full 再テストを推奨する） |
| 用語 | 本報告書の『ユニットテスト』は**コードレベルの自動テスト**、『単体テスト』は**実アプリの画面・機能単位のテスト**を指す（本プラグイン独自の区分であり、JSTQB/ISTQB の呼称とは異なる） |
| 手動 | `executed_by: human-assisted` の結果は**人間の実施・申告に基づく記録**であり、機械検証（自動実行）とは実行主体が異なる（実行主体列・サマリ内訳で区別する） |

- 文言は対象・実施状況に合わせて具体化してよいが、6 項目の趣旨を欠落させない
- 実施していないレベルに関する項目も削除しない（実施範囲の誤解を防ぐため、実施有無を添えて記載する）
