# harness-init エージェント運用定義

## このスキルで使用するエージェント

| 用途 | subagent_type | 実行形態 |
|------|--------------|---------|
| プロジェクト調査（下表の 4 観点） | `Explore`（読み取り専用調査）または `general-purpose` | 並列（Independent 型） |
| ドキュメント一括生成（Phase 4、10 件超過時のみ） | `general-purpose` | フォルダ単位で並列 |

## Phase 3: 調査エージェント構成（並列）

| # | 担当領域 | 調査内容 | 対応する生成先 |
|---|---------|---------|---------------|
| 1 | 技術スタック・環境 | 言語 / フレームワーク / バージョン、ビルド・テスト・リント・起動コマンド、環境変数、CI 設定 | `.claude/CLAUDE.md` / `environments/` |
| 2 | 機能・画面 | 画面・機能の一覧（名称 / 対応ソース / 概要）、画面遷移、ルーティング定義、業務ルール | `specs/` / `flows/` |
| 3 | アーキテクチャ・データ | モジュール構成・依存関係・レイヤ構造・データモデル（テーブル / エンティティ） | `architecture/` / `system-designs/` |
| 4 | 規約・判断・用語 | linter / formatter 設定、命名・配置の実態パターン、コード実態から読み取れる技術選定、ドメイン用語 | `conventions/` / `decisions/` / `glossary.md` |

### 起動時の必須プロンプト要素

各調査エージェントのプロンプトには以下を必ず含める:

1. 対象プロジェクトのルートパス
2. 担当領域の調査観点（上表）
3. 「ソースから確認できた事実のみを報告し、根拠ファイルパスを添える。推測は『推測』と明示する」
4. 返却フォーマット（統合しやすい Markdown 表）

### エラー増幅への対策

Independent 型並列調査のため、統合時にメインが以下を検証する:

- 調査結果間の矛盾（例: エージェント 1 と 3 で異なるフレームワーク報告）→ メインがソースを直接確認して裁定
- 根拠パスの実在確認（サンプリングで可）

## Phase 4: 生成エージェント構成（10 件超過時のみ・並列）

フォルダ単位（specs / system-designs / flows 等）で `general-purpose` に委譲する。プロンプトには以下を必ず含める:

1. テンプレートパス（`${CLAUDE_PLUGIN_ROOT}/references/template/` 配下の該当ファイル）
2. frontmatter 規則（`${CLAUDE_PLUGIN_ROOT}/references/structure-spec.md` 節 5）
3. Phase 3 の解析結果のうち担当フォルダ分
4. 「確認できない内容は `TODO:` と書く。推測で仕様を記載しない」制約

ファイル競合防止のため、**1 フォルダ = 1 エージェント** とし、同一ファイルを複数エージェントが書かないよう分割する。各フォルダの `CLAUDE.md` 索引と `.claude/CLAUDE.md` はメインが最後に生成する。
