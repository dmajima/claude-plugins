# case-09: 合意確認で修正指示が出た場合

## 入力

```text
（Phase 5 の合意確認で）「修正あり」を選択し、修正内容を指示する
```

前提: Phase 4 までが完了し、生成した `draft` ドキュメントの一覧と要旨をユーザへ提示済み。

## 期待動作

1. Phase 5 手順 2 の `AskUserQuestion` で合意可否を確認する（全て合意 / 個別選択 / 修正あり）。個別選択は 1 回の呼び出しへまとめて提示する
2. 承認されたドキュメントのみ `status` を `agreed` に更新し、`updated` を更新する
3. 修正指示があったドキュメントは **`status: draft` のまま** 修正を反映し、再提示する
4. 再提示後に承認されたものが `agreed` へ遷移する。修正のやり取りが続く間は `draft` を維持する
5. 修正内容はユーザの明示指示の範囲に限る。指示で埋まらない箇所は `TODO:` のまま残す
6. 報告では `agreed` と `draft` の件数を分けて示し、`draft` のまま残った理由を添える

## 期待出力

- 修正を反映したドキュメントの差分要旨と再提示内容
- 最終的な合意状態（`agreed` N 件 / `draft` M 件）と、`draft` のまま残った理由
- 未確定事項一覧（修正指示でも埋まらなかった `TODO:`）

## 禁止事項（このケースで起きてはならないこと）

- 修正指示のあったドキュメントの `agreed` 化
- 未提示・未承認のドキュメントをまとめて `agreed` にすること
- 修正指示に含まれない内容の追記・書き換え（合意根拠の範囲外。authoring-spec.md 節 1.1）
- 個別選択の確認を 1 件ずつ別々の `AskUserQuestion` に分割すること
- `status` 更新時の `updated` 更新漏れ
- `agreed` 化に伴う合意ベース定型注記の除去（除去は `implemented` への昇格時）

## 分岐の根拠

procedures.md Phase 5 の手順 2〜4（合意可否の確認・承認分のみ `agreed` へ更新・修正指示は反映のうえ `draft` のまま再提示）。`status` の遷移定義は structure-spec.md 節 5.2、定型注記の除去タイミングは authoring-spec.md 節 1.1。
