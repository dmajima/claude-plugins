# case-11: 委譲エージェントの違反を統合検証で検出

## 入力

```text
/project-harness:update
```

前提: 反映対象が 5 件を超えたためドキュメント単位でサブエージェントへ並列委譲した（case-09 の流れ）。統合時の検証で、1 件のエージェントが担当外ファイルへ書き込んだ、または担当ドキュメントの frontmatter（`title` / `sources` / `updated`）を破壊したことを検出した。

## 期待動作

1. Phase 4 の統合検証（agents.md「エラー増幅への対策」）で違反を検出する:
   - `git status` の編集ファイル一覧と委譲した担当ファイル一覧を突合し、担当外への書き込みを検出する
   - 各担当ドキュメントの frontmatter 3 フィールドの存在を確認し、破壊を検出する
2. 違反した変更を是正する:
   - 担当外ファイルへの書き込み → 当該ファイルの変更を破棄する（`git checkout --` 等）。破棄前に変更内容をユーザへ提示する
   - frontmatter 破壊 → 破壊されたフィールドを元の値で復元する（元値は `git diff` から取得）
3. 是正後、当該ドキュメントの反映をメインが直接やり直す（同一エージェントへの再委譲は行わない）
4. 検出内容・是正内容を報告に明示する（違反を黙って修正して完了報告しない）

## 期待出力

- 検出した違反の内訳（エージェント / 対象ファイル / 違反種別）
- 実施した是正内容と、やり直した反映の結果
- 反映結果表（正常完了分と是正分を区別して記載）

## 禁止事項（このケースで起きてはならないこと）

- 統合検証（担当外書き込みチェック・frontmatter 検証）の省略
- 違反を検出しながら報告せずに完了扱いとすること
- 担当外ファイルの変更をユーザへ提示せずに破棄すること
- 違反したエージェントへ同じ担当を再委譲して同じ違反を繰り返すこと

## 分岐の根拠

agents.md「エラー増幅への対策」（Independent 型並列反映で必須の統合検証）の NG 経路。case-09 は検証を通過するハッピーパスのみを扱う。
