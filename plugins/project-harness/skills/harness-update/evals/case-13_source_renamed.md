# case-13: ソースの移動（rename）を検出

## 入力

```text
/project-harness:update
```

前提: 最終同期コミット以降で `src/report/` が `src/features/report/` へ移動された（`git diff --name-status` が `R100` を返す）。`specs/report.md` と `system-designs/report.md` の `sources` は旧パス `src/report/**` を指している。

## 期待動作

1. Phase 2 で rename（`R`）を検出し、**旧パス** で既存ドキュメントの `sources` を照合する
2. マッチした 2 件を「ソース移動」に分類する（旧パス消失を理由に整理候補へ入れない）
3. 反映計画で「`sources` を新パスへ更新」と提示する
4. 反映時に `sources` を `src/features/report/**` へ書き換える。ファイル内容に実質的な変更が無ければ記載本文は据え置く
5. 移動と同時に内容変更もある場合は「更新」も併発させ、記載の乖離を解消する

## 期待出力

- ソース移動として反映した件数と、更新前後の `sources` 値

## 禁止事項（このケースで起きてはならないこと）

- 旧パスの消失を「対応ソース全削除」と誤判定し、アーカイブ・削除を提案すること
- 新パスを「どの sources にもマッチしない追加」と誤判定し、同内容の新規ドキュメント作成を提案すること（既存ドキュメントの重複生成）
- `sources` の更新漏れ（以後の差分照合が機能しなくなる）

## 分岐の根拠

sync-spec.md 節 2 の 5 分類のうち「ソース移動（R）」。整理候補（case-05）と新規候補の両方に誤って二重分類されうる経路であり、独立した検証が必要。
