# case-12: リファクタリングのみの差分

## 入力

```text
変更をドキュメントに反映して
```

前提: 最終同期コミット以降の差分が内部構造の変更のみ（クラス分割・メソッド抽出・ファイル移動等）で、画面・業務ルール・アプリ動作に変化がない。`git log --oneline` は refactor 系コミットのみで構成され、feat / fix を含まない。

## 期待動作

1. Phase 2 で `git log --oneline <sha>..HEAD` を取得し、変更の意図が内部構造の変更のみであることを確認する
2. diff の内容から外部から観測できる動作（画面表示・業務ルール・API の入出力）に変化がないことを裏づける
3. 反映範囲を絞る:
   - `specs/`（何を作るか）・`flows/`（画面の場所・導線）は据え置く
   - `system-designs/`（実装構成・処理フロー）・`architecture/`（モジュール依存）を更新する
   - ファイル移動があった場合は該当ドキュメントの frontmatter `sources` を新パスへ更新する
4. コミットメッセージの分類と diff の内容が食い違う場合（refactor と称して動作が変わっている等）は diff を優先し、`specs/` も更新対象に含める

## 期待出力

- 反映結果表と、`specs/` / `flows/` を据え置いた理由（外部動作に変化なし）の明示

## 禁止事項（このケースで起きてはならないこと）

- コミットメッセージの分類のみを根拠に据え置き判断すること（diff による裏づけを省略しない）
- 内部構造の変更を `specs/` の業務ルール変更として誤って反映すること
- ファイル移動時の `sources` 更新漏れ（以後の差分照合が機能しなくなる）

## 分岐の根拠

procedures.md Phase 2「コミットメッセージの活用」の分岐。変更の意図に応じて反映先フォルダを絞り込む判断であり、case-01（機能変更を含む標準反映）とは反映範囲が異なる。
