# case-17: 実装追随の対応が一意に推定できない

## 入力

```text
/project-harness:update
```

前提: ハーネス構築済み。未実装の仕様ドキュメントが 2 件ある（`specs/order-entry.md` は `status: agreed`、`specs/order-history.md` は `status: draft`。いずれも `sources: []`）。最終同期コミット以降に追加された `src/features/order/` 配下のファイル群が両ドキュメントの命名・記載に部分的に合致し、どちらへの対応とも決めきれない。

## 期待動作

1. Phase 2 手順 4 で `status: draft` / `agreed` のドキュメントを抽出し、どの `sources` にもマッチしない追加ファイル群との対応を照合する
2. 一次シグナル（パス・命名の類似性）で 2 件の候補が残り、二次シグナル（実装内容と仕様記載の一致）でも一意に絞り込めないと判定する（sync-spec.md 節 2.1 手順 3）
3. 自動で 1 件を選ばず、**候補一覧をユーザに提示して選択させる**。候補には各ドキュメントのパス・`status`・推定根拠としたシグナルを併記し、1 回の AskUserQuestion にまとめて提示する（procedures.md Phase 3）
4. ユーザが 1 件を選択した場合: 選択されたドキュメントを実装追随候補として確定し、Phase 4「実装追随の反映」へ進む（以降は case-16 と同じ）
5. ユーザが「いずれでもない」を選択した場合、または選択自体が困難な場合: 実装追随として扱わず **通常の新規ドキュメント候補へフォールバック** し、まとまった機能単位で新規ドキュメントの作成を提案する（procedures.md Phase 2 手順 5）
6. いずれの分岐でも、選択されなかった候補ドキュメントは `status` / `sources` とも変更せず据え置く

## 期待出力

- 候補一覧（ドキュメントパス・`status`・一意に絞り込めなかった理由）
- ユーザの選択結果と、それに応じた反映内容（実装追随の実施 / 新規ドキュメント候補へのフォールバック）

## 禁止事項（このケースで起きてはならないこと）

- 複数候補が残っているのに最も近い 1 件を自動選択して `sources` を設定すること
- 候補を 1 件ずつ順に確認し、長い割り込みの連鎖を作ること（1 回の AskUserQuestion にまとめる）
- フォールバック時に候補ドキュメントを整理候補として扱うこと（未実装仕様は対応ソース 0 件が正常。sync-spec.md 節 4）
- 選択されなかった候補ドキュメントの `status` を変更すること
- 実装追随として扱えないことを理由に、追加ファイル群を反映対象から丸ごと除外すること

## 分岐の根拠

sync-spec.md 節 2.1 手順 3「一意性判定」。実装追随候補とするのは対応が一意に推定できる場合のみであり、絞り込めない場合は「ユーザ選択」→「新規ドキュメント候補へのフォールバック」という 2 段の退避経路を持つ。誤った `sources` 設定が以後の差分検出を恒久的に歪めるため、曖昧なまま確定しない分岐が必要。
