# case-18: 非対話モードでの実装追随

## 入力

```text
/project-harness:update --non-interactive
```

前提: ハーネス構築済み。`specs/order-entry.md`（`status: agreed` / `sources: []`）に対応する実装 `src/features/order/` 配下が追加されている。ほかに既存ドキュメントの更新 2 件・新規ドキュメント候補 1 件の差分がある。

## 期待動作

1. Phase 1 の前提検査はすべて通過する（前提 NG 時は非対話では中断する。case-06 / case-07 / case-10 を参照）
2. Phase 2 手順 4 の実装追随の照合は **非対話モードでも実施する**（候補の特定までは行う）
3. Phase 3 で AskUserQuestion を発火せず、更新 2 件・新規 1 件を全反映する
4. 実装追随候補は **`sources` 設定・`status` 昇格のいずれも実施せず**、提案として報告に含める（SKILL.md 実行モード判定表・sync-spec.md 節 2.1 手順 5・procedures.md Phase 3 の確認方法表）
5. 対象ドキュメントの `status` は `agreed`、`sources` は `[]` のまま維持し、合意ベースの定型注記も残す
6. 索引 `CLAUDE.md` と `.sync-state.json` は通常どおり更新する
7. 報告に「実装追随はユーザ判断待ち。対話モードでの再実行が必要」と明記する

## 期待出力

- 反映結果表（更新 2 件・新規 1 件）
- 実装追随候補の一覧（対象ドキュメントと `status`・対応が推定される実装パス）と未実施の理由（承認必須のため）

## 禁止事項（このケースで起きてはならないこと）

- 非対話モードでの AskUserQuestion 発火
- 非対話モードでの `sources` 設定・`implemented` 昇格の実施
- 実装追随候補を新規ドキュメント候補として扱い、「新規は全反映」の経路に紛れて重複ドキュメントを生成すること
- 実装追随候補の存在を報告から省略すること（提案されなければユーザは対話での再実行を判断できない）
- 照合自体を省略し、追加ファイル群を無条件に新規候補へ送ること

## 分岐の根拠

SKILL.md 実行モード判定表（非対話では削除・アーカイブ・実装追随を実施せず提案のみ）と sync-spec.md 節 2.1 手順 5（承認を必須とする）。誤った `sources` 設定は以後の差分検出を恒久的に歪めるため、整理候補と同等の慎重さで扱う分岐。
