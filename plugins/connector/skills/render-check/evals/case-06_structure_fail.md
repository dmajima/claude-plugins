# Case 06: ADO Markdown でコードフェンス未クローズ（前処理で STRUCTURE FAIL → 修正 → PASS）

## 入力

| 項目 | 値 |
|-----|---|
| 起動フレーズ | "この本文、Azure DevOps の PR コメントでどう見えるか投稿前に確認して"（単体起動・ターゲット明示） |
| 起動経路 | 単体起動（発話でターゲット `ado-markdown` が確定しているため、ターゲット確認の AskUserQuestion は発火しない） |
| 引数 | 本文（下記）+ ターゲット `ado-markdown`（PR コメント） |
| フラグ | なし |
| 既存状態 | なし |

### チェック対象本文（行番号は先頭行を 1 行目として数える）

````text
ビルドエラーのログを貼ります。

```
error CS1002: ; expected

再現手順は別途共有します。
````

## 期待動作

### Phase 1: 入力確定
- 本文とターゲット `ado-markdown` を発話から確定する

### Phase 2: チェック実行（1 回目・前処理で打ち切り検出）
- 前処理: フェンス行（行頭バッククォート 3 つ）が 3 行目の 1 個のみ = **奇数個** → コード領域と地の文の分割が不能
- check-procedures.md セクション 0 に従い、STRUCTURE の FAIL（未クローズフェンス）として **最初に** 報告する
- 地の文の分割に依存する NOTATION / AUTOLINK は確定判定を保留する（分割不能のため。修正後の再チェックで実施）
- 本文全体が対象の SECRET / SIZE は実施する → いずれも検出なし

### Phase 3: 結果レポート
- STRUCTURE FAIL 1 件の表（3 行目・未クローズフェンス）+ 総合判定 FAIL を提示する
- 影響の説明を含める: 「3 行目のフェンスが閉じられていないため、4 行目以降（6 行目の地の文を含む）が全てコード表示になる」（azure-devops-markdown.md セクション 4 のフェンス開閉不一致 = FAIL）

### Phase 4: 修正提案と採用確認
- 修正案を提示する: 4 行目 `error CS1002: ; expected` の直後に閉じフェンス（行頭バッククォート 3 つ）を 1 行挿入し、ログのみをコード領域に収める
- AskUserQuestion で確認する（選択肢: 「修正案を採用して再チェック」/「採用せず終了（レポートのみ）」。「FAIL のまま投稿可」とは扱わない）
- ユーザーが「修正案を採用して再チェック」を選択する

### Phase 5: 再チェック（2 回目）と終了
- 修正後本文でフェンス行が 2 個（偶数ペア）となり、コード領域（ログ行）と地の文の分割に成功する
- 5 カテゴリ **全て** を再チェックする: NOTATION（Backlog 記法混入なし）/ AUTOLINK（地の文に `#` `!` `@` パターンなし。ログ行はコード領域のため対象外）/ STRUCTURE（フェンス偶数ペア）/ SECRET / SIZE → 全て検出なし
- 総合判定 PASS + 投稿プレビュー（ログ行のみがコードブロック表示になり、末尾の地の文が通常テキストで表示される旨の注記付き）を提示して終了する（単体起動のため投稿は行わない）

## 期待出力

| 項目 | 期待値 |
|-----|-------|
| 生成ファイル | なし（render-check はファイルを生成しない） |
| 標準出力（要約） | 1 回目: STRUCTURE FAIL 1 件（3 行目・未クローズフェンス・以降がコード表示になる説明）+ 総合判定 FAIL + 閉じフェンス挿入案 / 2 回目: 総合判定 PASS + プレビュー |
| 終了状態 | 成功（PASS レポート提示で終了・投稿なし） |

## 分岐の根拠

このケースが分岐するトリガーは 前処理のフェンス行数 = 奇数（1 個）である。コード領域と地の文の分割が不能となるため、NOTATION / AUTOLINK の確定判定より先に STRUCTURE FAIL（未クローズフェンス）を報告する経路に入る（check-procedures.md セクション 0）。
