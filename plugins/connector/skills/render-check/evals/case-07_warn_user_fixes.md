# Case 07: AUTOLINK WARN でユーザーが「修正する」を選択（インラインコード化 → 再チェック PASS）

## 入力

| 項目 | 値 |
|-----|---|
| 起動フレーズ | "この内容で PR 789 に進捗コメントを投稿して"（`azure` スキルへの発話。render-check はその内部ゲートとして起動） |
| 起動経路 | `azure` スキルの書き込み操作直前の必須ゲート呼び出し |
| 引数 | 本文（下記）+ ターゲット `ado-markdown`（PR コメント） |
| フラグ | なし |
| 既存状態 | 投稿先は Azure DevOps の PR コメントスレッド |

### チェック対象本文（行番号は先頭行を 1 行目として数える）

````text
@yamada 修正方針を確定しました。対応は本日中に完了予定です。
````

## 期待動作

### Phase 1: 入力確定
- 本文とターゲット `ado-markdown` を呼び出し元から受領する（ターゲット確認の AskUserQuestion は発火しない）

### Phase 2: チェック実行（1 回目）
- 前処理: コードフェンスが存在しないため本文全体を地の文として扱う
- AUTOLINK: azure-devops-markdown.md セクション 3・4 の表を地の文に適用し 1 件を検出する
  - 1 行目: 行頭の `@yamada` → メンション。**対象ユーザー（yamada と思われる）に通知が飛ぶ** ことを明示して WARN
- NOTATION / STRUCTURE / SECRET / SIZE: 検出なし（短文でも 5 カテゴリ全てを省略せず実施する）

### Phase 3: 結果レポート
- AUTOLINK WARN 1 件の表（行番号付き）+ 総合判定 WARN（FAIL なし・WARN あり）を提示する
- 投稿プレビューで `@yamada` の通知発生箇所を注記する

### Phase 4: ユーザー選択（修正する）
- WARN のみのため AskUserQuestion で「このまま投稿」/「修正する」を提示する
  - 「修正する」を選んだ場合の抑止案も併記する: `@yamada` をインラインコード化（azure-devops-markdown.md セクション 3 の通知抑止策）
- ユーザーが「修正する」を選択する

### Phase 5: 修正案の提示と採用
- `@yamada` をインラインコード（`` `@yamada` ``）化してメンション通知を抑止した修正済み本文を提示する（記法変換のみで文意は変えない）
- AskUserQuestion で採用可否を確認し、ユーザーが採用を選択する

### Phase 6: 再チェック（2 回目）と引き渡し
- 修正後本文で 5 カテゴリ **全て** を再チェックする（AUTOLINK のみの部分再検査をしない）
- `` `@yamada` `` はインラインコードのためコード領域扱いとなり、AUTOLINK 検査の対象外 → 全カテゴリ検出なし → 総合判定 PASS
- 投稿プレビュー（`@yamada` がコード表示になり、メンション通知が発生しない旨の説明付き）を提示する
- `azure` スキルへ総合判定 PASS と修正後本文を返す（投稿処理自体は `azure` スキルが実施する）

## 期待出力

| 項目 | 期待値 |
|-----|-------|
| 生成ファイル | なし（render-check はファイルを生成しない） |
| 標準出力（要約） | 1 回目: AUTOLINK WARN 1 件の表（メンションは通知が飛ぶ旨を明示）+ 総合判定 WARN + 修正案（インラインコード化）/ 2 回目: 総合判定 PASS + プレビュー |
| 終了状態 | 成功（PASS + 修正後本文を `azure` スキルへ引き渡し・投稿続行） |

## 分岐の根拠

このケースが分岐するトリガーは WARN 時の AskUserQuestion の選択 = 修正する である。case-02（このまま投稿）と同じ AUTOLINK WARN 起点だが、ユーザーが修正を選択するため、修正案の採用 → 全カテゴリ再チェック → PASS を経て修正後本文を引き渡す経路に入る。
